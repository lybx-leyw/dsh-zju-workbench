这个算法给出什么

一张可 review 的分配表＋一次可 dry-run 的搬移计划。它回答「这堆函数各自属于哪一类」，并把答案变成目录形状。

它不给出什么（边界，写死在设计里）

整文件搬走后相对导入必然断。分桶产物不是可运行仓库：桶是分类视图，存档是唯一可信副本。想让它可运行，得另做一次依赖重写 —— 那是重构，不是分桶。

01单位下沉到函数，标签才能被证据支撑

文件级标签只能靠文件名猜；函数级标签可以靠签名、导出、@decorator、调用边去支撑。粒度错了，后面所有覆盖率都是自欺。

02一个单位恰好一个标签

允许重复就是允许含糊。互不相交是并发裁决与「覆盖率 = 1.0」同时成立的前提 —— 也是这套算法从解析器那边唯一硬搬过来的性质。

03先挂账，后判定

打标阶段只记账，不动文件。判定留到聚合阶段 —— 那时才有「这个文件整体像什么」的信息。在信息不全时拍板，等于把局部最优焊死在树上。

04无主导就进 mixed，不猜

主导标签不足阈值时，文件进暂存桶等人工裁决。把 40% 的文件硬塞进 55% 的桶，是这张表最早失去可信度的方式。

05少数派必须外显，不许被主导标签吞掉

一个 pure-core 文件里混着一个 prompts 函数，桶照样定，但那一处必须进清单。被吞掉的少数派就是未来最贵的 bug。

06原文不动，因为这是唯一的回滚点

分桶产物可以随时重算，存档不能。每个桶内文件带 origin 指针与 contentHash —— 哈希一漂，说明存档与新代码已经不同源。
