观察NOTES · 05
01

旧图把「链」画成了「层」

旧版把 28 个 core 归成「处理链 A / 处理链 B / 汇流 / 旁路」四组，那是按语义印象分的，不是按数据流分的。

结果是 classroom-generate 与 classroom-studio 这种「上游 route 服务化」的真实关系反而看不见。现在每一组都挂在它实际消费的那条数据上 —— 04 的编排族只服务 04，不参与 01。

02

「汇流」一句话盖掉了三个节点

那句「把两条链的产物装成一个可用的工作台」不是节点，是三个节点被压成一句：资源终稿 → 入库 → zhiyunStudy。

压掉之后，lecture 依赖 parser、knowledge 依赖 storageDomain 这两条边在图上就没有了落点。

03

图上全画，仓里没有

旧版画了 CC98、学习通、教务三个源，看起来和课堂、学在浙大一样在用。实际上 zhiyunCc98 与 zhiyunXxt 在仓内没有任何消费者，zhiyunZdbk 只被登录页的健康探测摸一次。

这不是「图不够美」，是会误导判断：读者会以为停掉 CC98 会影响某条链路，其实一条都不影响。

04

终点有三类，不是一类

页面给人看（page-study 等）；工具给 agent 调（tool/study 的三个方法），注入点是 preset/lecture 那一行 —— 写进 profile 就会变成所有 preset 都看得到；skill 给 agent 先读后做（docs/contributing/skills/ 的 SKILL.md，经 skill-filesystem → dsh-skill → tool-skill 进会话目录）。

三者的数据形态完全不同：页面吃已装配的领域状态，工具吃服务 + 注册表并吐出结构化返回值，skill 吃磁盘上的 Markdown 并吐出一段指令。把它们画成同一类终点，就等于说「反正都是给人用的」。

还有一条：docs/contributing/skills/ 刻意不在任何扫描根里，所以它不会自动生效 —— 图上用虚线标出这一段，是因为它确实是断的，不是漏画。

怎么读沿一条泳道从左往右，就是一份数据从外部事实变成你能看见的东西的全部路径。节点右上角是包名；入 / 出 写的是形态变化，不是「做了什么」—— 做了什么是实现细节，形态变化才是契约。

为什么没有 vendor 与 radarpackages/vendor/* 与 packages/radar/* 有意不进 workspaces，前者是锁版上游、后者是未评审候选骨架，都不在当前产品的数据流上。

与代码的一致性服务名、provide / inject / ctx.get、宿主路由都取自查仓库当前状态；悬空节点的判据是可复核的搜索结果，不是推测。代码改动后这张图会过期 —— 运行时的活图在产品的「插件」页，它直接从 DSH 运行时读拓扑，不靠手抄。
