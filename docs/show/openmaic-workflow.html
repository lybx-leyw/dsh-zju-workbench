总览

谁在什么时候在场：一条泳道看清整条链路

横轴是时间，纵轴是角色

横着看是一个阶段，竖着看是同一时刻谁在干活。最值得注意的是第二段和第四段：人不在场，任务照跑； 以及第三段：worker 停下来等人，而不是人等着 worker。

图 1 总览泳道左侧灰条 = 角色；颜色 = 该格的主门控类型
总览逐段详解
阶段谁在场产出卡住 / 失败时
① 提交 人 + 服务端 一条 generation run，排队等 worker 领走。 请求体不合法或模型槽位缺失直接 400；超并发返回 429，不会静默排队。
② 生成 服务端 + 模型 + 外部 一份场景计划：每场类型、要点、时长、要不要图 / 视频。 单步 300s；重试耗尽就停在该步，Retry 从检查点继续，不重算已完成的步骤。
③ 确认 人（可被倒计时替代） 锁定后的场景清单，revision +1 后才允许继续。 标题为空的场景挡住“确认并生成”；revision 不匹配 409；确认前可 discard。
④ 逐场生成 服务端 + 模型 + 外部 完整课程文档：场景正文、动作脚本、旁白音频、媒体。 内容重试首场 2 / 其余 5 次；动作 60s、旁白 30s；媒体失败不暂停整条 run。
⑤ 完成 服务端 “生成完成”标记——只说明文档齐了，不等于对外可见。 多进程靠租约 / 心跳 / 接管，保证同一时刻只有一个 worker 写。
⑥ 上课 / 交付 人 + 播放器 + 模型 + 外部 作答与讨论记录；PPTX / 离线 HTML / ZIP / MP4。 纯播放段零 LLM；导出有总闸（大纲与媒体没落定就拦）；无渲染服务时 MP4 直接 501。
为什么总览值得单独画：把“谁在场”摊开之后，很多争论会自动消失。比如“生成过程能不能改单个场景”——④ 段学习者那条泳道是空的，所以不能； “要不要给大纲加自动质检”——③ 段本来就站着人，再加一道模型自评只是叠床架屋。门控该放在哪，取决于那一刻谁在场，而不是取决于哪一步看起来更重要。
图 2 / 生成

从输入到大纲，再到一场一场生成

服务端异步任务 · 关掉标签页也继续跑

主链只有一条：输入 → 受理 → 大纲 → 人类确认 → 阵容 → 场景循环 → 完成 → 发布/导出。 材料分析与研究是可选支线；媒体生成是一条与场景并发的旁路。

图 2 生成流水线橙色 = 人类确认门；虚线 = 可选 / 并发
图 2 逐节点详解
节点做什么谁把关卡住 / 失败时
输入 主题、材料、是否开交互 / 任务引擎；也可由外部智能体代填。 人类选文件与模式 请求体不合法或模型槽位缺失直接 400，不入队。
受理 解析 owner、校验请求、检查并发额度，写入 generation run 后入队。 系统schema / 配额 / 429 每 owner 活跃 2、排队 10、每进程 4；超限返回 429，不会静默排队。
材料分析 只选一个抽取器（首选，或首个同时支持 MIME 与能力的）；视觉图按优先级进入提示。 系统外部 视觉图 15s 预算、连续 3 次不可解析就停；整步超时 300s，失败可 Retry。
研究 小模型把需求改写成检索式，再搜索，结果喂给大纲提示。 LLM外部 没有 webSearch 槽位时该步直接跳过（工具本身不存在），计划不漂移。
大纲 流式生成场景计划：类型、要点、时长、媒体请求；手写扫描器边流边解析。 LLM系统 同模型重试 2 次 + fallback 1 次；content-filter 不重试也不切模型；300s 上限。
人类确认 整堂课唯一能“看到全局并整体改写”的干预点；可原样放行或改完再放行。 人类系统 空标题挡住“确认并生成”；revision 冲突 409；未产出课程前可 discard。
智能体阵容 生成人设、头像、音色绑定；教师优先用学习者选的旁白音色。 LLM系统 要求 ≥2 个 agent、恰好 1 个 teacher、JSON 可解析；不合格静默回落预设，run 不暂停。
场景循环 每个场景依次跑内容 → 动作 → 旁白；旁白与“追加场景”同一次提交。 LLM系统外部 内容解析失败按首场 2 / 其余 5 重试；耗尽暂停在该步；动作 60s、旁白 30s。
媒体支线 图片 / 视频按 elementId 去重后独立泳道生成，结果再放进场景。 系统外部 媒体失败不暂停整条 run；永久失败码不给 Retry，场景保留失败说明。
完成 / 发布 “完成”只表示文档齐备；“发布”才对外可见，需要真实账号和 course:publish。 人类系统 匿名 owner 一律拒绝发布；多进程靠租约/心跳/接管保证只有一个 worker 写。
导出 课程转 PPTX、离线 HTML、ZIP 或 MP4；媒体与页面按体积上限选择容器。 人类系统外部 有未完成大纲或媒体任务没落定就不让导；离线 HTML 400 MiB 转 ZIP；无渲染服务则 MP4 501。
图 2 没画出的关键点：生成链路只保证“结构合法、能播放”，不保证内容讲得对。所以真正的质量门最自然的位置是人类确认（人已经在那里）和测验 / PBL 的评价结果，而不是场景生成后再加一道程序审校。
图 3 / 上课

播放是一串动作，讨论才切进 live

纯播放零 LLM · 讨论由导演循环现场决定

课程不是视频文件，而是 21 种动作的序列。播放器按序执行；遇到 discussion 动作才进入 live， 由服务端导演拿着 4 个工具决定“谁先说、叫不叫学生、何时收尾”。

图 3 课堂运行时实线 = 状态迁移；虚线 = 讨论结束回到播放
图 3 逐节点详解
节点做什么谁把关边界
状态机 idle → playing ⇄ paused；讨论动作进入 live；学生打断也在这里收敛。 人类播放 / 暂停 / 跳转 跳转只能从可重建的前缀跳；视频、讨论、组件操作不参与安全跳转。
动作执行 按序执行 speech、spotlight、laser、play_video、白板、discussion、组件操作等 21 种动作。 系统allowlist / 时长 spotlight / laser 是 fire-and-forget，不阻塞游标，5s 自动清除。
讨论触发 discussion 动作把课堂切进 live；讨论卡延迟 3s 出现，再倒计时 5s 自动跳过。 人类系统 讨论不是智能体“自主发起”，而是生成期写进场景的动作。
Pi 导演 导演每轮决定叫谁发言、要不要 cue 学生、何时收尾；板书等由被叫智能体执行。 LLM系统 4 个工具白名单；close_session 需已有可见发言，cue_user 需已有实质教学回合。
学生 随时提问、举手、作答、提交；也可以退出讨论。 人类 学生不问，这一段就不发生；cue_user / close_session 一旦成立，本回合结束。
测验 / PBL 客观题本地精确判分，简答题交模型判；PBL 走规划 → 导师 → 角色扮演 → 评价。 LLM系统人类 简答分 clamp 到 [0, points]，≥80% 才算对，判分失败兜底 50%；PBL 任务 60 分通过。
这层的代价：导演是真正的 LLM 门控，节奏不预设，所以同一门课两次播放的讨论不会一样。纯播放段则完全确定性，适合离线导出和 MP4 渲染。
图 4 / 卡住时

三个确认档，四类失败

同一道门的不同开法 · 重试不是审校

大纲确认看起来只有“等人”和“自动”，实际有第三档 countdown；失败处理也不是“都重试”， 而是按状态码、安全拒绝和场景序号分流。

图 4 确认模式与失败分类左：确认门怎么开；右：失败后怎么走
图 4 详解：确认门与失败分类
情形实际行为容易误读的地方
wait run 释放 worker，一直停到大纲确认；设置项“总是审大纲”打开时走这里。 input.ts 的 schema 缺省也是 wait，但真实入口很少走到。
countdown 就绪 2500ms 后自动确认；期间打开审阅页会 hold 住，把它变回人工确认。 浏览器默认就是这一档，所以“默认一定等人”是过期说法。
auto 生成大纲的同一次提交里直接确认，不等人。 无头生成 API 强制 auto；批量 / 脚本入口也走它。
可重试错误 408 / 409 / 425 / 429 / 5xx 按指数退避重试，带抖动。 重试只表示“再问一次”，不表示有人复核过内容。
不可重试错误 400 / 401 / 403 / 404 / 422 立即判该步失败。 显式配额拒绝也不重试；宿主自己的失败可以覆盖状态码判断。
安全拒绝 content-filter 直接停，不重试也不切 fallback。 不是“模型偶发失败”，而是供应商侧的安全拒绝。
场景失败 内容解析失败重试：首场 2 次，其余 5 次；耗尽暂停在该步。 Retry 从该步继续，已完成检查点不重算。
进程死亡 租约过期后被其他 worker 接管；接管次数超限则暂停。 多进程只有一个写者，不靠“谁先抢到”碰运气。
这三个档位是同一道门，不是三道门。只有 auto 会让人彻底离场；countdown 只是把“人可能来不及看”变成默认路径，所以产品把审阅页设计成“点开就 hold 住”。
补充

图上画不出来的三件事

内容正确性没有门

生成链路只保证结构合法、可播放。学科上对不对，没有程序校验，也没有二次审校。要加质量门，最自然的位置是人类确认和测验 / PBL 的评分结果。

交互页只验语法，不验功能

生成期用 node:vm 编译脚本，语法错就拒；但不会真的点一遍。运行期只有沙箱和观察上限（32 KiB / 深度 64 / 800ms），没有功能验收。

工作台没有逐工具审批

智能体直接改真实课程文档，代码里没有 permission / approval 门。人类门控靠“看结果再要求改”、技能 SOP 的提示词约定，以及发布时的账号与角色。
