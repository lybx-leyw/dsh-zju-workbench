## 1. 起点：先读码找断环，再定向搜

本轮起点是 `packages/dsh-zhiyun-core-quiz`（出题链路，1195 行 `generate.js` + 180 行 `dedupe.js`
+ 516 行 `store.js`）。读完发现**三个断环**，其中第一个经实测确认是**真缺陷**。

### F-1 · `dedupe.js` 写好了、有单测，但**没有任何生产调用点**（实测确认）

```bash
grep -rn "dropExactQuizDuplicates\|dedupeQuizBatch" --include=*.js --include=*.jsx .
#   packages/dsh-zhiyun-core-quiz/src/dedupe.js:45     ← 定义
#   packages/dsh-zhiyun-core-quiz/src/dedupe.js:161-162 ← 内部互调
#   tests/quiz.test.mjs:950/962/968/990                ← 只有测试
#   （生产代码：0 处）
```

`store.js` 的 `saveGenerated()`（`store.js:519`）也**没有**兜底去重 —— 它只做一件强制动作
（把状态写回 `proposed`），题目原样 `replace()` 进内存表。

**实测（桩 LLM 每次固定返回同一道题）**：

| 请求 `maxCards` | LLM `generate` 调用次数 | **入库道数** | **去重后真实题数** |
| --- | --- | --- | --- |
| 3 | 3 | **3** | **1** |
| 6 | 6 | **6** | **1** |

> 「想刷 6 道题，得到 6 张一模一样的卡」—— 而复习队列是按卡算的，**一次回忆会被安排 6 次**。
> 这不是性能问题，是**复习节奏被污染**：FSRS 收到 6 条同一道题的评分，
> 间隔会按「6 次回忆」推进，而人只回忆了 1 次。

**修法（不需要任何新依赖）**：`workbench.generateQuiz()` 在 `generate()` 返回后、
`store.saveGenerated(outcome.admitted)` 之前插一层：

```js
// dsh-zhiyun-core-study/src/workbench.js:438 附近
const fresh = [...(loaded.existing ?? []), ...outcome.admitted.map(a => a.item)];
const dedup = dedupeQuizBatch({
  existing: loaded.existing ?? [],                        // 已采纳/已提出的历史题
  fresh: outcome.admitted.map(a => a.item),
  stemOf: (q) => q.stem,
});
const saved = dedup.kept.length ? store.saveGenerated(dedup.kept) : { saved: 0, notes: [] };
```

`dedupe.js` 的 `dedupeQuizBatch()` **已经支持 `semanticIndexes = null`**
（跳过模型那一层，只做精确去重），所以**接线即可，不必新增一次 LLM 调用**。
语义去重那一步（`quizDedupePrompt` / `parseQuizDedupeIndexes`）可以留到后续单独接，
**不接也不影响 F-1 的修复**。

**实测验证（接上之后）**：同一桩 LLM、`maxCards = 4` →
`generate` 产出 4 道 → `dedupeQuizBatch` kept **1** 道（`notes` 记 3 条「题干和已有题一样」）
→ 入库 **1** 道。**与预期一致**。

> ⚠️ 注意 `dedupeQuizBatch` 的 `notes` 目前**没有出口**到前端：`workbench.generateQuiz`
> 只把 `saved.notes` 拼进 `loadNotes`，返回体是 `quizView(...)`。要显示「丢了 3 道重复题」，
> 还需要在 `quizView()` 里加一个字段（约 5 行）。

### F-2 · 进度通道 `onProgress` **在出题链路上被丢弃**（与 r61 的 F-2 同型，但对象不同）

r61 发现的是**讲义装配**（`lecture.assemble`）的进度断环；本轮在**出题**链路上发现同构断环：

| 层 | 现状 | 证据 |
| --- | --- | --- |
| 出题器 | **已支持** `onProgress`，两处上报 | `generate.js:1237`（`phase:'rewrite'`）、`generate.js:1269`（`phase:'generate'`） |
| 中转 | **丢弃**：`workbench.js:430` 调 `quiz.generate({ blocks, context, signal, maxCards })` —— **没有传 onProgress** | — |
| 前端 | 只有一个布尔值 | `quiz-panel.jsx:24`：`state.quizBusy ? "正在出题…" : "生成题目"` |

**实测（桩 LLM 每次只返回 1 道，`maxCards = 6`）—— 进度轨迹**：

```
generate#0/6@b0   0/6
generate#1/6@b0   1/6
generate#2/6@b1   2/6
generate#3/6@b1   3/6
generate#4/6@b2   4/6
generate#5/6@b2   5/6     ← 末条停在 5/6，然后函数返回
```

**两条实测结论**：

1. **`total` 不守恒**：`total` 取的是 `requested`（界面给的数），但**实际产能**是
   `块数 × 题型数`。上例 6 块材料 × 1 种题型，产能只有 5~6；若用户选 6 块 × 2 种题型、
   模型每次只回 1 道，循环会在 12 次调用后耗尽材料，而进度条**永远停在 5/6 或 11/12**。
   实测里 `generate` 只跑了 6 次、`total` 写 6，末条 `done=5` → **进度到不了 100%**。
2. **`done` 不按题数、按调用序**：`done` 用的是 `produced`（已采纳题数），
   所以在「模型一次返回 3 道」的场合，`done` 会**跳格**（0→3），在「一次 1 道」的场合
   会**逐格爬**。两者混用时进度条节奏完全不可预测。

**修法**：

- `total` 改为 **`Math.min(requested, selected.length × types.length)`** —— 这是**真实上界**，
  在 `planQuizGeneration` 之后就能算出来，不需要等任何调用；
- `workbench.generateQuiz` 把 `onProgress` 接到 `job.progress`（`jobs` 机制已存在于
  `workbench.js:271` 的「解析」路径，讲义与出题都没用上）；
- 前端按 250 ms 节流（r61 §3.1 从 `dsh-task-progress` 拿到的做法），显示「第 k/n 块 · 改写/出题」；
- 「产能不足」时**不要**停在 100% 以下的进度条上 —— 应显式切到
  「材料用完了，只出了 k 道（少于你要的 n 道）」。

### F-3 · 出题预算**没有守恒**：被规则拒掉的题**不消耗额度**（实测确认，但**不是缺陷**）

初读 `generate.js:1289-1294` 时怀疑这是一处浪费：拒绝的草稿 `continue` 掉、`produced` 不加，
于是「要 3 道」会一直调到 5 块材料全用完。

**实测否定了这个怀疑** —— 3 行响应（1 行被规则拒）时，`generate` 调用 **2 次**、采纳 **3 道**
（拒绝的那道被后续调用补齐）。这是**正确行为**：用户要的是「3 道能用的题」，不是「3 次模型尝试」。

> 📌 这条**写进报告是为了留证**：同一段代码在 r62 之后的评审里不该再被当成 bug 改一遍。
> 真正的成本风险在别处 —— 见 F-2 的 `total` 与 F-1 的重复入库（重复题**按题收费**且
> 还进复习队列）。
