## 1 · 本轮轴：为什么是「CC98 正文的读侧」

### 1.1 从一个已有骨架的 `README` 里读出的一处不对称

`packages/radar/dsh-radar-cc98-ubb-bridge/README.md` 把本仓的 CC98 文本能力总结得很清楚：

| 方向 | 能力 | 实现 |
| --- | --- | --- |
| **读进门**（UBB → 纯文本） | ✅ 已有 | `packages/dsh-zhiyun-source-cc98/src/ubb.js`（78 行手写正则） |
| **写出门**（Markdown → UBB） | ❌ 缺失 | 该骨架正是为补这一条而生成 |

也就是说：**写侧已经有主了**（`cc98-ubb-bridge`），**读侧却停在"78 行正则 + 纯文本"**。
按强化式集成的判据，读侧值得单独问一句：**这 78 行正则的天花板在哪？**

### 1.2 天花板是结构性的，不是"标签没列全"

`ubb.js` 的契约写死在函数签名上 —— `ubbToText(content) → string`。
一旦输出是**字符串**，下面这些信息就**无法恢复**：

- **嵌套层级**：`[quote]` 的深度被压成行首一个 `> [引用]`；两层引用与一层引用在输出里**逐字相同**；
- **原位偏移**：正文里哪一段对应原文的哪个字符区间，丢光；
- **媒体与文本的分界**：`[图片: url]` 是**占位符字符串**，与用户手打的同一串字**不可区分**；
- **样式语义**：`[color=red]` / `[size=5]` 一律剥成空，**颜色和字号是站点上的真实排版信息**。

所以这里的候选标准不是「再找一个更全的正则」，而是**换一种表示：AST**。
这正是本轮要搜的东西。

## 2 · 实测：BBob 到底能不能吃 CC98 方言

**不靠 `description` 判断**，直接装到临时目录跑了四组探针（`@bbob/core@4.4.1` + `@bbob/preset-html5@4.4.1`）。

### 2.1 探针一：方言覆盖（结论：能吃，而且认得出）

```js
parse('[upload=2]https://file.cc98.org/f.pdf[/upload] [ac01][em02][CC9801] [bili]BV1xx411c7mD[/bili]')
```

| 输入 | AST 结果 | 判定 |
| --- | --- | --- |
| `[upload=2]url[/upload]` | `{tag:"upload", attrs:{2:2}}` | ✅ 带参附件认得 |
| `[upload]url`（无闭合，站点历史写法） | `{tag:"upload"} + "url"` | ⚠ 标签认得，但 URL 落在**兄弟节点**，需桥接层重组 |
| `[ac01] [em02] [CC9801] [ms01] [tb01]` | 五个独立 tag 节点 | ✅ 表情编号原样保留（比本仓的 `[表情]` **不丢信息**） |
| `[bili]BV…[/bili]` | `{tag:"bili"}` | ✅ |
| `[quote]a[quote]b[/quote]c[/quote]` | **两层** `{tag:"quote"}` 嵌套 | ✅ 这正是本仓纯文本化丢掉的东西 |
| `[size=5][align=center]x[/align][/size]` | 两层属性节点 | ✅ 属性保留 |

### 2.2 探针二：字符偏移（结论：**这是最值钱的一条**）

每个 tag 节点带 `start:{from,to}` / `end:{from,to}`，指向**原文字符区间**：

```json
{"tag":"code","content":[...],"start":{"from":0,"to":6},"end":{"from":21,"to":28}}
```

本仓 `ubbToText` 的输出是**无处对应原文**的字符串 —— 想「点正文跳到楼层里那句话」没有任何锚点。
BBob 的偏移**天生就是锚点**。按「底层多调了更优质实现」这条判据，这是**现成能力为 0、上游直接给**的一块。

### 2.3 探针三：`[code]` 块 —— **本轮最重要的负面发现**

```js
parse('[code]if [b]x[/b] > 1[/code]')
```

**默认结果**：`[b]` 被解析成**真的 bold 节点**（`content: [{tag:"b", content:["x"]}]`）。

在 CC98 里这是**错的**：代码块内容必须是字面量。若直接接进渲染层，
「贴一段含 `[b]` 的代码」会**丢掉方括号、变成粗体** —— 这不是"少个功能"，是**改坏正文**。

**修复探针**：`{ contextFreeTags: ['code'] }`

```json
{"tag":"code","content":["if"," ","[","b]x","[","/b]"," ",">"," ","1"]}
```

内容**不再被解释**（✅ 语义正确），但被切成了 7 段 —— `[` 与 `b]x` 分离。
拼接后字面量正确，**但每个子串的 `from/to` 偏移不再可用**（这是 `contextFreeTags` 的实现代价）。

> **两条结论合起来才是完整的**：`[code]` 正确性**能修**（一个选项），但修完**牺牲该块内的偏移**。
> 因此「BBob 直接替换 `ubbToText`」是不成立的 —— 必须**分层**：`[code]` 走本仓现有正则、其余走 BBob。
> 这就是它只能评 🟡（需移植改造）而非 🟢 的原因。

### 2.4 探针四：依赖闭包（结论：可锁版，但依赖全为 `*`）

```
added 6 packages in 4s
@bbob/core 4.4.1 ← @bbob/parser 4.4.1, @bbob/plugin-helper 4.4.1, @bbob/types 4.4.1
@bbob/preset-html5 4.4.1 ← @bbob/plugin-helper, @bbob/preset, @bbob/types（均解析到 4.4.1）
```

| 检查 | 结果 |
| --- | --- |
| 安装干净、无 peer 冲突 | ✅ 6 个包，4 秒 |
| `package-lock.json` 有精确版本 | ✅ 8 处 `"version"` |
| **每个包的 `dependencies` 都是 `"*"`** | ⚠ **实测存在** |

> `"*"` 意味着**上游随时可能把 `@bbob/parser` 推到 5.x 而 `@bbob/core@4.4.1` 不跟着改**，
> 届时 `npm i` 会拉到不兼容版本。本仓 lockfile 能冻住**当前**解析结果，但**锁不住下一次 `npm i`**。
> 骨架的 `package.json` 因此**显式列出全部 6 个包并写死版本**，不只写顶层两个 ——
> 这是对「锁版」这条规则在 `"*"` 场景下的**唯一可行执行方式**，已在骨架 README 里写明。

## 7 · 本轮方法沉淀

- **"依赖里全是 `*`"是一个必须先查的字段**。`@bbob/*` 每个包都写 `"*"`，
  意味着只锁顶层版本**锁不住任何东西**。查法：装完后逐个读 `node_modules/<pkg>/package.json` 的 `dependencies`，
  而不是看 npmjs 页面的 `latest`。这与 r89「先看 `files`」、r90「先看有无 `main`/`exports`」同类 ——
  **都是"一个字段省掉一次误判"**。
- **探针要专门试"库作者没为自己的场景设计的那一块"**。BBob 的测试全在标准 BBCode 上，
  `[code]` 里放标签这种"论坛才有的脏数据"不会出现在它的用例里 —— 而 CC98 技术版**全是这种数据**。
  以后凡"通用格式解析库"进论坛场景，**`[code]` / 嵌套引用 / 无闭合标签**三件套必测。
- **`contextFreeTags` 这类"修复选项"要同时记它的代价**。它修好了语义，但代价是块内偏移失效，
  而偏移正是本候选的主要卖点之一。**只报"能修"不报"修完丢什么"，等于没测。**
- **B 组封板判断应看"轴"不看"组"**。r87 说"B 挖不到 A 类是结构性的"，那是**类型**结论，不是**轴**结论。
  B 组仍有未碰的轴：CC98 渲染（本轮）、课程表/日历（`ics` 侧历史上查过）、
  图书馆/借阅、统一身份的后端服务端（非登录）。
