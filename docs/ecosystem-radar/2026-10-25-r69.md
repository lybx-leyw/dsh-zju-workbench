## 1. 起点：先说结论 —— 这里**没有** F 级缺陷，我上一版报错了

本轮一开始读 `time.js:296-307` 的月历分格算式，认为它是「把上海 1 号 0 点算出的 UTC 时刻
当成月首取星期」。**这个判断是错的**，我把它撤回，并把原因写清楚 —— 因为它本身是本轮最有价值的产出。

```js
const firstUtc = Date.UTC(targetYear, targetMonth - 1, 1);   // 2026-11-01T00:00Z
const firstAt  = firstUtc - 8 * 3600 * 1000;                 // 2026-10-31T16:00Z
const dowOf = (ms) => Intl.DateTimeFormat('en-US', { timeZone: 'Asia/Shanghai', weekday: 'short' })…
const gridStart = firstAt - dowOf(firstAt) * 86400000;
```

我当时的推理是：`firstAt` = 10-31T16:00Z，按上海读是 **11-01**，
所以 `dowOf(firstAt)` 没问题；**但我先断言了「10-31 是 11 月 1 号的 0 点」之后又把它当成「上个月最后一天」**。
两句话互相矛盾，我当时只检查了前一句。

实跑（`node --input-type=module`，直接 import 本仓 `time.js`）：

| 检查 | 结果 |
| --- | --- |
| `dowOf(firstAt)`，`firstAt = 2026-10-31T16:00Z` | **`0`（周日）** —— 正是 2026-11-01 的星期 |
| `gridStart` | `2026-10-31T16:00Z`，按上海读 = `2026-11-01`，**就是本月 1 号** |
| 2026-11 视图 35 格 | `11-01 … 12-05`，**本月 30 天全在** |
| 2020–2030 共 **132 个月**逐个比对「网格里本月格数 vs 该月天数」 | **132/132 全对，0 个出错月份** |
| 翻月 `monthOffset = ±1` 共 264 次 | **全部正确** |

**结论：`buildMonthCalendar()` 的分格是对的。`dowOf(firstAt)` 与 `dowOf(firstUtc)` 在
`Asia/Shanghai` 下恒等**（两者相差 8 小时，都落在同一个上海日），所以那句「看起来可疑」的代码
其实是**同一个日期的两种写法**，不是两个日期。

### 1.1 我为什么会错（**流程缺陷，比代码缺陷更值得记**）

我第一版写进报告的两条「证据」都是**自造的复算**，不是跑本仓代码：

1. 我把算式在 `node -e` 里**手抄了一遍**，抄的时候把上海日归日写成了「宿主时区/as 北京+8」的

## 2. 真正的缺口：**不是分格算错，是分格「没有第二双眼睛」**

132/132 全对不等于这块代码不会错，只等于**在 `Asia/Shanghai` 且 `Date.parse` 行为不变的前提下**不会错。
两处真实脆弱点（F 级，且都不需要新依赖）：

| 编号 | 结论 | 证据 |
| --- | --- | --- |
| **F-1** | `firstAt - 8 * 3600 * 1000` 是**硬编码 +08:00**，`dayKey`/`partsOf`/`dowOf` 三处用的却是 `Intl` + `ZONE`。**同一文件里两套时区口径**：一旦 `Asia/Shanghai` 有历史夏令时（1986–1991 实行过），硬编码与 `Intl` 就会分叉 —— 短时段不会，**但 `dateTable()` 可以传任意 `now`**，月历也能通过 `monthOffset` 翻到 1986 年及以前 | `time.js:300`（`- 8 * 3600 * 1000`）vs `:279`/`:290`（`timeZone: ZONE`） |
| **F-2** | 单测**只钉了 2026-10 一个月**（`planning-calendar.test.mjs:66-79`），且其中一条把「10-31 是周六 → 不用向后补」写成断言 —— 那是**巧合**；`:67` 的「格数 % 7 === 0」永真（35/42 都满足） | 11 条全绿（实跑 `node --test`），但遍历 2020–2030 的断言一条都没有 |

> **判定**：F-2 建议补一条**性质断言**（对 2020–2030 逐月：网格必须含本月 1 号与最后一天、
> 首格必须是周日、末格必须是周六）。成本约 12 行，**不需要任何依赖** —— 这是本轮最该先做的事。
> F-1 建议把 `firstAt` 与 `firstUtc` 的分工写成一行注释（「前者是上海 0 点的 UTC 时刻，后者只是
> `Date.UTC` 的构造中间值，**两者都不是『上个月』**」），避免下一个人（包括 r69 的我）再误读。

## 5. 本轮结论（可复核的 5 条）

1. **最高优先：撤回一条自己写错的结论，并修方法论**。`buildMonthCalendar()` 的分格在
   2020–2030 共 **132 个月 + 264 次翻月** 中**全部正确**（`dowOf(firstAt)` 与 `dowOf(firstUtc)`
   在 `Asia/Shanghai` 下恒等）。我上一版之所以报出「11 月只显示 1 天」，是因为**手抄算式复算**
   而不是**调用本仓函数实跑**，且中间踩了 Node 22.13 的 `Intl` 选项报错与 `weekday` 被静默忽略
   两次坑 —— 详见 §1.1。→ 建议写进 skill 的「失败处理」：**缺陷报告必须 import 实跑，不准复算**。
2. **F-1 是真脆弱点，但不是「算错」**：`time.js:300` 用**硬编码 `- 8 * 3600 * 1000`**，
   同一文件 `dayKey`/`partsOf`/`dowOf` 用 `Intl` + `ZONE`。今天是恒等的，**历史上不是**
   （`Asia/Shanghai` 1986–1991 有夏令时），而 `dateTable()` 接受任意 `now`。→ 一行注释 + 一处
   `Intl` 化即可，**不需要依赖**。
