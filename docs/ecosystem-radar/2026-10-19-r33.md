## 4. 本轮结论（三条，按价值排序）

**① B 组「信息侧」轴可以宣布封板：10 次搜索只换来 1 条无许可的 Python 仓库。**
把本轮与在册的 B 组记录合起来看，浙大生态在 GitHub 上其实只有**四类**东西：
课程资料库（内容版权、多数无证）、教务/课堂爬虫（本仓 `omni` 已覆盖）、校园生活脚本（多为 GPL）、
以及**个位数 ★ 的个人小工具**。**「再扫一遍」不会出现新东西**。

> **建议（供人工决策）**：B 组从「每 3 天必跑」降为**事件驱动**（新出现的 zdbk/xzzd 接口变更、
> 或某个浙大项目突然涨星时再跑）。省下的额度给 A 组——A 组至今仍是唯一稳定出 🟢 的组
> （第三十二轮的 `dsh-evolve-modes` 即出自 A 组）。

**② 本仓真正的空洞不在「取数」，在「读数」。**
本轮最反直觉的发现：`zdbk.gpaSummary` / `grades` / `xxt.notices` / `xxt.deadlines` 这些能力**写好了、没接界面**。
「今天」页只读课表，「个人」页只有外观开关。**这是本仓内部的问题，不是生态的问题**——
雷达能给的建议只有一句：**这条空洞不该用「引入外部项目」来填**，因为填补它需要的是本仓自己的页面代码，
而外部项目在这个位置普遍**无证或非 JS**（见本轮 `zju-bulletin-board` / `zju-library` / `mentor-agent` 三条）。

**③ 本轮主动放弃 L2 骨架——这是判断，不是遗漏。**
在收尾前，我补扫了一条「读后整理层」的正交轴（`keyword extraction rake` total 150、
`textrank sentence ranking` total 15），并**动手实测**了其中唯一合格的 JS 候选 `waseem18/node-rake`
（MIT ✅、★103、`app.js` 入口、**零运行时依赖**、unpacked 仅 **12,459 B**、可锁 `1.0.1`）。
判据面上它是「重复且可强化」：本仓 `packages/dsh-zhiyun-page-study/src/layered-search.js` **L10** 白纸黑字写着
> `⑥ 匹配是**字面**子串（大小写不敏感、不切词、不算相关度），不是向量检索；`

但**实测把它否掉了**，两条硬伤当场复现：

| 缺陷 | 复现 | 影响 |
| --- | --- | --- |
| 中文直接崩溃 | `rake.generate('梯度下降是一种优化算法。…')` → `TypeError: Cannot read properties of null (reading 'forEach')` at `index.js:75` | 根因：`removeStopWords` 用 `\b(?:…)\b` 切停用词，`\b` 对 CJK **没有词边界**；且 `stopWords.txt` **一个中文词都没有** → 中文整句不被切分，`phrase.match(...)` 返回 `null`。**本仓的主力语料恰恰是中文字幕**，即核心场景 100% 不可用 |
| 评分公式索引笔误 | `index.js:63` `Object.values(wordFreq).forEach((freq) => { wordDegree[freq] += … })`——拿**频率值**当**键** | 打分函数 `degree/freq` 里 degree 被污染；本地打补丁对比后排序确实变化（`"Gradient descent optimizes"` 从并列升为第 3）。上游 2018-03 起未发新版，**上游自己没修** |
> 结论：`node-rake` 的算法骨架对，但**对中文不可用、对英文也不可信**。
> 按「强化式集成」三条判据，③（底层多调了**更优质**实现）不成立 → **⛔「重复且无增益」**，不建骨架。
> 更关键的是：**若要做这件事，正确做法是 30 行中文友好的候选短语切分（标点/虚词/`Intl.Segmenter`），
> 不是锁一个 2018 年停更、中文会崩的库。** 硬凑一个骨架只会给评审制造假工作量。
>
> 本轮因此**没有 `packages/dsh-radar-*` 增量**，也就不构成「实质产出」，**不开 PR 的判定依据见 §6**。
