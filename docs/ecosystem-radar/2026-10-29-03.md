### 3.1 它有的、本仓没有的（两个纯函数）

**① `parseWeeks(text)` —— 周次表达式解析**

上游原实现（`core/schedule.js:17-46`）要点，已实测确认：

```js
const parity = /单/.test(source) ? 1 : /双/.test(source) ? 0 : null;
const normalized = source
  .replace(/[－—–~～至]/g, "-")        // 中文破折号/波浪号/「至」
  .replace(/[，、；;]/g, ",")          // 全角逗号、顿号
  .replace(/第|周/g, " ");
// → 区间展开（min/max 容错倒序），过滤 (0, 60] 整数，最后按 parity 筛单双
```

**这正是本仓缺的那一块**：

- `packages/dsh-zhiyun-source-xxt/src/parse.js:372` —— `weeks: lesson.weeks ?? null`，
  **平台原样透传，形态未定**（可能是 `"1-8,10-16"`，也可能是数组）；
- `packages/dsh-zhiyun-source-zdbk/src/parse.js:297` —— `@property {'all'|'odd'|'even'} weeks`，
  **只有单双周语义，没有「第几周到第几周」**；
- `packages/radar/dsh-radar-ics-rrule/src/index.js` —— README 自述「本仓课表条目**没有周次**」。

→ 三个源三种形态，**中间缺一层归一化**。上游这 30 行就是干这个的，且**中文标点鲁棒性已被
真实数据打磨过**（破折号 `—` `–` `－`、`～`、`至`、顿号 `、`）。

**② `inferWeekOneMonday(blocks)` —— 第 1 周周一反推**

```js
const candidate = addDays(block.firstDate, -((firstWeek - 1) * 7 + block.weekday - 1));
// 对每个 block 投一票，取票数最高者，返回 { date, confidence, candidates }
```

本仓 `ics-rrule` 的 P1 约束是「组不连续就必须退回逐条」，但**连「哪天是第 1 周」都还没有**。
这一函数用**投票 + 置信度**解决：多个 course block 各自反推，多数一致才采信 ——
**不猜，猜不准就返回 LOW confidence 让上层退回逐日展开**。这与本仓「默认从严」的原则同构。

### 3.3 强化式集成三条判据核验

| 判据 | 是否成立 | 依据 |
| --- | --- | --- |
| ① **仍是同一个面板** | ✅ | 不新增面板。`parseWeeks()` 只被 `ics-export` 的 `buildCalendar()` 内部调用，用户看到的还是「导出日历」那一个按钮 |
| ② **功能仍相似正交** | ✅ | 仍是「课表 → .ics」，只是**同一门课从 16 条独立事件变成 1 条带 `RRULE`**。不改双向同步、不加订阅源 |
| ③ **底层多调了更优质实现** | ✅（**部分成立，须写明**） | 「`1-8,10-16周(单)` → `[1..8,10,12,14,16]`」这件事本仓**完全没有实现**（三源三形态，无归一化）。上游实现**已被中文真实数据打磨**，比自写更稳。**但**它**不含** RRULE 生成 —— 那部分仍须本仓 `ics-rrule` 的锁版 `rrule@2.8.1`，上游不解决 |

**结论：🟢 可集成，但范围严格限定为「两个纯函数」，不引入其 `exporters.js`。**

> ⚠ **必须如实标注的边界**：判据③**是部分成立**。
> 上游只解决「周次字符串 → 周次数组」与「第 1 周定位」，
> **RRULE 的 `COUNT` / `BYDAY` / 不连续退回**仍完全依赖本仓 `ics-rrule` 骨架。
> 若把本包理解为「RRULE 的替代品」，那就是误读 —— 二者是**串联**关系：`week-parser` 喂 `ics-rrule`。

### 3.4 建议下一步
