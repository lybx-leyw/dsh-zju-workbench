- `ADSR1042/ZJU_VocabBoost` 在 L2906 —— 一行**合并登记了 8 个仓库**，第 1 列放了 8 个名字，awk 只取到第一个；

**这是最坏的一种失败**：不是报错，而是**报成功**。连续若干轮里，任何依赖此脚本的验收都会「通过」，

| 2 | ✗ error | `DEP_MISSING` | `dsh-radar-zotero-bridge` | **`@local/dsh-zotero@1.0.1` 在 npm 404** —— **此前从未被任何一轮发现** |
| 3–5 | ⚠ warn | `HOST_GENERATION_CLASH` | `evolve-modes` × `kb-rag` / `llm-fallback` / `tool-plus` | peer 区间不相交（与 r80 的 G0.1 团一致，非新增） |
| — | ℹ | `STALE_PIN` | — | 锁版落后 latest **17 条**（与 r80 相同，未复制漂移） |

**第 2 条是新发现，且性质与第 1 条不同**：

- `credit-audit-vendor` 是「**设计了但从未发布**」（README 明写要发内部 scope，没做）；
- `@local/dsh-zotero` 是「**上游只发 GitHub Release tgz、不发 npm**」，而骨架却把它写成了 npm 依赖。

后者的 README 其实**自己写明了**这一点（「上游从未发布到 npm，所以 `npm install` 会直接失败 —— 这是已知且故意保留的缺陷」）。
**所以正确做法不是改依赖，而是让检查认识「tgz 锁版」这一形态**：从 Release 锁 tgz 是完全合法的锁版方式，
它的 URL 可验证、字节可比对，比 npm 版本号更严格。目前脚本把它一律判 error，会**持续制造噪音**，最终让人无视这个检查。

> **本轮不改它** —— 加一条「允许 `file:`/tgz URL 锁版并对其做可达性校验」的规则属于**改判据**，需要评审拍板。
> 我只把结论记在这里：**`zotero-bridge` 的 error 是「判据过窄」还是「真缺陷」，取决于是否承认 tgz 锁版。**
> 这一点必须由人决定，脚本不该单方面替人决定。

## 9 · 本轮方法沉淀

- **「0 个对象」的检查通过，必须当成失败处理**。任何遍历型校验只要返回 `count == 0` 就应报 error 或至少 warn，
  因为「扫错了地方」与「真的没有」在输出上**完全同形**。本轮 `骨架 0 个 → error 0 · 退出码 0` 就是这样骗过了若干轮。
- **重构目录之后，必须回头 grep 所有硬编码该目录的脚本**。阶段 1.5 迁目录只改了 `workspaces`，
  但 `radar-baseline-check.mjs` 里有一个 `path.join(root, 'packages')` —— 一行硬编码，让整套检查失效。
  **迁目录的正确收尾动作是 `grep -rn "packages/" scripts/`**。
- **判据过窄会产生和判据失效同等的伤害**：一个把合法形态判成 error 的检查，最终会被人直接忽略。
  `@local/dsh-zotero` 的 tgz 锁版是否合法，应显式写进判据，而不是让脚本默认判死。
- **去重只能按全文 substring**（§3.1）。`registry.md` 的簇登记把 8–11 个仓库塞进一行，列解析必漏。
