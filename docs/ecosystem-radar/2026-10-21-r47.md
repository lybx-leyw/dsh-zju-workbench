## 三、评估

### 3.1 为什么是 🟡 而不是 🟢

| 维度 | 判定 |
| --- | --- |
| 许可证 | **MIT**，仓库根 `LICENSE` 1060 B，GitHub `spdx_id = MIT` ✅ 硬门槛通过 |
| 项目类型 | B 类（非 DSH 插件、**未发布 npm**、无模块边界） |
| 学生场景 | 选课 / 课表 —— 高 |
| **与现有功能** | **重复且可强化** ✅ —— 同类信息（课表地点）本仓已在「今天」页展示，但**缺失校区语义** |
| 活跃度 | ★3，**只有一次 push（2026-09-15）**，此后 36 天无动 → ⚠ |
| 适配成本 | 低（只提取一个纯函数口径），但**必须先有一张楼栋表** |
| 相关性二次过滤 | 通过：明确面向 ZJU zdbk |

**判据③（底层更优）成立**：本仓 `packages/dsh-zhiyun-omni/src/platforms/zdbk/parse.ts` 只把地点原样装进
`location: string | null`；全仓六个校区名只在 `PERIOD_TIMES` 的注释里出现过一次；
`dsh-zhiyun-page-today` 的 `place(entry)` 直接拼 `roomName · teacherName`。**校区归属这一层是 0。**
上游虽然只给了一条别名，但**「地点 → 校区」这个动作本身**是上游有、本仓没有的。

**为什么不是 🟢**：★3 + 单日 push 的项目不足以直接托底；且它的判定口径在
**楼栋名不含校区名**的地点（`东1` / `西2` / `段1` / `蒙民伟楼`）上会**系统性误报** —— 照抄即错。
只可提取「形状」，不可沿用「精度」。

## 七、给人工 review 的重点

1. **最该先问的一句**：`0x000005/better-zdbk` 值不值得为**一条别名映射**（`紫金港 ⊃ 银泉`）引入？
   本仓真正缺的不是这段代码，而是一张**校区 → 楼栋前缀表**。若这张表没人维护，
   骨架做完也只能输出 `unknown`，那它就没有存在价值 —— **建议优先裁决「楼栋表从哪来」，再决定本骨架存废。**
2. **`isHomeCampus` 必须是三态**（`true` / `false` / `null`）。上游的二态口径对
   「楼栋名不含校区名」的地点会**系统性误报**，本包不可照抄。
3. **「本校区」从哪里来**：本仓无用户常住校区字段。骨架里给了三条路，
   **推荐 (c)「不判定本校区，只输出校区 + 相邻课是否跨校区」** —— 无需用户配置。
4. **B 组的轴已经用尽**：`zju zdbk` 之外，本轮 6 个窄词里 3 个为 0。
