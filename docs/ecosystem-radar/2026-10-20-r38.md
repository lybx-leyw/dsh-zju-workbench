## 3. 现场实测：本仓登录链路的真实断点（**本轮最重要的产出**）

### L-1 · `executionToken()` 用正则抠 `<input>`，value 里一个 `>` 就让登录失败

`packages/dsh-zhiyun-classroom/src/auth.js:27`：

```js
function attributes(tag) {
  return Object.fromEntries([...tag.matchAll(/([\w-]+)\s*=\s*(?:"([^"]*)"|'([^']*)')/g)].map(m => [m[1].toLowerCase(), m[2] ?? m[3]]));
}
export function executionToken(html) {
  for (const tag of html.match(/<input\b[^>]*>/gi) ?? []) { const a = attributes(tag); if (a.name === 'execution') return a.value; }
  return null;
}
```

**把这段原样复制进夹具（不改一行）**，对同一批合法 HTML 跑，与 `cheerio@1.2.0`（`./slim`）、
`linkedom@0.18.13` 对照：

| # | 夹具（全部是合法 HTML） | 本仓正则 | `cheerio/slim` | `linkedom` |
| --- | --- | --- | --- | --- |
| 1 | `<input name="execution" value="e1s1"/>` | `"e1s1"` | `"e1s1"` | `"e1s1"` |
| 2 | `<input value="e2s1" type="hidden" name="execution" />` | `"e2s1"` | `"e2s1"` | `"e2s1"` |
| 3 | `<input\n  value="e5s1"\n  name="execution"\n/>` | `"e5s1"` | `"e5s1"` | `"e5s1"` |
| 4 | `<input name="execution" value="a>b">` | **`undefined`** | `"a>b"` | `"a>b"` |
| 5 | `<input name="execution" value="abc&amp;def">` | `"abc&amp;def"` | `"abc&def"` | `"abc&def"` |
| 6 | `<input type="hidden" NAME="execution" value="e3s1">` | `"e3s1"` | `"e3s1"` | **`null`** |

**第 4 行是硬断点**：`executionToken()` 返回 `undefined` → `submitCasForm()` L72 `if (!execution)` 成立
→ 抛 `AUTH_SHAPE: 登录页缺少 execution` → **登录直接失败**。
根因是 `[^>]*` 用 `>` 界定标签边界，而 `>` 在双引号属性值里**是合法字符**（HTML5 允许）。
`attributes()` 的正则同样假设「属性值里没有引号」，两者是同一个假设的两处体现。

**第 5 行是静默错值**：`&amp;` 原样进 `URLSearchParams`，上游收到双重转义。
CAS 的 execution 现为 `e1s1` 形态，所以今天没炸 —— 属「今天不炸、改版就炸」。

**第 6 行是选型依据，不是缺陷**：`linkedom` 的选择器对属性**名**大小写敏感
（`NAME=` 时 `[name=execution]` 匹配不到），cheerio 按 HTML 规范把属性名小写化，能命中。
这一行是本轮**选 cheerio 而非 linkedom 的实证**，而不是偏好。

> ⚠ 第 5 行同时是一条**验收警告**：若将来替换实现，`executionToken()` 的返回值会从
> `"abc&amp;def"` 变成 `"abc&def"`。这**是修正**，但属于返回值变更，必须写进 PR 并补夹具。

### L-2 · 今天页遇到 `meta.complete !== true` 就**什么都不画**（不是新发现，但本轮复现了触发条件）

`page-today/src/agenda.js:16`：`if (!meta || meta.complete !== true) return { kind: "incomplete", … }`；
`client.jsx:85` 对应分支只显示「课表还没有收全 / 重新读取」。这是**正确的保守策略**。

问题在触发条件有多宽。`source.js` 的 `getSchedule()` 走 `result(items)` 默认参数
（`complete = true`），只有 `explicit-empty` 分支显式传 `reason`；也就是说**课表永远不会是 `null`**，
只有 `true`。所以 `incomplete` 分支**目前只能由「meta 缺失」触发**（`scheduleMeta: null`），
而它和「读取失败」是两条不同的路径 —— 今天页对这两条路径的文案是分开的（`scheduleError` vs `incomplete`），
这点是对的。

**因此 L-2 本轮不成立为本包的接入理由**，只作记录：它说明「今天页的上游只有一个不可信点（`complete`）」，
而 `complete` 恒为 `true` 意味着**这条保护目前是空转的**。若将来给课表加分页，它会立刻变成真问题。
→ 写进 §8 的「建议人工处理」，**不**作为骨架依据。

## 6. 本轮结论（四条）

**① B 组「找新插件」确实封板，但「抓取后解析层」这一轴有产出，且起点必须是自己仓库的断点。**
9 次搜索、约 19,000 条命中，**零个新 DSH 插件**；唯一 🟢 是一个**早就存在**的库（cheerio ★30,523，
不是"新发现"），它之所以成为候选，**完全是因为先读到了 `auth.js:27` 那段正则**。
这与第三十七轮（`recordAttempt` 无调用方）、第三十六轮（`layers` 空集静默）是同一个模式：
**本仓的价值洼地在「已有能力的接缝」上，不在「缺一个外部库」上。**

**② 「改用 HTML 解析器」这件事，入口比库重要。**
`cheerio` 包根静态 `import undici`（Node-only，第 11 行，实测），直接影响浏览器构建；
`cheerio/slim` 不带它，体积从 384 KB 降到 **200 KB**。
若不查出口，只看 ★30,523 和 MIT 就接入，**客户端会构建失败**。
→ 建议把「**npm 包的子路径导出面**」写进 A/B 两类候选的第三门：
第三十六轮查的是「包是否存在」，本轮要查「**从哪个入口进**」。

**③ 本轮最有价值的产出仍然是缺陷，不是候选。**
L-1 的 `>` 断点今天没触发（CAS 的 execution 是 `e1s1`），但它一旦触发，
现象是「登录页缺少 execution」—— 看起来像**官网改版**，实际是本仓正则的假设错了。
这类「把上游变化当原因」的失败模式，比任何缺失能力都更难查。

**④ `meta.complete !== true` 这条保护目前是空转的（L-2）。**
`getSchedule()` 恒返回 `complete: true`，所以今天页的 `incomplete` 分支只能由「meta 缺失」触发。
不是 bug，但意味着**这条最保守的保护还没被真正验证过**。建议给课表加分页时同步接入 `meta` 断言。

## 8. 建议人工 review 的重点

1. **先看 L-1，不看骨架**：`auth.js:27` 的 `[^>]*` 遇到 value 含 `>` 就截断，登录会以
   `AUTH_SHAPE: 登录页缺少 execution` 失败。**修法有两种**：① 采纳本骨架（换解析器）；
   ② 只把正则改成 `/<input\b(?:[^>"']|"[^"]*"|'[^']*')*>/gi`（约 1 行，无新依赖）。
   若评估认为「不值得为一个 `>` 引入 200 KB」，**方案②更合理** —— 本骨架的存在意义是**给出选择**，不是强迫。
2. **入口必须先定**：若最终只在宿主进程（服务端）用 cheerio，客户端 bundle 里它就是死代码，
   可以 `devDependencies` 化甚至内联；反之若要进浏览器，`./slim` 是硬要求。
   **这个决定会改变 TODO-5 的验收线**（gzip < 70 KB vs 服务端不设限）。
3. **`nextLocation()` 的 meta refresh 解析（TODO-3）单独评审**：现状对 `content="5; url=/x"`
   （带前导秒数）会拿 `"5; url=/x"` 去 `new URL()` 然后抛错。cheerio 版会**让它成功**，
   这是**行为变更**，不能和 `executionToken` 混一个 PR。
