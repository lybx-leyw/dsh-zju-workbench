## 1. 起点：一个「有函数、有字段、零赋值」的调度面

本轮不从「找插件」开始。起点是 10-19 第三十二轮已经封过板的一句话：

> **复习调度轴确认枯竭**……建议 C 组该子轴封板 3 个月。

那句话当时是对**外面**下的判断（JS 生态没有更好的 SRS 库）。本轮把它掉转方向问一次：
**如果外面真有一个更好的调度器，本仓接得进去吗？**

顺着 `packages/dsh-zhiyun-core-quiz/src/generate.js:1087` 往里读，答案是**接不进去**，而且不是缺一个库的问题：

```text
generate.js:1087  export function computeBacklog({ cards, now })   ← 唯一的「到期积压」计算
generate.js:1096    const at = c.dueAt === null || c.dueAt === undefined ? null : Date.parse(c.dueAt)
generate.js:1099    if (at !== null && !Number.isNaN(at) && at <= at0) due++
```

`cards[].dueAt` 在这行**被读**。于是本轮全仓检索它**在哪被写**：

```text
grep -rn "dueAt *[:=]" packages --include=*.js --include=*.jsx | grep -v "dsh-radar-"
→ packages/dsh-zhiyun-core-quiz/src/generate.js:1096   （只有这一行，而且它是「读」，不是「写」）
```

`isNew` 同样：`computeBacklog` 读它、`fresh++` 后 `continue` —— 全仓没有一处在卡片上**置** `isNew`。
结论先说：**`computeBacklog` 是一个没有任何数据源能喂饱的函数**。它在实现层是对的（注释里对
「到期 ≠ 新卡」的区分、对 `dueAt === null` 的「不猜」处理都很克制），但它上面**没有上游、下面没有调用方**：

```text
grep -rn "computeBacklog" packages --include=*.js --include=*.jsx | grep -v "dsh-radar-"
→ generate.js:1087   （只有定义本身）
```

这与 r62（有单测零调用）、r37（有测试无调用方）是**同一族的第三例**，但形状不同：
那两例是「实现了但没人调」，本例是「算了但没人喂」—— 一个函数的**入参在仓库里不存在**。

## 2. 顺着「谁该写 dueAt」往下读，读到第二处空转

`dueAt` 该由调度器写。本仓的调度面是什么？`store.js:40-56` 写得极清楚：

```text
store.js:46   **AI 判分的结果不得直接当复习调度评分用。**
store.js:48   - `selfRecall`（四档评分或 `null`）—— 用户**真实回忆**时的评分，
store.js:49     它是 `fsrsRating` 的**唯一**来源；
store.js:183      get fsrsRating() { return selfRecall; }
```

这个隔离**做得对**，而且是本轮读到的最讲究的一段代码：`autoVerdict === correct` 时 `fsrsRating` 仍返回 `null`，
因为「AI 说对了」不构成「我记得」。注释甚至引了 Anki 手册「忘了却按 Hard」会静默把间隔拉长的依据。

但把它接下去，链条断在同一个地方：

```text
grep -rn "calculateNextReview|createEmptyCard|ts-fsrs" packages/dsh-zhiyun-core-quiz/src \
        packages/dsh-zhiyun-core-study/src packages/dsh-zhiyun-page-study/src
→ 0 命中
```

**`fsrsRating` 有 getter、有注释、有隔离设计 —— 没有任何消费者。** 而本仓 **已经有两个** FSRS 候选骨架
（`dsh-radar-fsrs-scheduler` 锁 `ts-fsrs@5.4.2`、`dsh-radar-fsrs-browser`）在 `packages/` 下放了 seven 天到十一天，
两者的 README 都写着「增强学习页·习题调度」—— 而它们要增强的那个接口（`fsrsRating` → 调度 → `dueAt`），
**中间那段从来没人写**。

这就是本轮的核心结论，也是判据③（「底层多调了更优质实现」）在本仓当前状态下**不可能成立**的原因：
不是「没有更优的底层」，是**本仓与任何底层之间根本没有插座**。

### 2.1 第二处空转：`reviewQueue` 的读法

`generate.js` 的注释把 `computeBacklog` 用在「复习队列」上。队列来自 `store.js:501`：

```text
store.js:501   get reviewQueue() { return items.filter((q) => q.status === QUIZ_STATUSES.accepted); },
packages/dsh-zhiyun-core-study/src/workbench.js:386   queue: store.reviewQueue.map(pub),
```

`items` 是 `itemFromJson()` 造出来的**带 getter 的对象**（`item.js`/`model.js` 一类，`status` 是 getter）。
而 `pub` 是 `workbench.js` 里的**发布函数**，它的职责是把对象摊成可 JSON 的形状 ——
也就是说：**getter 在 `pub` 这一步就被求值成普通属性了**。
`computeBacklog` 若拿到的是 `pub` 之后的对象，`c.isNew` / `c.dueAt` 读到的是**展开值**；
若拿到的是 `store` 内部对象，读到的是**getter**。两条路的语义**不一样**，而函数签名 `{ cards, now }` 对此**一言不发**。

⚠️ 本轮**没有**把这条写成缺陷。理由：我没能当场构造出「两条路给出不同结果」的可复现输入（`pub` 的实现细节未读完，
`isNew`/`dueAt` 本来就没有写方，无法造出非空差异）。**记为 M-2 · 待验证**，不升格为 F 级发现。

### 2.2 第三处：`masteryLabel` 的口径是对的，但它不许被「升级」

`store.js:270-300` 的 `masteryLabel` 是全仓少见的**拒绝把掌握度做成分数**的地方：

| 条件 | 说法 |
| --- | --- |
| 做过 < 3 题 | 数据不足（做过 N 题，少于 3 题） |
| 最近 3 次都错 | 近 3 次都错（共做过 X 题，错 Y 题） |
| 最近 3 次都对 | 近 3 次都对 |
| 其余 | 有对有错 |

注释写明「不报『掌握度 87%』」「规则与依据是一条注释，不是一个数字」。

这条口径**与本轮搜到的一类候选直接冲突**：外面几乎所有「掌握度/知识追踪」插件都输出一个 0–1 的概率
（BKT 后验、IRT 的 θ、ELO 的 rating）。若把它们「接进来增强掌握度」，就必然要把这段「可解释规则」换成「模型推断的分数」——
**那是降级，不是强化**。所以本轮对这类候选一律不给 🟢，理由写成「与本仓 mastery 口径相悖」，而不是「重复」。

### 4.1 为什么不出骨架（且这不是「偷懒」）

1. **前三轮的两个骨架已经有同一个病**：`dsh-radar-fsrs-scheduler`（10-14）与 `dsh-radar-fsrs-browser`（10-17）

   只是把**同一处空转**复制成第三份。
2. **`DSH-better-sidebar` 的接入面是「宿主 + 客户端注入」**：它需要 `dsh.client.inject` 三个 `@deepseek-ai/dsh-client-*`
   与 `react@18`，而本仓的 `dsh-zhiyun-shell-workbench` / `shell-ui` 已自建侧栏。接它 = **两条侧栏并存或替换其一**，
   这是「同一个面板」判据（强化式集成第一条）**过不去**的方向 —— 要么它替换本仓侧栏（大改），要么它只是多一条侧栏（重复）。
   → 本轮**不判 🟢** 更严谨的做法是降为 🟡「需移植改造」，但我**没有证据支持降级**（没读它的 patch 与导出面）。
   **折中**：保留 🟢 但**明确标注「接入形态未定，不出骨架，待人工裁决侧栏归属」**，并在 registry 备注写明。

## 7. 本轮结论（可复核的 5 条）

1. **「外面没有更好的 SRS 库」这个封板理由，本轮被换成了另一个更硬的理由**：不是外面没有，是**本仓没有插座**（F-1/F-2）。
   在这两处修好之前，**任何** SRS/闪卡/掌握度插件接进来都是空转 —— 包括本仓自己的两个 FSRS 骨架。
2. **A 组新面孔率 6.8%（7/103），第六次量化「枯竭」**。今天 A 组已跑四次，本轮新增的 **10 行里有 6 行是 ★0 或空仓库**。
   建议：**A 组「主词扫描」封板 3 个月**，改为只跟 `topic:dsh-plugin` 的 `updated` 增量（本轮该查法前 20 条里 18 条在册）。
3. **`dsh-flashcard` 的 ⛔ 从「一条理由」变成「三条」**：npm 404（不可锁版）+ SM-2（旧一代）+ 卡模型与 `QUIZ_TYPES` 不互通。
   这类「形态完全对口、但每条门都不过」的候选，值得在 registry 里单独有个**「形态对口但不可接」**的标签，避免下一轮重读。
4. **`masteryLabel` 是本仓的一条口径红线**：它拒绝输出分数。任何「掌握度概率」类插件**在判定表里应直接落 ⛔**，

5. **本轮不出骨架是刻意的**，且我把它写成了一个待裁决项（§4.1 第 2 条）：`DSH-better-sidebar` 与本仓 `shell-workbench` 的侧栏
   **只能二选一**，那是架构决策。雷达能给的最多是「它存在、它 MIT、它活跃、它被 flashcard 硬依赖」。
