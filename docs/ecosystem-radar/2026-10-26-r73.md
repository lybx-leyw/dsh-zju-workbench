## 1. 本轮结论

题库练习链现在是**「能组卷、能判分、能落记录，但记录与题目都读不回，且知识点一换版就断」**。

| # | 断链 | 位置 | 性质 | 证据 |
| --- | --- | --- | --- | --- |
| **F-1** | 题库里**任何**一道题都读不回 store（`loaded: 0`） | `model.js:531` `itemToJson` 的 `type: item.type.code` | **真缺陷**（静默） | 实跑 §2.1 |
| **F-2** | `type` 在库里有**两种形状**（代号 / 对象），`bank-answer` 与前端按代号比对 → 简答题被当填空题判、题型筛选全空 | `points.js:189` 与 `question-bank.js:52` 两条来源并存 | **真缺陷**（读码确证） | 读码 §3.1 |

### 2.2 F-3 / F-4 · 知识点 id 随 `revision` 漂移（实跑）

```text
$ node t9.mjs
③ 同一份讲义 id：解析后(sourceVersion) → c1:s1:v28:0:0
   同一份讲义 id：再解析一次         → c1:s1:v29:0:0 | 与第一个相同 = false
   同一份讲义 id：终审完成后         → c1:s1:9f3c-uuid:0:0 | 与前两个相同 = false
④ 拿新版「甲概念」id 去筛旧题 → [] （期望 ["o0"]）
   拿新版「甲概念」id 做全量 mixed 练习（不按知识点筛）→ 2 道可用
⑤ 只改章节名 → [ 'c1:s1:v28:0:0', 'c1:s1:v28:1:0' ] | 与原名相同 = true
⑥ 前面插入一个新主题 → [ 'c1:s1:v28:0:0', 'c1:s1:v28:0:1', 'c1:s1:v28:0:2' ] | 甲概念仍为第一个 id = true
```

**成因**：`knowledge-points.js:27`

```js
const out = [], revision = record.lecture?.revision ?? record.sourceVersion ?? record.fetchedAt;
// id = `${courseId}:${subId}:${revision}:${ci}:${ti}`
```

`revision` 的三条来源：

| 阶段 | `lecture` | 实际 `revision` | 是否变 |
| --- | --- | --- | --- |
| 解析完、出讲义前（`workbench.js:350`） | `null` | `sourceVersion` | — |
| 讲义组装完成（`workbench.js:356`） | `{..., revision: randomUUID()}` | **随机 UUID** | **每次都变** |
| 终审完成（`workbench.js:363`） | `{..., revision: randomUUID()}` | **又一个随机 UUID** | **每次都变** |

→ 同一份讲义，一次成稿过程里 id 就要变 **2 次**。而题的 `pointId` 在出题那一刻写死
（`points.js:190`）→ **重出一次讲义，该节全部旧题的 `pointId` 指向不存在的知识点**。

**好的部分（不吝承认）**：id **不含章节名**，章节改名、前面插主题都不影响（⑤⑥ 皆 `true`）。
坏只在 `revision` 本身。

### 2.3 修法校准 · 为什么不能直接换成 `sourceVersion`

本轮第一版建议「把 `revision` 换成 `sourceVersion`」。**实测发现也不够**：

```text
$ node t15.mjs   # 复刻 workbench.js:66 的 finalVersion 输入
仅重出讲义（semanticPlan 不变）：sourceVersion 是否变 → true   ← 应为 false
重新解析出更多知识点：sourceVersion 是否变 → true
```

`finalVersion = digest([sourceId, pages, sentences, unassignedSentences, blocks, spine, outline, tree, semanticPlan])`
—— **`semanticPlan` 在里面**，而 `semanticPlan` 正是「知识点怎么切」的依据。
所以「只重出讲义不重新解析」时 `sourceVersion` 是否变，取决于是否有解析侧写入覆盖它；
**本轮未能确证这一点**（需在真实工作流里跑一次「仅重出讲义」才能判）。

→ **保守建议**：知识点 id 应采用**语义身份**——`digest([courseId, subId, chapterTitle或topicTitle, blockIndexes])`
（或至少 `[courseId, subId, blockIndexes]`），**与任何 revision 脱钩**。
这正好是 §4 里 `ohash` 的做法；但**不需要引入它**，`concepts.js` 已有 `contentHash` 可复用。

### 2.4 F-4 的真因不是参数解构

第一版判「`planPractice` 被平铺传参」（`question-bank.js:191`）。**实测否定**：

```js
// question-bank.js:191  payload 是对象 { mode, count, pointIds, strategies, types }
const chosen=planPractice(bank.questions,payload);   // ← 第二参是对象，解构正常
```

`bank-answer` 一节同样用的是对象 payload。**F-4 的唯一原因是 §2.2 的 id 漂移**：
前端把 `state.points`（**当前**解析结果）的 id 传下去，库里旧题带的是**出题那次**的 id。

### 3.1 F-2 · `type` 两种形状并存

| 来源 | 写入的 `type` | 行 |

→ 若某题的 `type` 是对象：**简答题走填空题精确比对**（永远判错），且**跳过自评校验**。

> **判据边界（不夸大）**：这两条 `===` 的**实际后果取决于库里到底存的是哪种形状**。
> 本轮**未能确证**真实库里 `type` 的对象形态存在率达到多少 —— 只能说**两种形状都能进库**，
> 且**没有任何一处规范化**。列入 P1 而非 P0。

- 「出题链」有测 ✅
