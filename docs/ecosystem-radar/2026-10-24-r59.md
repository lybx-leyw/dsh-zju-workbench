#### ⚠ 为什么是「能力提取」而不是「锁版挂载」

这是本轮最要紧的一个判断，**推翻了我开工时的预设**：

- 上游是 **Obsidian 插件**：`main.ts` 直接 `import { App, TFile, Plugin } from "obsidian"`，
  `images.ts` 第 1 行就是 `import { App, TFile } from "obsidian"`。
  **`obsidian` 是宿主运行时注入的虚拟模块**，不在 npm 上、无法作为依赖安装 → 锁版挂载（A 类做法）
  在这里**物理上不成立**。
- 但**核心三层恰好是纯函数、零宿主依赖**，且**互相引用的只有一处循环**：
  `md-to-ubb.ts → links.ts → convert.ts`（`splitMarkdownCode`），`convert.ts` 不反向依赖前两者。
  实测：把两个相对 import 改成带扩展名即可在 `node --experimental-strip-types` 下直接跑通（M2）。
- 所以正确形态是：**从上游提取这三个纯函数模块的全部逻辑，移植进本仓的一个新包**
  （B 类骨架已按此形状给出；**骨架内不含任何上游代码**，只有 TODO）。

MIT 白名单 ✅，移植可行（`ATTRIBUTION.md` 已有「含实现移植」一节的先例：ZJU-Omni）。
