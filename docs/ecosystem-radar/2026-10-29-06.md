## 6 · 主产出之二：轮换器的「假 B」

### 6.1 现象

```text
$ node scripts/radar-rotation.mjs        # 06:05 运行
今天        : 2026-10-29（年积日 302，公式取组 = C）
状态        : last_group=C last_run_at=2026-10-29 00:15
本轮该跑    : B   （依据：same-day(unused)）
今天已跑过  : C
```

看起来完全正确 —— **但 03 时段（r96）明明跑过**（提交 `d302743`，`2026-10-29 03:03:30`）。
按脚本逻辑，03 那轮应执行 `--commit C --at "2026-10-29 03:0x"`，把 `last_run_at` 推到 03:0x；
实际仍是 `00:15` → **03 那轮的写回没有落地**。

### 6.2 两层缺陷叠加

| # | 缺陷 | 后果 |
| --- | --- | --- |
| 1 | **写回靠人工收尾步骤**，漏了就无人发现（r93 §6 已提过，未修） | `last_run_at` 停在 00:15 |
| 2 | 脚本在 **CST 06:05** 读日期，若内部仍用 UTC 取「今天」（r87 已提过要修），会把「今天」算成 10-28 | 两条缺陷**互相抵消**，输出恰好「看起来对」 |

**这是「两个 bug 相互抵消」的典型**：三种修法都给出 B ——
- 只修写回 → `last_run_at`=03:0x（今天）→「今天已跑过 C」→ B ✅；
- 只修时区 → `last_run_at`=00:15，但当天比较正确 →「今天已跑过 C」→ B ✅；
- 两个都不修 → 也给出 B。

**结果相同、依据完全不同。所以不能靠「这次结果对」判断脚本是对的** ——
它现在是**因为两个错误恰好抵消**才给对答案，而不是因为在读对的状态。 本轮**未改脚本**：
它属工具行为，不在 `radar` 分支的雷达包边界内，且修法需人工拍板（改签名 or 加 `--today` 默认值）。
**建议下一轮先加一条断言**：`last_run_at` 的日期若 ≠ 最新一份报告的日期，直接报错退出。

> **对 skill 的一处偏离，如实记下**：本轮按脚本建议取 **B**，但 B 组老词面 r93 已判见底，
> 故改用 B 组的**开发者向词面**（工程语义）。这既不是纯 B（词面扩充），
> 也不是换组跑 A/C（那会掩盖轮换器的问题）。**组名记 B，词面记「开发者向」。**

   真正的问题是**类型大小写不归一** —— 一个「读代码能猜到、跑一遍就知道猜错」的典型。
   **教训：凡是要写进 README 的「上游缺陷」，必须在沙箱里用真实输入跑一次再落笔。**
2. **★ 数与可集成性无关，甚至负相关**。本轮 ★ 前五（646 / 542 / 446 / 368 / 341）**全部 ⛔ 或排除**：
   它们强，是因为它们是**一整套发版流水线**；本仓没有流水线，接进来就是「重复且无增益」。
   真正可用的那个是 ★2。
3. **「找到一个可用的」不等于「找到一个值得的」**。骨架给出了三条判据，但判据③在 ★2 的上游上
   只能靠「改正它的一处错误」成立 —— 那就必须在 README 里**明写「若你认为该自写，本骨架作废」**，
   否则会留下一个「为锁版而锁版」的包。
