## 4. 本轮最重要的一条结论：**中文数词解析，JS 生态整体不可靠**

同轮把「能跑的都跑一遍」——三家不同实现、三个不同错法：

| 输入 | 真值 | `Achuan-2` | `spa5k` |
| --- | --- | --- | --- |
| 一亿二千万 | 120000000 | ✓ | **1000020000000** ✗ |
| 一千二百万 | 12000000 | **1002000000** ✗ | ✓ |
| 十二亿三千四百万 | 1234000000 | **4204000000** ✗ | — |

这不是「某一家写错了」，而是**「亿 / 万 / 万级内部千」的三层嵌套**在「顺序栈 + 贪心乘」
这种写法下必然出错。沙箱里另写一版**显式单位节点 + 按层级合并**的原型（有理数 `Fraction`），

```
一亿二千万 120000000 / 一千二百万 12000000 / 十二亿三千四百万 1234000000
九亿九千九百九十九万九千九百九十九 999999999 / 三万零五百 30500 / 一百零五万 1050000
```

全部正确。**结论**：这个轴该「换底层」（任意精度小数）+「自写薄解析」，**不该整库引入**。

## 6. 建议人工 review 的重点

1. **中文数词自写实现**的覆盖面：`廿/卅`、`两`、`〇`、大写 `壹貳叁`、`一亿零五万` 这类带「零」的省略读法。
2. **`attempt` 是否要区分「等价命中」与「字面命中」** —— 建议区分，否则错题归因看不出「拼写差异」和「真不会」。
3. **`decimal.js` 284KB 的落点** —— 判定发生在宿主侧、非浏览器首屏；需确认打包位置。
4. **是否接受「`unknown` 兜底」**：任何一侧解析失败都进人工，**不**退化为 `incorrect`。
