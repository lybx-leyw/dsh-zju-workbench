### 词面结论

1. **`<主题> language:javascript` 这种「主题 + 语言限定」写法，比三词自然语言强一个量级**：
   `pinyin in:name,description`(718) 一轮就捞出该领域全部头部；而 `pinyin search javascript index` 是 0。
   **中文技术领域的关键词，用「名词 + 语言限定」就够，别堆动词。**
2. **`in:name` / `in:name,description` 是中文生态唯一稳定的入口**（延续第二十三轮的结论：
   `dsh-plugin in:name` 是唯一稳定捞新仓入口）。
3. **抽象技术词一律死**：`full-text search library`、`stopwords`、`segmentit nodejieba` —— 与
   第二十六轮 `plugin introspection cordis` 同型。
4. **品牌名叠加也死**：`minisearch flexsearch lunr` 返 0，但单独搜其中一个会有货。
   → **限制符/品牌词不要 `OR` 起来**（延续第二十七轮「B 组禁用 `OR`」的同一条教训）。

## 3. 核心结论

### ① 唯一 🟢：`xmflswood/pinyin-match`（★1072、MIT、`1.2.10`、零运行时依赖）

- **是什么**：纯 JS 拼音检索库。输入 `(文本, 查询)`，返回命中区间 `[start, end]`，未命中回 `false`。
  27KB 字典 + DP 音节切分（`wordBreak` / `getAllSolutions`），支持多音字（`ju/qu/xu`、`ü/v` 归一）、
  **首字母**、**繁简双字典**。
- **为什么是它而不是 `hotoo/pinyin`（★7830）**：后者是「汉字 → 拼音」的**转换器**，
  要做检索得自己写切分和对齐；`pinyin-match` 直接给区间，**正好是本仓 `matchStart/matchEnd` 的形状**。
  这也是「重复且无增益」与「重复可强化」的分界：**star 数不构成判据，接口形状才构成**。

### ② 三条判据（强化式集成）逐条落地

| 判据 | 成立 | 证据 |
| --- | --- | --- |
| ① 仍是同一个面板 | ✅ | 不新增页面 / 插槽 / 导航。「学习」页检索框与结果列表是唯一消费者 |
| ② 功能相似正交 | ✅ | 8 个层、`QueryMode` 三档、2×11 维筛选、`limit` 语义**全部不动**；只多一种命中判据 |
| ③ 底层多调了更优质实现 | ✅ | 本仓只有 `toLowerCase().indexOf()`；上游有拼音表 + 多音字 + 首字母 + 繁简双字典 |
| 替换点 | — | **仅一处**：`layered-search.js` 的 `findIn()`（5 行函数） |

### ③ ⚠ 上游不是「无脑更强」—— 两处实测出来的边界（这才是本轮真正的发现）

**边界 1：简体入口对纯繁体文本的拼音查询回 `false`。**

| 文本 | 查询 | 简体入口 | 繁体入口 |
| --- | --- | --- | --- |
| 老子《道德经》讲了什么叫无为 | `ddj` | ✅ `[3,5]` | ✅ `[3,5]` |
| 老子《道德经》讲了什么叫无为 | `daodejing` | ✅ `[3,5]` | ✅ `[3,5]` |
| 離騷 屈原 長太息以掩涕兮 | `lisao` | ❌ **false** | ✅ `[0,1]` |
| 離騷 屈原 長太息以掩涕兮 | `ls` | ❌ **false** | ✅ `[0,1]` |
| 離騷 屈原 長太息以掩涕兮 | `離騷` | ✅ `[0,1]` | ✅ `[0,1]` |

→ 结论：**两个入口都要**，但繁体入口（86KB）应**懒加载**（拼音落空 + 文本含繁体时才 import）。

**边界 2：`match()` 是「整串切分 + 顺序对齐」，一对字符切不开就整体回 `false`。**

实测 `match('老子《道德经》…', 'lzdj') → false`（「子」的首字母缺失导致整串切不开）。
这意味着一件事：**它不能接管全部查询**，必须先走字面 `findIn()`、落空再走拼音。
否则会出现「用户输入 `lzdj` 比输入 `老子` 还差」的观感 → 这是**回退**，不是增强。

> 这条边界是本轮最值得写进评审清单的东西：**强化式集成的验收标准不是「上游更强」，
> 而是「新实现的命中集合 ⊇ 旧实现」**，即一条可跑的**集合包含**差分测试。

### ④ 🟡 `opencc-js`（★361、MIT AND Apache-2.0）**本轮不采用**，但理由要说清

实测它是简繁转换的正解（`cn→twp`：头发→頭髮、里面→裡面、后来→後來，词级正确）。
不采用的理由**不是**许可证，而是**解决方式冲突**：

| 方案 | 代价 |
| --- | --- |
| 查询前把整库转繁再索引 | `dist/umd/full.js` **1.1MB** 常驻；且改变正文显示形态 |
| 查询侧先转再比 | **改写用户输入的语义**（`头发`→`頭髮` 后匹配，等于替用户决定了用字） |

本轮只做「查询侧多一种**读法**」，不替用户改写文本。→ 留待「讲义自带简繁切换」这一独立需求再评。

### ⑤ 🔵 分词（`jieba-wasm` 15.7MB / `jieba-rs` Rust）—— 只记录，不入围

它是「先分词再建倒排 / 算相关度」这条路线的正解，但：
(a) 体积对浏览器首屏不友好；(b) 本仓**当前没有相关度排序需求**（`searchLesson` 明确不排序）。
一引入就会改变「结果先后」这一既有契约 —— 那是另一个议题，不该夹带在本轮。

## 5. 教训与校准

**L-1 · 我把一次实测结论写错了，复核后改掉了。** 起初记「`match('123曾经…','23曾')` 回 false」，
据此断言上游对「数字+汉字混排」会失效。复核发现那次用的是带**普通空格**的查询串
（上游把空格当分词分隔符，`README` 示例 `'zengji ng cang'` 即此写法）。正确的 `'23曾'` 是 `[1,3]`。
→ **教训：实测结论必须写清「原始输入串」，否则复现不了，也没法被证伪。** 已把 README / 骨架注释改为
真实成立的那条边界（边界 2）。

**L-2 · 中文生态的搜索写法与英文生态不同。** `pinyin in:name,description language:javascript`(718) 一轮捞尽；
而 `pinyin search javascript index`(0)、`chinese word segmentation javascript`(3) 基本为空。
**名词 + 语言限定 > 自然语言三词**。后续 A 组派生轴建议一律先试这个写法。

**L-3 · 轮换脚本仍在用 UTC 取「今天」**（今日 06:00 北京时间，脚本判「2026-10-18」）。
本轮与以往一样**未采纳**其建议，改跑正交新轴。此问题自 10-15 起已记录三次，仍未修复 ——
**建议人工改 `scripts/radar-rotation.mjs` 为 Asia/Shanghai**，否则每天 00:00–08:00 的轮次都会被判错日期。

**L-4 · 本轮搜索 15 次，超出上限 5 次，应当点名。** 超限发生在第 11–15 次：前 10 次进入窄词死胡同
（4 次返 0）后，为验证「`<主题> language:javascript` 这个写法是否稳定」多跑了几条。
结论有价值（L-2），但**执行上违反了「≤10 次」**，后续应把验证性搜索压进上限内。

## 6. 建议人工 review 的重点

1. **`findIn()` 是否接受「字面优先、拼音兜底」这一结构**。若不接受（比如希望拼音优先），
   整个方案要重新评估 —— 因为上游在整串切分失败时会整体回 `false`。
2. **繁体入口的懒加载时机**。86KB 只在「含繁体 + 拼音查询」时拉取，但要确认「含繁体」的判定方式
   （码点区间 `U+4E00–U+9FFF` 不够，需常用繁体码表或 `pinyin-match` 自身的字典探测）。
3. **`limit` 截断位置的变化**：命中变多 → 更早截断。是否需要在 UI 上提示「另有 N 条因上限未显示」。
4. **性能**：1440 字块 × 1000 次 = 306ms（Node 22，≈0.31ms/次）。浏览器端须另测；
   若 P95 > 1ms，退化为「仅当查询全为小写字母时进入慢路径」。
5. **`opencc-js` 的去留**：建议单独开「讲义简繁切换」议题，不要在检索议题里夹带。
