## 4. 实质产出：依赖图对行的开关不透明（`LIVENESS_ERODES`）

### 4.1 问题

`packages/dsh-zhiyun-page-plugins/src/runtime.js` 的 `readPlane()` 只从**活着的** Loader 条目
与 fiber 里读「谁提供哪个服务」。这是对的 —— 它读的是运行时真相。但它有两个下游假定没被审视：

1. **「活着的包」=「应该出现在图里的包」**。用户关掉一个包，它的 Entry 还在
   `listBundles()` 里（那一行还在，随时能打开），但它的 fiber 不在了 → 它从 `host.rows` 消失；
2. **「活着的提供者」=「唯一应该算作提供者的」**。它提供的服务随之从 `providers` 消失。

于是 `buildView` 里那一段：

```js
for (const service of row.requires ?? EMPTY) {
  const provider = serviceProviders.get(service);
  if (provider !== undefined && provider !== row.name) addEdge(row.name, provider);
}
```

对一个**只通过服务**依赖 provider 的包来说，provider 一关，`provider === undefined`，
这条边就不存在了。而这一页的整张图只有三个出口：叶 / 可取消 / 文案
—— 三个出口全部**把「边少了一条」读成「没人需要它」**。

### 4.2 复现（`scripts/radar-provider-liveness.mjs`，本轮新增）

用本仓真实包名的教科书形状：`core-parser` 提供 `zhiyunParser`，`core-study` 需要它，
`page-today` 需要 `core-study` 提供的 `zhiyunStudyController`。三包都活着时：

```text
$ node scripts/radar-provider-liveness.mjs
基线边集（全部活着）：core-study -> core-parser | page-today -> core-study

关掉 core-parser：
  消失的边：core-study -> core-parser
  它自己：leaf=true cancellable=false
  因此新获得「可取消」的包：page-today

关掉 core-study：
  消失的边：core-study -> core-parser | page-today -> core-study
  它自己：leaf=true cancellable=false
  因此新获得「可取消」的包：core-parser、page-today

关掉 page-today：
  消失的边：page-today -> core-study
  它自己：leaf=true cancellable=false
  因此新获得「可取消」的包：core-study

✗ 判定不通过：LIVENESS_ERODES（4 条边因关包而消失）      exit=1
```

**最刺眼的是第二段**：关掉 `core-study` 之后，`core-parser` 从「被 1 个包依赖」变成
**叶 + 可取消**。而此时 `core-parser` 仍在运行、仍在提供 `zhiyunParser`
—— 它恰恰是**最不该被关掉**的那个（关掉它，`core-study` 下次一打开就会 pending）。

页面这一侧还会照着 `Panel.jsx:38` 那行文案写：
**「不依赖本工作台的任何其他包」**。

> 这与 r79 F-1 是**同一族、不同层**：r79 的是「上游提供者被 `inScope` 静默丢弃」，
> 本轮的是「**下游消费者**被读数的『只读活的』静默丢弃」。两条一起说明了同一件事：
> **这张图的两端都可以在没有任何报错的情况下消失。**

### 4.3 这个判定证明了什么、没证明什么

| 已证明 | 未证明 |
| --- | --- |
| 读数变薄时，`buildView` 会让边消失（纯函数级，输入可控） | **真机上**用户点「取消」之后，页面是否真的重新读到这份变薄的读数（见 §4.4 第 3 条） |
| 边消失会让**别的**包新获得 `cancellable`（→ 「取消掉不该取消的包」的通路存在） | 有多少个真实包**只**通过服务（而非 `inject` 模块名）依赖别的包 —— 沙箱里没有真机 profile |
| 归因是干净的（一次只关一个包，不连坐） | 修复方案（§4.4）的取舍 —— 这是产品决策，雷达不改 |

**为什么不直接改 `runtime.js`**：三个候选修法各有代价（见 §4.4），而这一页的叶/可取消判定
直接连着「能不能取消」，属于 r78 记过的「权责问题」。雷达只出证据与选项，改动交评审。

### 4.4 三个候选修法（交评审）

| # | 修法 | 代价 | 风险 |
| --- | --- | --- | --- |
| A | `readPlane` 额外读**已关条目**的 `inject` 声明（`listed` 与 `alive` 分开） | 要一条新数据源；`reflect.store` 里已无该包的服务实现，只能读配置层 | 配置≠运行时，可能把「声明了但从来没生效」的边也画出来 |
| B | 把「关掉的包」画成**半透明节点**（`ghost: true`），不参与 `providers`，但参与 `dependents` | 只改 `buildView` 的折叠 + 页面渲染 | 「半透明」的语义要写清楚，否则用户以为它还活着 |
| C | 不动图，只在有包被关时给整页加一条横幅：「以下依赖关系可能因 X 已关闭而不完整」 | 最小 | 只治标；`cancellable` 仍然是错的 |

**推荐 C 先上（1 行，立刻止血），B 作为终局。** A 的风险最高，不建议。

### 4.5 顺带发现（不修，只登记）

`Panel.jsx:58` 的 `const [open, setOpen] = useState(false)` 与 `:108` 的
`open={open} onToggle={event => setOpen(event.currentTarget.open)}` 构成一对
**自反馈**：`<details>` 的 `open` 由 state 强制、`onToggle` 又把 state 写回 DOM 的值。
`setOpen` 在 `:108` 之外**全仓零调用**（`grep -rn "setOpen" packages/` → 3 处，全在本文件）。
行为上没有坏（用户点击 → 浏览器先翻转 → `onToggle` 读到新值 → 写回同值），
但它让这行 `<details>` 变成了**受控组件**，以后想用 `defaultOpen`/折叠状态记忆会踩坑。
**只登记，不动** —— 属于交互细节，不是缺陷。

## 6. 校准与方法论

### M-1 · 「生态侧名词」的词池正在见底，且见底的方式与功能词不同

功能词（`timetable ics export`）见底的方式是**搜不到**；生态侧名词（`dsh plugin manager`）
见底的方式是**搜到的全是同一层的东西且六成在册**。前者要换词，后者要**封这一层**。
