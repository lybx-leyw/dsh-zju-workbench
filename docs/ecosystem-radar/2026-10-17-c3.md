### 2.3 ★ 本轮最高价值发现：既有「复习队列」是**只读投影**，本仓**没有任何调度写入方**

这是本轮**唯一实质产品结论**，也是**推翻**本轮既有骨架前置假设的关键。全部为**代码级证据**。

#### 证据链（四条，互相独立、逐条可复核）

**① 本仓确实持有一个名为 `reviewQueue` 的「复习队列」，但它只是过滤器，不是调度器。**

```js
// packages/dsh-zhiyun-quiz/src/store.js:501
get reviewQueue() { return items.filter((q) => q.status === QUIZ_STATUSES.accepted); },
```

它按 `status === 'accepted'` **过滤**，**没有任何时间、间隔或优先级维度** ——
即：**采纳顺序 = 复习顺序**，永远。

**② 消费侧把它投影给界面时，**显式丢弃了 `fsrsRating`，也不输出任何 `dueAt`**。**

```js
// packages/dsh-zhiyun-study-core/src/workbench.js:314-321

  return {
    pending: store.pending.map(pub),
    queue: store.reviewQueue.map(pub),   // ← 队列直接映射，无排序、无 dueAt 字段

```

**③ `selfRecall` / `fsrsRating` 的**输入侧**在 `quizView` 里**根本没有暴露**。**

- `store.js:183` 定义了 `get fsrsRating() { return selfRecall; }`，且文档明确它是
  「**能喂给复习调度的评分**」，隔离良好（`selfRecall === null` 时恒为 `null`，不回落到 `autoVerdict`）；
- 但 `quizView` 的 `pub()` **不含 `selfRecall`、不含 `fsrsRating`、不含 `dueAt`、不含 `attempts`**
  → **界面拿不到评分，也就无法把它交给任何调度器**。

**④ `dueAt` / `isNew` 在全仓**只有**一处出现，且在一个**孤立的、无人导出的**函数里。**

#### 结论

> **本仓的「到期 / 新卡」判定（`computeBacklog`）与「可调度评分」（`fsrsRating`）都已建好，
> 但没有一行代码负责把「作答」变成「下次什么时候该复习」。**
> 也就是说：**调度能力（写入方）是完整缺口，`dueAt` 从未被赋值** ——
> 「复习队列」当前等价于「采纳顺序列表」。

#### 顺带确认（对本仓有利的一条）

`dsh-zhiyun-quiz/src/store.js:38-54` 的「**FSRS 隔离**」做得**比常规实现更严格**：

- `selfRecall`（用户真实回忆的四档评分）与 `autoVerdict`（AI 判对/判错）**是两个分开的字段**；
- `fsrsRating` **只**来自 `selfRecall`，`autoVerdict === correct` 时它**仍是 `null`**；
- 注释引用 Anki 手册给出了理由：*FSRS 几乎能适应任何习惯，唯独不能容忍「忘了却按 Hard 而不按 Again」*，
  一旦如此**所有间隔都会严重偏长，且是静默地坏**；
- 并且**这个约束是签名级的**，不是约定 —— 调用方在未自评时**拿不到可用的评分值**。

> ✅ 这意味着**接入 FSRS 不需要先补数据合规层** —— 隔离已经做好，`fsrsRating` 可直接作为调度输入。
> 这是本轮的一个**正面结论**，也是**降低骨架落地成本**的依据。

> - 更重要的是：**它们与既有骨架锁版的是同一组织（`open-spaced-repetition`）**，
>   因此走**方案②（分层）在依赖治理上其实是「一个组织、两个包」，而非跨组织拼接**。
>
> **建议人工裁决时，把方案②的优先级上调** —— 它既拿到 WASM Optimizer，又不丢 `ts-fsrs` 的稳定纯算法路径，
> 且依赖来源单一。**相应地，`fsrs-browser`（方案①）的独特价值被削弱**：
> 它多提供的是「浏览器内直接跑」，而本仓宿主是 Electron，**Node 侧原生绑定（`binding`）可能比 WASM 更合适**。
> ⚠ 这两者的取舍**须实测**（本仓未做实测，仅据包元数据判断）。

## 3. 本轮结论

### 3.1 本轮最大收获是**一个产品缺口**，而不是一个新候选

C 组第十轮（B 组首轮 + A 组治理轴）带回了 28 行登记，但本轮**有效候选只有 10 条**。
然而本轮的价值不在候选数量，而在**第一次把「复习调度」这条轴落到了本仓代码上**，并发现：

> **本仓的调度写入方是完整缺口 —— `dueAt` 从未被赋值，`computeBacklog` 无调用方，
> `fsrsRating` 无消费方。第九轮骨架的「接缝已经在那儿」假设不成立。**

这条结论**同时**验证了：
1. 第九轮把 `fsrs-browser` 判为 🟢 **是对的** —— 缺口比原论证更大（从无到有，而非手动换自动）；
2. 但第九轮骨架的 **①「不改交互」措辞是错的** —— 必须新增「到期 / 积压」显示；
3. 而且**新增这个显示是本仓既有纪律**（`generate.js:1076-1083` 已论证 review debt 必须显式呈现）。

### 3.2 「复习调度」轴**尚未枯竭**，但**已收窄到单点**

| 子方向 | 状态 |
| --- | --- |
| 优化器（Optimizer） | **已封板** —— 4 条簇成员全部判完（1 🟡 溯源 / 1 ⛔ 语言不符 / 1 ⛔ 无增益 / 1 ⛔ 无许可证），**无需再扫** |
| 调度器（Scheduler） | **已由 `fsrs-browser` + `ts-fsrs` 覆盖**，无新候选 |
| ⭐ **增量阅读（Incremental Reading）** | **唯一有新语义的方向** —— 见 §3.3 |

> **结论：`fsrs optimizer` 与 `spaced repetition scheduler wasm` 两词建议从关键词池移除**（前者已封板，后者返 0）。

### 3.3 ⭐ 新发现的方向：**增量阅读** —— 本仓「笔记 → 出题 → 复习」三段是手动串联的

`incremental reading browser extension`（`total_count = 1`）是**本轮唯一命中新语义**的词，
指向 `nanhualyq/ir-ext`（**无许可证 ⛔，不采用、不摘取代码**）。

**但它揭示的范式缺口值得单列**：

> **增量阅读** = 读长文时，把可提取的片段**就地**做成卡片，并与**阅读进度一同调度**
> （SuperMemo / Readwise 的核心机制）。

对照本仓现状：

| 环节 | 本仓现状 |
| --- | --- |
| 读（`dsh-zhiyun-page-study` 讲义阅读） | ✅ 有 |
| 记（`dsh-zhiyun-notes` 笔记 + 划词） | ✅ 有 |
| 出题（`dsh-zhiyun-quiz` 生成 + 质检 + 采纳） | ✅ 有 |
| **串联（读的过程中就地成卡，无需切换上下文）** | ❌ **缺** |

**即：三段能力都在，但三段之间是「手动串联」的** —— 用户必须读完、切到笔记、再切到出题面板。
**增量阅读正是这条「串联」本身**，且它天然需要调度（决定「哪一段该回头重读」）。

> 📌 **建议**：把 `incremental reading` / `readwise alternative` / `cloze extraction`
> 列为**下一轮 C 组的独立轴**。本轮只此一词命中、且唯一命中的仓库无许可证，
> **不足以出骨架**，但足以确立「该方向存在、且本仓缺的正是串联而非任一段」。
