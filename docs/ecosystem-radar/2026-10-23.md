## 2. 候选与分级

### 2.1 🟢 直接集成 · `adamgibbons/ics`

| 项 | 值 |
| --- | --- |
| 仓库 | [`adamgibbons/ics`](https://github.com/adamgibbons/ics) |
| npm | `ics@3.12.1`（2026-10-01） |
| 许可证 | **ISC** ✅（GitHub + npm 两处一致） |
| Stars | ★787，push 2026-10-01 |
| 类型 | **B · 其他 JS 项目**（纯生成器库） |
| 与现有功能 | **重复且可强化** → 强化式集成 |
| 体积 | 72 KB 源 + **bundle 实测 75 KB**（大头是 yup） |

**强化三判据逐条对账**

| 判据 | 是否成立 | 依据 |
| --- | --- | --- |
| ① 仍是同一个面板 | ✅ | 只在「规划」页页头加一个导出动作，不新增导航项；课表数据仍来自「今天」页那份 `projectAgenda` |
| ② 功能相似正交 | ✅ | 现有答「接下来做什么」（站内）；新增答「怎么在**自己的日历**里看到」（离开工作台）。同数据、同域、不同问题 |
| ③ 底层多调了更优质实现 | ✅ | 本仓**零** iCalendar 实现；RFC 5545 的折行（75 octet）、`,` `;` `\` 转义、`DTSTAMP`、`VALARM` 全由上游处理 |

**实测 10 条（沙箱实跑，全部写在骨架 README 的 M1–M10 表里）**

最关键的三条 —— 都是**不报错、但结果是错的**那一类：

1. **R1 默认随机 UID**：不传 `uid` 时每条事件 UID 随机（`aXPsYcWAV4xBuUE_N_2JP`）。
   而本仓课表条目**没有稳定 id**（`projectAgenda` 输出的是逐日平铺对象）。
   → 用户每导出一次，日历里就**多出一整套重复事件**，且删不掉。
   传 `uid` 后两次生成逐字相同 → 必须由 `(学期, courseTitle, startMs)` **确定性派生**。
2. **R2 无 VTIMEZONE**：`timezone: 'Asia/Shanghai'` 直接报 `unspecified keys`。
   只有「浮动时间」与「UTC」两条路：浮动 → 跨时区导入错；UTC → 时刻对、显示不好看。
   **建议 UTC**，理由见骨架 README 的「需要人工拍板」第 2 条。
3. **R3 毫秒必须显式按上海拆**：把 `Date(ms).getUTC*()` 当本地时间传，
   产出 `DTSTART` **早 8 小时且不报错** —— 这是最容易漏、最难肉眼发现的一种 bug。

**唯一的成本争议**：75 KB，其中大头是 yup 校验库（仅用来拒绝未知字段）。
若产品认为「为生成一段文本引入校验库」不划算，应改判 🔵 并改手写 RFC 5545 子集；
本报告保留 🟢 的依据是：手写要自己保证折行与转义，出错**同样不报错、同样难发现**。

## 4. 读码结论与方法论（非候选，但比候选重要）

### 图 A · C 组三条支线的状态

```
课表/日历   ── 数据齐(projectAgenda) ── 出口缺(iCalendar 零实现) ── 本轮补 → 🟢 ics
论文批注    ── 阅读器有(page-paper)   ── 导出/批注带走的出口: 未见明确需求 → 按兵不动
刷题        ── FSRS + 掌握度 已有    ── 生态里 ★≤4 全是小站 → 重复无增益
OCR         ── ocr-web 骨架在途      ── 本轮扫到的都是「AI 全家桶」→ 无底层可换
```

### 图 B · 「锻炼」轴第三次零结果

`fitness tracker language:typescript` → `total_count: 0`（前两轮同词亦为 0）。
→ **建议把「锻炼」移出 C 组默认词池**，改为「仅在用户明确要求时扫」。
理由：Web 端锻炼追踪类 JS 项目无法接触 Google Fit / HealthKit（r35 已登记
`rn-fitness-tracker` 为「原生桥，Web 用不上」），该轴在 Web 工作台里**结构性无解**，
不是「今天没扫到」。

### 结论 1 · C 组第四次复现同一形状

r37（关键路径）、r49（掌握度）、r50（锚点校验）、本轮（iCalendar）——
四次都是「**能力/数据已在，出口没有**」。

> **本仓的缺口主体是「接线」，不是「依赖」。**
> 但这不等于不需要依赖：本轮缺的 iCalendar 是**真需要外部实现**的
> （RFC 5545 的折行/转义不该手写）。**判别线**是：
> 「缺的是一行调用」→ 补接线；「缺的是一套规范实现」→ 才接依赖。
> 这条判别线建议写进 README 的「强化式集成」小节，防止下一轮把接线问题当依赖问题。

### 结论 2 · 本轮候选的失败模式是「不报错的错」

M2（UID 随机）、M5（浮动时间）、M7（时区拆错）三条**全部不抛异常**，
产出的文件语法完全合法，只是内容错了。
→ 建议：**凡接入「序列化 / 格式化」类上游，验收标准必须含「同一输入两次输出逐字相同」**
与「时区往返守恒」两条断言，否则这类 bug 永远测不出来。
本骨架已把这两条写进 `buildCalendar()` 的 TODO-1 与 `stableUid()`。
