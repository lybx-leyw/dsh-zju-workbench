## 1. 本轮结论

**「勾掉」这个动作在本仓有实现、有持久化、有页面，唯独没有「归属」—— 于是它会在多实例并存时静默丢失。**

今天没有先去找「哪个插件能加功能」，而是查了一个**本仓自己的、被昨天 r77 拖出来的**问题：
r77 结论是「错题重练缺的不是算法，是数据」；顺着「数据为什么会在」这条线往下，问到了
`ticks.json`（规划页的勾选表）—— 一份**被宿主进程独占写、页面却只增不减地读**的小文件。
实测（§3）结论：

| 问题 | 现象 | 后果 |
| --- | --- | --- |
| P-1 写覆盖 | 两个 `TickStore` 实例（重启后的旧窗口 / 两个窗口）各持一份内存快照，`save()` **整份覆盖** | **A 勾掉的那条作业被 B 的落盘抹掉**，重启后消失 |
| P-2 判真口径 | 今天页用 `Boolean(ticks[key])` 判「勾没勾」 | 记录值一旦是 `false`/`0`/空串（旧数据、手改），**交掉的作业重新出现在「今天到期」** |
| P-3 `prune` 契约 | `prune()` 有实现、有测试，**全仓零调用方** | 勾选表只增不减；r77 记的「文件慢慢积累残影」至今成立 |

一句话：**这不是「缺一个插件」，是「本仓的一处所有权缺失」。外部没有任何插件能修它 —— 它连自己的数据长什么样都不知道。**

### 2.1 为什么 `gating-hub` 是 🟡 而不是 🟢

它是**同一块面板**（插件页）且**功能正交**（它管「装/升/回滚」，不管「装什么」），
底层确实多了一层本仓没有的东西 —— 升级前**契约预检**、**回滚点**、失败**自动回滚**、
**有证据才自动禁用**。三条「强化式集成」全部成立，故不是 ⛔。

但降级到 🟡 的理由是**适配成本不在于代码，在于权责**：

| 项 | 实测 | 影响 |
| --- | --- | --- |
| 依赖 | `dependencies: []`（零运行时依赖） | ✅ 干净，锁版挂载成本低 |
| 形态 | 自带 `dsh.bundle.patch` + `cordis.patch.yml`，**是完整插件而非库** | 不能像 `ts-fsrs` 那样当底层调用；只能**整包挂载**再在外围加壳 |
| 侵入点 | 它要**接管 profile 的写入与升级**（回滚点 = 改 profile 前的快照） | 本仓的插件页**也**在写 profile（装/卸/排序）。两者同时挂 = 两套写入者，正是 §3 P-1 那类问题的放大版 |

## 3. 本仓实测校准（本轮真正的增量）

> 全部在沙箱用 **Node v22.13.1 直接 `import` 本仓源码**实跑，无 mock、无网络。

### P-1 · 两个实例并存 → 先勾的那条**被后落盘的整份覆盖**

`ticks.js` 的 `save()` 原本写的是 `JSON.stringify({ ticks: this.ticks })` ——
`this.ticks` 是**构造时读进内存的快照**，此后只随本实例的 `setDone` 变。

```js
const a = new TickStore(file, now, 'inst-A');
const b = new TickStore(file, now, 'inst-B');   // B 在 A 勾之前启动，持有空快照
a.setDone('xzzd', '48213', true);               // A 勾掉「软工项目报告」
b.setDone('pta', '1042', true);                 // B 勾掉另一条
```

修复前实测：

```
A 勾后磁盘: {"xzzd:48213":{"doneAt":1000000000}}
B 勾后磁盘: {"pta:1042":{...}}                  ← A 的那条没了
A 的 xzzd:48213 还在? false
重启 A 后 all()= {"pta:1042":{"doneAt":null,"owner":null}}   ← 自己的勾彻底消失
```

这条路径**不是假想**：`index.js:1446` 每次 `apply` 都 `new TickStore(...)`，
而本仓的「设置 → 重启实例」会让**新旧进程并存一小段时间**；今天页（`page-today`）
也在读同一份快照。用户看到的是「我勾了，怎么又活了」—— 与 P-2 的症状**一模一样，成因完全不同**。

**已修**（`packages/dsh-zhiyun-page-planning/src/ticks.js`）：

1. 每条记录加 `owner`（进程级 UUID，`PROCESS_OWNER`，同进程内多次构造保持一致）；
2. `save()` 改为**增量合并**：磁盘上「不是本实例」的记录**原样保留**，本实例只覆盖自己名下的键；
3. `load()` 把归不到自己的记录放进 `foreign`（只读，不显示为「我勾的」），新增
   `statusFor()` → `'mine' | 'elsewhere' | 'none'`、`isDoneElsewhere()`、`absorbForeign()`；
4. **旧格式兼容**：没有 `owner` 的记录按「自己的」收下，升级不丢勾选。

修复后实测：

```
A 的勾还在? true
B 的勾在? true
A 视角 pta:1042 status = none（尚未 absorb）
重启 A status xzzd = mine | pta = elsewhere
```

> 设计取舍（写在这里免得被当成疏漏）：`all()` **仍含**别人勾的那几条（值 `{ doneAt: null, owner: null }`），
> 这样页面可以把它们也置灰 —— 否则用户会看到「明明勾过，怎么又活了」。为此今天页的判真**必须**改成「键在即勾」，见 P-2。

### P-2 · 「今天到期」按**值的真值**判勾，脏值让交掉的作业复活

`packages/dsh-zhiyun-page-today/src/due.js` 原写法：

```js
const ticked = source !== 'local' && Boolean(ticks?.[`${source}:${id}`]);
```

`ticks` 存的是**记录对象**，正常情况恒为真 —— 所以平时看不出来。一旦值是 `false`
（早期某版写过布尔、或用户手改过 `ticks.json`），判真翻成 `false`，**一条已勾掉的作业重新出现在「今天到期」**。实测：

```
修复前: 条目数 = 1  ["编译原理实验三"]
修复后: 条目数 = 0  []
```

**已修**：抽 `isTicked()`，只看 `hasOwnProperty`（键在即勾），并限定来源为 `xzzd` / `pta`
（本机规划的完成态是 `row.done`，不走这张表；未知来源一律不认，避免未来某个 `source` 撞键被判成已做）。

### P-3 · `prune()` 零调用方（本轮**只记录、未修**）

`grep -rn "\.prune(" packages/` → 0 命中。`ticks.js` 自己的注释写着「`prune` 由调用方在拿到最新列表后调用」，
而 `index.js` 的 `loadTodos` 里**没有**这段（`tests/planning-ticks.test.mjs` 里有一个 `pruneAfterLoad`
**复刻**了它，但复刻的是**期望行为**，不是实际代码）。

> 不修的理由：`prune` 的正确触发条件是「xzzd 和 pta **两边都读成功**才清」（测试文件里那条注释写得很清楚：
> 一次网络抖动就清掉一学期的标记）。这需要动 `index.js` 的取数流程，**要连带处理 `absorbForeign` 的时序**，
> 不适合在雷达轮次里顺手改。列入 §6 建议。
