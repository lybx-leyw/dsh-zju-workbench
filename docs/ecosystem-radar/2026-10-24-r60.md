## 3. 评估与判定

### 3.1 为什么 `react-activity-calendar` 是 🟢，而且必须是**同一个面板里的一层底色**

**判据③「底层多调了更优质实现」—— 本轮结论是「不成立」，必须写明。**

本仓**没有任何**热力图 / 活动日历渲染（§1.2 第 ① 条，`grep` 0 命中）。
所以这不是「已有的东西换更好的底层」，而是**无 → 有**：

| 强化式集成三判据 | 本轮 |
| --- | --- |
| ① 仍是同一个面板 | ✅ **成立** —— 不新增页面。「个人」页（`zhiyun.me.content`）只多一块，学习页不动 |
| ② 功能仍相似正交 | ✅ 成立 —— 与「个人」页现有的偏好设置 / 学习空间正交（它展示的是"你做过什么"，不是"你要改什么"） |
| ③ 底层多调了更优质实现 | ❌ **不成立** —— 本仓**没有**被替换的底层 |

判 🟢 的理由与 `cytoscape.js`（10-18，`dsh-radar-note-graph`）、`temml`（10-16）**完全同型**：
> 接进来就有东西看，且**不新建任何东西**（不新增页面、不新增存储、不新增开关）。

**但「定性是全新还是强化」必须由人工拍**。本包 README 顶部写的是
「**全新（补缺视图）· 非强化式集成**」——不写成强化，避免把「0→1」说成「1→1.2」。

### 3.2 为什么「连击（streak）」**不集成、应当自写**

搜索 #3（`streak calculation language:typescript`）17 条里 **★ 最高 1**，
且每一条都是**完整 App**（自带 SQLite / Cloudflare D1 / Expo 存储），
没有一条导出可复用的纯函数。而本仓需要的连击算法只有 15 行：

```js
// 语义：从「今天」往回数，连续有活动的天数；今天没活动时从「昨天」起数（宽限 1 天）
function streak(days /* Set<'YYYY-MM-DD'> */, today) { … }
```

**判 🔵→⛔ 的理由不是「它不好」，而是「为 15 行引入一个 App 的存储层」违反了
判据③的实质**（多调的不是更优质实现，是多调了一整套与本仓冲突的数据模型）。
这是本轮**第二条「数据在、出口没」但正确答案是自写而非集成**的判断 —— 与 r45 的
「缺口是真的、包接不进来，应按自写而非集成处理」同结论。

### 3.3 骨架的**唯一真成本**（写在出数之前，不是之后）

`react-activity-calendar@3.2.1` 的 `dependencies` 是 `date-fns@^4.2.1` + `@floating-ui/react@^0.27.19`。
本仓 `scripts/build.mjs` 的客户端构建是 **`bundle: true` + `external: [...HOST_SEEDS, ...declared]`**，
且 `tests/build-seeds.test.mjs` 有一条断言：**产出里出现任何 `node_modules` 文件即失败**（「零依赖进包」）。

于是本包挂上去会遇到三种情形之一：

| 情形 | 做法 | 代价 |
| --- | --- | --- |
| A | 照常打包（三个包全 bundle 进 `lib/client.js`） | 包体增大；**且**那两条测试要按「允许的白名单」放宽 —— 这是本仓**第一次**给客户端包开这个口子，须人工裁决 |
| B | 把 `date-fns` / `@floating-ui/react` 加进 `dsh.client.external` | 运行时必须有宿主侧模块表兜底，**否则 `Could not resolve`**（build.mjs 顶部注释已记录过这个失效方式） |
| C | 不用 tooltip（`tooltips.css` 是可选的独立导出） | 可以吃掉 `@floating-ui/react`，但 `date-fns` 仍在（日历格的时间运算） |

> **骨架不选边**。`src/upstream.js` 把「打包策略」写成 **TODO-B-1 阻塞项**：
> 出数（真机挂载）之前不得升「已采纳」。这条与 r55（`citation-js` 的打包验证写成 TODO-A-1）
> 是同一纪律：**体积/打包成本未验证的候选，只能停在 proposed。**

→ **C 组以后优先搜「跨功能的元数据/可视化层」，而不是再枚举功能名。**

**M2 · 产品词 vs 代码词的第七次证据（去程）。**
`contribution heatmap` → 6 条（5 条 ★0）；`activity heatmap` → 13 条（★961 / ★599）。
差别只在 `contribution` 这个词 —— 它是 **GitHub 产品语汇**。
→ 反推出 r57 结论的另一半：**成熟生态里，越"产品化"的词越窄**。

**M3 · 热力图底座的事实标准只有一个。**
10 条相关命中里，`shadcn-heatmap`（★39）与 `ai-heatmap`（★3，**Power by `ccusage` + `react-activity-calendar`**）
**都在用或复刻同一个 API 形状**；★961 的 Obsidian 插件不可嵌入、npm 404。
→ 与 r57「这条轴是空的，接 1 个即够」同型：**该轴已收敛，封板 3 个月**。

**M4 · 「连击」是 App 属性，不是库属性。**
`streak` 相关的 17 条命中**全部**带存储层、★ 全 ≤1 —— 说明**没有人把它抽成库**，
因为它只有十几行、却和"哪天算一天"的业务定义死死绑在一起（宽限期、时区、
一天内多次是否只算一次）。→ **该类能力应自写并测；搜 GitHub 找不到、也不该找到。**

**M5 · 本仓的「零 node_modules 进包」断言，是雷达选型的真实过滤器。**
`react-activity-calendar` 有 2 个传递依赖，这在 npm 世界算"轻"，却直接撞上本仓
`build.mjs` 的断言（§3.3）。→ **今后 B 类选型第一筛就该问「依赖数」，
而不是等到出骨架时才发现**；代价是可能错过一批"轻但不零"的优质库，
所以这一步的正确做法是**开一个显式的白名单决策**，而非默认拒绝（§6）。

**M6 · 「有数据、没出口」第四次同型。**
r53（课表 → ics）/ r54（`endMs` → 剩余整块时间）/ r59（笔记 → UBB）/ 本轮（attempts + updatedAt → 日历）。
四次全部是：**数据已落盘、目标出口已存在、中间缺一个纯转换/渲染**。
→ 这已经不是巧合，建议把它写成**一条固定的扫描起点**：
> 开跑前先 `grep` 「落盘字段」与「界面消费点」，**差集就是本轮的搜索方向**。
（本轮 12 次搜索里有 6 次是功能词复扫、收益 0；4 次是这条路线带来的。）

## 5. 流程自查

### 5.1 检索超限（⚠）

12 次 > 10 次上限。多出的 2 次是 **P1/P2 定向探针**（npm registry 两次 + GitHub repo 两次，合并计 2 次）。
理由：`react-activity-calendar` 若不能在 npm 上锁版（`3.2.1` 是否存在、`exports` 与 `peerDependencies` 形态），

这一步无法省。**如实记为超限，不辩解。**

### 5.2 未做的事（须在人工 review 时知道）

- **未做**真机挂载 / 打包验证（§3.3 的 A/B/C 三种情形都没实测）→ 骨架停在 `proposed`。

  （若否，情形 C 的成本会进一步降低）。这需要 `npm pack` 下载产物，本轮未做。
- **未核** 「session `updatedAt`」在跨设备/多工作区下是否会重复计入（同一会话在两处打开）。
- **未登记**任何 `NOASSERTION` 新项 —— 本轮 `NOASSERTION` 只有 1 条且已在册（`dsh-usage-stats`）。

### 5.3 轮换脚本

`node scripts/radar-rotation.mjs` 输出 `same-day(unused)` → C，与人工判断一致（**本轮无漂移**）。
