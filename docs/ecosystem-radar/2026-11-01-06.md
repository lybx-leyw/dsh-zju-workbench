**它补了哪一格**

| 问法 | 现有实现 | 上游补的格 |
| --- | --- | --- |
| 笔记里的图片存在哪？ | `dsh-zhiyun-core-notes/src/store.js`：内联 `zy-asset://<id>`，字节落 `note_assets/<id>.<ext>` | —（不动） |
| 图片能贴到 CC98 吗？ | **不能**。`dsh-zhiyun-source-cc98` 只导出十个只读 API，`ubb.js` 只会**解析** `[img]`，不会产出 | 本地图 → `POST https://api.cc98.org/file` → 拿到服务端图片 id，拼成 `[img]…[/img]` |
| 要重登吗？ | 本仓 `token.js` 已有 CC98 OpenID 的 token 生命周期（缓存/刷新/落盘） | —（上游脚本用的是**账号密码**换 token，**本仓必须删掉这条**） |

**上游协议事实（已实核，非猜测）**

```text
TOKEN_URL  = https://openid.cc98.org/connect/token      ← 本仓已有更好的 token 管理，不复用此路
UPLOAD_URL = https://api.cc98.org/file
请求形状   = multipart/form-data，字段名 "files"，data={"contentType":"multipart/form-data"}
返回       = 服务端图片对象（含图片 id，用于拼 [img] 或 Markdown 链接）
重试       = 遇 403 等 1s、**仅重试当前图一次**；任一图失败则**不输出正文**（防「半张贴」）
已上传不可撤回 ⇒ 重跑会重传（必须把这个事实写进 UI 提示，不能静默）
```

**三条「强化式集成」判据逐条核对**

1. **仍是同一个面板** —— 不新增页面/插槽/导航。落点是**笔记页**既有的图片操作
   （`dsh-zhiyun-page-notes`），一个「复制为 CC98 版」的出口，与既有「导出 Markdown」并列。
2. **仍是相似正交的功能** —— 现有：内联图片**在本仓内**渲染；新增：**把同一张图换成远端 URL**。
   两者都作用于「笔记里的图片」，一个是本地面，一个是外发面。
3. **底层多调了更优质实现** —— 本仓**没有任何上传实现**（`grep upload` 在 `source-cc98` 零命中），
   现在调用的是一条已验证的 CC98 官方上传端点（上游实测可用），而不是自造。

**边界（写进骨架，免得实现越界）**

- **不搬上游源码**。上游是 Python + `markdown-it-py`；本仓是 JS。只借**协议事实**（端点/字段/重试语义），
  Markdown 图片定位必须用本仓已有的 `core-notes/src/note.js` 的 `zy-asset://` 扫描（`:281` `extractAssets`）。
- **不引入账号密码登录**。上游的 `getpass` 交互流与本仓「token 缓存 + 刷新」相冲，直接砍掉。
- **不做「自动上传」**。仅为**显式点击**动作；后台静默上传会把笔记里的私图推到公网论坛。
- **失败不降级为「部分替换」**。上游「任一图失败则不输出」的口径保留 —— 半张贴出去的帖子比不贴更糟。
