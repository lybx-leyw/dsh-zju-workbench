### 3.1 为什么 🟢 是「重复可强化」而不是「全新」

强化式集成的三条判据，逐条对照：

| 判据 | 本轮 🟢 的回应 |
| --- | --- |
| **① 仍是同一个面板** | ✅ **是，且不新增任何导航项**。「字幕」页（`contentTabs` 第 5 项）照旧、`video-panel.jsx` 的 `TranscriptLine` 照旧、`zy://section?...&t=` 时间链照旧。新增的只是**同一页里那串文本的分隔与双语呈现** |
| **② 功能仍相似正交** | ✅ 上游做的是「**字幕格式 ↔ cue 结构**」，本仓缺的是「**cue 结构 → 可读句子**」。两者回答同一域的不同问题：上游管**边界在哪**，本仓管**边界之间怎么连**。不重叠 |
| **③ 底层多调了更优质实现** | ✅（**条件性**）本仓**没有任何**字幕解析器：字幕是智云 API 返回的 JSON（`BeginSec/EndSec/Text`），`dsh-zhiyun-classroom` 只做字段映射。`media-captions` 带来的是**标准格式层**（VTT/SRT/SSA cue 树 + `region`/`voice`/`align` 等 cue settings），这是本仓**完全没有**的一层。⚠ 但它**不负责断句** —— 见 §5 结论 ①，别把「接了它」误当成「句子化做完了」 |

> **不能用的理由先摆在这**：上游**不做**中文断句、**不做**标点恢复、**不认** `BeginSec/EndSec` JSON。
> 它增益的是「格式标准化」，不是「可读性」。判据③成立，但强度是「中」，不是「高」。

## 5. 本轮结论（三条，均可复用）

**① 「格式解析」与「句子化」是两件事，上游只解决前者。**
`media-captions` 能把 SRT/VTT 拆成结构化 cue，但它**不会**把 `'我们看这个矩阵'` 和 `'它的秩是三'`
连成一句、也不会补句号。本仓真正的缺口（F-1 的 `join("")`）**没有任何 JS 库能替我们补** ——
它必须靠本仓自己写「按标点 + 停顿阈值 + 语义未完成」的合并规则。**接上游 ≠ 做完断句**，
骨架 README 已把这条写成最重要的「不要误读」警告。

**② 中文标点恢复在 JS 生态里是空的。**
`punctuation restore language:typescript` → **0**；`subtitle segment merge algorithm` → **0**；
`subtitle segmentation input:name` → **0**。三个最贴的词全是 0，说明这不是「没搜到」，
而是**这个位置确实没有 JS 实现**（Python 侧有 `funasr`/`punctuation-restore`，但技术栈不符）。
→ 结论与第三十轮（中文数词解析）同一形态：**中文语义底层连续第三个轴都只能自写薄实现**。

**③ 字幕域的可迁移能力只有三样，且已全部找到。**
12 次搜索后能确认：这个域能提供的就只有 ① **格式解析**（🟢 `media-captions`）
② **反向序列化**（🟡 `subtitle`） ③ **双语轨渲染**（上游 cue settings，本仓 `english` 字段的落点）。
其余「字幕编辑器 / 播放器轨 / SRT CLI」都是重复劳动。→ **字幕域建议封板 3 个月**，
下轮 C 组应转向「**作答统计可视化**」或「**错题变体生成**」（第三十四轮已建议，尚未执行）。
