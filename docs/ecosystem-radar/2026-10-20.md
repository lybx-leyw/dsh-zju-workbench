### 3.1 为什么 🟢 是「重复可强化」而不是「全新」

强化式集成的三条判据，逐条对照：

| 判据 | 本轮 🟢 的回应 |
| --- | --- |
| **① 仍是同一个面板** | ✅ **是，且不新增任何导航项**。「字幕」页（`contentTabs` 第 5 项）照旧、`video-panel.jsx` 的 `TranscriptLine` 照旧、`zy://section?...&t=` 时间链照旧。新增的只是**同一页里那串文本的分隔与双语呈现** |
| **② 功能仍相似正交** | ✅ 上游做的是「**字幕格式 ↔ cue 结构**」，本仓缺的是「**cue 结构 → 可读句子**」。两者回答同一域的不同问题：上游管**边界在哪**，本仓管**边界之间怎么连**。不重叠 |
| **③ 底层多调了更优质实现** | ✅（**条件性**）本仓**没有任何**字幕解析器：字幕是智云 API 返回的 JSON（`BeginSec/EndSec/Text`），`dsh-zhiyun-classroom` 只做字段映射。`media-captions` 带来的是**标准格式层**（VTT/SRT/SSA cue 树 + `region`/`voice`/`align` 等 cue settings），这是本仓**完全没有**的一层。⚠ 但它**不负责断句** —— 见 §5 结论 ①，别把「接了它」误当成「句子化做完了」 |

> **不能用的理由先摆在这**：上游**不做**中文断句、**不做**标点恢复、**不认** `BeginSec/EndSec` JSON。
> 它增益的是「格式标准化」，不是「可读性」。判据③成立，但强度是「中」，不是「高」。

## 5. 本轮结论（三条，均可复用）

**① 「格式解析」与「句子化」是两件事，上游只解决前者。**
`media-captions` 能把 SRT/VTT 拆成结构化 cue，但它**不会**把 `'我们看这个矩阵'` 和 `'它的秩是三'`
连成一句、也不会补句号。本仓真正的缺口（F-1 的 `join("")`）**没有任何 JS 库能替我们补** ——
它必须靠本仓自己写「按标点 + 停顿阈值 + 语义未完成」的合并规则。**接上游 ≠ 做完断句**，
骨架 README 已把这条写成最重要的「不要误读」警告。

**② 中文标点恢复在 JS 生态里是空的。**
`punctuation restore language:typescript` → **0**；`subtitle segment merge algorithm` → **0**；
`subtitle segmentation input:name` → **0**。三个最贴的词全是 0，说明这不是「没搜到」，
而是**这个位置确实没有 JS 实现**（Python 侧有 `funasr`/`punctuation-restore`，但技术栈不符）。
→ 结论与第三十轮（中文数词解析）同一形态：**中文语义底层连续第三个轴都只能自写薄实现**。

**③ 字幕域的可迁移能力只有三样，且已全部找到。**
12 次搜索后能确认：这个域能提供的就只有 ① **格式解析**（🟢 `media-captions`）
② **反向序列化**（🟡 `subtitle`） ③ **双语轨渲染**（上游 cue settings，本仓 `english` 字段的落点）。
其余「字幕编辑器 / 播放器轨 / SRT CLI」都是重复劳动。→ **字幕域建议封板 3 个月**，
下轮 C 组应转向「**作答统计可视化**」或「**错题变体生成**」（第三十四轮已建议，尚未执行）。

## 2. 本轮的关键发现：习题链断了两环（读码实测）

### F-1 · 「作答」没有调用方 —— `attempts` 轨永远为空

```

```

**只有定义处，没有任何调用方。**

而 `store.js` 文件头把三条轨道的分工写得很清楚：

> | attempts | 作答记录 | 错题归因与薄弱点统计的**唯一**依据，是**已经发生过的事** |

也就是说：`makeAttempt` / `makePointAttribution` / `makePointMastery`

但**产不出数据**。`quiz-panel.jsx` 只有「采纳 / 丢弃 / 移出队列」三个动作，**没有「作答」按钮**。

**这条不需要任何外部依赖**，是本仓自己的一行 UI + 一次 `recordAttempt()` 调用的事。
本轮**不为它出骨架**（它不需要上游库，出骨架反而违反「不重复集成」的边界），只在报告里点名。

### F-2 · 出题原料只能来自「已解析的讲义块」

```js

text: (block.sentences ?? []).map((line) => line.text).join(""),
```

`quiz-panel.jsx` 的候选片段只有 `state.result.blocks`。板书照片、手写笔记、课件截图、
老师群里发的题图 —— **完全没有入口**。全仓 `grep -r ocr packages/*/src` → 零命中。

这一环可以靠外部库补，于是有了本轮的 L2 骨架。

> **两环的先后**：F-1 在 F-2 **之前**。没有作答，就永远不会产生 attempts，
> 出题原料再多也没法闭环。**建议人工先做 F-1，再评审 F-2 的骨架。**

### 4.1 为什么 `bent2685/ocr-web` 是 🟢（而 ★ 只有 3）

三条硬理由，逐条可核：

1. **许可证明确且宽松** —— `MIT`，`LICENSE` 实文首行已核（不是只看 API 的 `spdx_id`）。
2. **技术形态是本仓唯一能落地的** —— 纯 JS + `onnxruntime-web`（wasm），**零运行时依赖**，
   浏览器内跑完。同轮其他 OCR 全部要求 Python / 原生二进制（`dsh-ocr-plugin` 是 Python、
   `ScaleDP-TS` 是 AGPL），与本仓「无独立后端」的约束直接冲突。
3. **上游接口对本仓友好** —— `OcrLine` 带 `text` / `points`（四边形）/ `score`，
   `points` 让「按版面聚成段」成为可能；`OcrEngineWorker` 让推理不卡主线程；
   `onProgress` 让「正在下载模型」可以被显示而不是静默卡住。

**但它同时有三条实打实的风险**（写进 README，不掩饰）：★3 且 5 个月未更新（R-5）、
wasm 静态托管在本仓没有现成管线（R-1）、模型默认从 CDN 拉与「离线」定位冲突（R-2）。
**这是「够用且合法」的选择，不是「最好的选择」** —— 评审可以驳回，也可以选择自写。

## 8. 建议人工 review 的重点

1. **F-1 先做，且不需要骨架**（`recordAttempt()` 无调用方）。这是「习题」闭环的**唯一堵点**，
   且改动量是「加一个作答按钮 + 一次调用」。**本轮不出骨架是刻意的** —— 它不需要任何外部库。
2. **`ocr-web` 的 ★3 / 5 个月未更新要不要接**。若评审倾向「不接第三方、自写」，
   则本骨架应整体删除，并把 `onnxruntime-web` + PP-OCRv5 的接入成本单独立项。
3. **wasm 与模型的部署方式**（R-1 / R-2）。这决定本包是「离线可用」还是「首次需联网」，
   也是本仓第一次需要在部署产物里带二进制资源 —— **影响面超出本包**。
4. **「判分」这一环要不要补**（`diff-match-patch` 只是 🔵）。它同样**没有消费者**：
   因为 F-1 没接上。**先做 F-1，再谈判分**，否则又是在空链上加环节。
