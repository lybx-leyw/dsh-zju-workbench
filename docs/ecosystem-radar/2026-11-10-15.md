## §4 本轮唯一骨架：`dsh-radar-hook-order`

```text
packages/radar/dsh-radar-hook-order/
├── package.json        # 锁版 @tengxiaohtx/dsh-plugin-hooks-ordering@0.2.0
├── cordis.patch.yml    # 只控 4 个 hook（不是上游的 13+1）
├── src/index.js        # apply() 直接抛错
├── src/upstream.js     # loadUpstream() 直接抛错 + 全部凭据
├── README.md           # 顶部「未评审·不可用」+ 「今天收益为 0」单列一节
└── OWNERS              # Owner: shared
```

**与上游的两处刻意不同**：

1. **控制面收窄到 4 个**（`tools/pre-execute` / `tools/post-execute` / `fs/write-intent` / `fs/edit-intent`）。
   上游默认控 13 个 waterfall + 1 个 serial。本仓 0 个订阅者却要承担「排序策略压过第三方
   隐式假设」的风险 —— **逐条放行是可回退的扩张，一上来全开不是**。
2. **`serialHooks: []`**。空 serial coordinator 的 front 那个**有短路整条 dispatch 的能力**，本仓无订阅者不开。

**为什么这个骨架值得出，尽管今天收益为零**：`packages/radar/` 里已有多个骨架会订阅 `tools/post-execute`
（`dsh-radar-diff-approval`、通知类、预算闸类）。它们一旦同时落地，**谁先跑没人能声明**。
先把声明面摆好，等第一批订阅者到来时它已经在位。**这是一个「为将来正确性」的骨架，不辩解。**
