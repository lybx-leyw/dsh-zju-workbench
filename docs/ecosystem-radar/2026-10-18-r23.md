### 为什么是这一轴（本轮方法论点）

近五轮 A 组试过：能力域细分 → 外观/主题 → 治理审计 → 导出工作流 → 乐理 → `topic:` 全量视图 → topic 分页。

但生态里同时长出了**另一类仓**——它们不服务于终端用户，而是**服务于「插件集合本身」**：
`dsh-plugin-radar`(★1476)、`dsh-plugin-shop`(★706)、`bruc3van/awesome-dsh-plugin`(★422)、
`whyihaveyou/dsh-suite`(★60)、`PerryLink/dsh-test-drive`(★12)、`PerryLink/dsh-score`(★12)、
`MicroMilo/upstream-radar`(★11)、`wqx11235/dsh-upgrade-guard`(★2)……

这解释了**为什么能力词越搜越空、而这批仓挤在一起**：DSH 插件已过万，
「找插件」和「插件还能不能用」成了比「再造一个插件」更痛的问题。
本条轴对**本仓**尤其重要，因为本仓自己就有「插件」页（`dsh-zhiyun-page-plugins`），
且已在 10-17 出过 `dsh-radar-compat-vet`（静态契约比对）。

**`MicroMilo/upstream-radar`** —— 与 10-17 的 `dsh-radar-compat-vet` **同域但不同层**。

- **是什么**：常驻式「DSH 插件兼容性测试」—— 盯住 DSH 与插件的**精确版本**，
  输入一变就起 Agent：读仓库证据 → 自选 Node / 执行 profile → 在**一次性 CI** 里
  **真装真跑** → 边跑边读日志、处理可恢复的构建门禁 → 产出**带证据的兼容性报告**。
  它的口号很能说明定位：*No “install succeeded, therefore compatible.”*
- **包形态**（已核 npm `upstream-radar@0.45.0`）：
  `dsh.bundle.patch: ./cordis.patch.yml` ✅；patch 为**标准 `insert` 形态**、行 id `upstream-radar`、
  入口 `upstream-radar/dsh`；`inject: ['agents']`；**纯服务端、无 `dsh.client`**（不新增面板）；
  **零运行时依赖**（`dependencies: {}`）；`engines.node >= 22`；Apache-2.0（LICENSE 实文已核）。
- **为什么它是「强化」而不是「重复无增益」**（三条判据同时成立）：

| 判据 | 本候选 |
| --- | --- |
| 仍是同一个面板 | ✅ **「插件」页**，同一张依赖图、同一行，**只加一列**。上游**本身无 client 注入**，不可能另起面板，比 `compat-vet` 更容易守住「不新增导航项」 |
| 功能仍相似正交 | ✅ 同批插件、同一个问题「它对我的工作台意味着什么」。现有答**「现在能不能关掉」**（横），本轮答**「下次启动还能不能被加载」**（纵）。与 `compat-vet` 的区别：后者是**静态契约比对**（读 `dsh.engines.framework` / peer 范围），本条是**动态隔离实跑**（真的装起来跑一遍） |
| 底层多调了更优质实现 | ✅ 本仓与 `compat-vet` **都拿不到「真装真跑」这条证据链**：需要一次性运行器、Node/profile 选择、日志增量读取、可恢复构建门禁、去重与重试。这是**独立的一整类基础设施**，不是「自己写几百行」能替代的 |

- **是否与 `dsh-radar-compat-vet` 重复**（必须回答，否则就是「简单集成重复功能」）：
  **不重复，是同一列的两种取证策略。** 类比：`compat-vet` 是**体检报告**（看指标），
  `upstream-radar` 是**实车碰撞测试**（真撞一次）。二者输出同构
  （「插件 × DSH 版本 × Node 版本 → 可加载 / 不可加载 / 未知」），正好汇入**同一列**。
  但**须先做一件事**：`compat-vet` 骨架尚在 `proposed`、未评审，
  **两条并存会让评审者面对两套同列方案**。建议人工裁决先后（见 §6）。

## 6. 需要人工 review 的重点

1. **⚠ 与本轮骨架正面冲突的「双方案」** —— `dsh-radar-compat-vet`（10-17，静态）与本轮
   `dsh-radar-upstream-radar`（动态）**抢同一列的同一行**。骨架已各自写明差异，
   但**两者只能有一个先进 UI**。建议：**先评审 compat-vet 的「列的形状」**（它更轻、无 Agent 依赖），
   再决定是否把 upstream-radar 作为**该列的第二取证源**（新增 `source: static | isolated-run` 字段）。
   **在此之前不要把任一骨架接入 profile。**

2. **⚠ 运行时成本与依赖面（本轮最大未知项）** —— `upstream-radar` 的 `inject: ['agents']` 意味着
   它会**在宿主里起 Agent 跑一次性环境**。对本仓（学生日常使用、离线课堂环境可能无网）意味着：
   ① 这不是「打开页面就出结果」，而是**异步、耗分钟级、可能失败**——UI 必须显式区分「未测」与「通过」；
   ② 上游自己强调 *completed ≠ passed*，本仓文案**不得**把「分析完成」渲染成「兼容」。
   建议评审时先确认：**离线/无 Agent 配额时是否优雅降级为「未知」**。

3. **`engines.node >= 22` 硬门槛** —— 本仓 `runtime.lock.json` / CI 的 Node 版本需核对；
   若低于 22，锁版安装会直接失败。**这是采用前第一件要验的事。**

4. **`dsh-plugin-gating-hub` 的「只借判据、不借写路径」** —— 若评审同意借其五类契约检查，
   须先补 `ATTRIBUTION.md`；且须明确**禁止**引入其 profile 写入 / 自动回滚 / 自动禁用三条能力
   （与「不另开写入口」「受保护行永不自动禁用」的本仓原则冲突）。

5. **`HiWhaleW/dsh-toolbox` 值得单独一看** —— 它是本轮**唯一**「功能对得上、许可证却说不清」的仓。
   若人工核实为宽松许可，可能比 `upstream-radar` 更轻（多了 plugin preflight）。

## 7. 方法论沉淀（供后续轮次复用）

- **宽词 `deepseek-harness plugin`(9216) / `cordis plugin`(1898) 已彻底失效**：前 10 条被头部大仓占满，
  新仓无法浮出。**建议 A 组宽词退场**，改用「窄词 + 词根」：`plugin compatibility`(66)、`plugin upgrade`(46)、
  `plugin dependency`(155) 这类**两位数到低三位数**的词，信噪比最高。
- **`dsh-plugin in:name`(4013)** 是**唯一稳定能捞到新仓**的入口（本轮 4 条首次登记来自它）。
- **生态进入「元工具期」**：插件过万之后，增长最快的是**测插件、卖插件、给插件评分**的仓，
  而不是新插件。这对本仓的直接含义：**「插件」页的价值可能高于再造一个功能页**。
