## 4. 实质产出：`review` 错题路由检查器

### 4.1 问题（r77 已提出，本轮复现）

`packages/dsh-zhiyun-core-quiz/src/points.js` 的 `planPractice`：

```js
const fresh = shuffle(eligible.filter(q => !q.attempts?.length), random);
const old   = shuffle(eligible.filter(q =>  q.attempts?.length), random);
...
else chosen.push(...(mode === 'new' ? fresh : old).slice(0, count));
```

`old` 池里同时装着「答对的」和「答错的」。而 `store.js` 的 `makeAttempt` **早就有**
`countsAsWrong` 这一维（用户自评优先、`unknown` 一律不算错）—— **选池一次都没读过它**。

### 4.2 实测数字

`node scripts/radar-review-route.mjs`（固定种子，可复跑）：

| 项 | 值 |
| --- | --- |
| 题池 | 错过 10 道 / 只做对过 10 道 / 没做过 10 道 |
| 抽样 | `review` 模式 200 次 × 10 题 |
| 命中 | 错题 **1006** / 做对过 **994** / 没做过 **0** |
| **错题占比** | **50.3%**（阈值 85%） |
| 判定 | ✗ `ROUTE_MISSING`，退出码 **1** |

50.3% 意味着什么：**它与「在做过的题里纯随机抽」在统计上无法区分**。
换一个刺眼的说法：10 道「错过」和 10 道「只做对过」混在一起抽，用户点「复习」时
**每两道里有一道本来就会做**，真正该再练的那道有一半概率被跳过。

> 对照实验（单测 ④）：把 `old` 再按 `countsAsWrong` 分两段、错题在前，
> 同一套统计 **10/10 = 100%，过阈值**。这说明失败来自被测逻辑本身，而不是检查器算错 —— **阴性对照**。

### 4.3 检查器设计

`scripts/radar-review-route.mjs`（≈190 行，零外部依赖）：

- **黑盒**：只调 `planPractice` 的公开接口，不读源码、不 mock 内部函数 → 修复后**自动变绿**。
- **自证标签**：先断言题池里 `countsAsWrong` 认出的「错过」数 == 构造数，不符即报
  `LABEL_MISMATCH` 并停止 —— 防止上游 `makeAttempt` 改语义后继续输出误导性的数。
- 判定码：`ROUTE_MISSING` / `ROUTE_WASTED`（`review` 混进没做过的题）/ `SHORT_BATCH` / `SAMPLE_TOO_SMALL`。
- `--json` 机器可读；退出码 0/1，可直接接 CI。

### 4.4 一个必须记下来的坑

`countsAsWrong` 是**对象恒等比较**：

```js
return autoVerdict === QUIZ_AUTOGRADE_VERDICTS.incorrect;
```

第一版探针我用 `{ code: 'incorrect' }` 自造判定对象，结果 `wrong = 0` ——
`countsAsWrong` **静默返回 `false`、不报错**，20 道题全被当成「只做对过」，
那一次算出的 49.4% 是**假数**。改用 `QUIZ_AUTOGRADE_VERDICTS.incorrect` 本体后才是 50.3%。

> 这不是检查器的 bug，是**本仓一个真实的脆弱点**：任何从 JSON 还原、或跨模块传递判定的地方，
> 只要复制了 `{ code, label }` 而没走 `autoVerdictFromCode`，`countsAsWrong` 就会**全部变 false 且不报错**。
> 建议列入 P0（§7）。
