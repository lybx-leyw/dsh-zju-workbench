## 一、本轮判定轴：依赖图的边画的是**包名**，不是**版本**

A 组前几轮把「插件页」做得很厚：拓扑序、叶包/支撑包、层序漂移、使用账本、能力表、供应链溯源，
治理簇已有 `plugin-audit` / `compat-vet` / `plugin-caps` / `plugin-graph` / `plugin-ledger` / `plugin-score` / `upstream-radar` 七个骨架。

本轮不再加第八个体检器。换一个问法：**这七个骨架里有哪一个，能回答「宿主升版后谁的接口对不上」？**

### 1.1 一手实测（逐条 `grep`，非推断）

| 事实 | 位置 |
| --- | --- |
| 「插件」页的边来自运行时模块图，只有**包名** | `dsh-zhiyun-page-plugins/src/store.js:17`（`ctx.registry.values()`）、`host.js:27`、`runtime.js:69` |
| 全 `packages/`（除 `packages/radar/`）**零处** `registry.npmjs.org` | `grep -rln "registry.npmjs.org" packages/ --include=*.js --include=*.jsx \| grep -v radar` → **空** |
| 全 `packages/`（除 `packages/radar/`）**零处** `peerDependencies` / `engines` 求值 | 同上，两轮 grep 均空 |
| 版本漂移类的雷达骨架已有，但**都没接 profile、都没联网** | `dsh-radar-upstream-radar/src/upstream.js` 只有 `UPSTREAM_REPOSITORY` 常量；`/updates`、`/preflight*` 仍停在 TODO |

**结论**：缺口不是「谁依赖谁」，而是「**依赖的版本约束还成不成立**」。这一格与本仓任何现有面板都不重叠 ——
拓扑图答结构，账本答使用，能力表答导出，**没有一个答版本区间**。而版本区间恰恰是 DSH 生态里唯一会**悄悄坏掉**的东西：
插件还在，图标还在，只是 `cordis <5` 的声明已经不覆盖宿主 5.x，点击时才报错。

### 1.2 与「重复且无增益」的边界

- 与 `dsh-radar-plugin-audit`（骨架）重复 → 那是**装前**的静态审计；本条是**装后**的持续漂移。不同时点。
- 与 `dsh-radar-upstream-radar`（骨架）重复 → 那是**对外**扫上游新版本；本条是**对内**比对已装插件的声明与宿主。方向相反。
- 与 `hezhongtang/dsh-update-copilot`（本轮新登记）重复？→ 它做的是**更新执行**（预检闸门 + 一键升级 + 回滚），
  本条只**读约束、不下判断**。按「相似正交」登记 🟡，并注明若评审选它则可合并。
