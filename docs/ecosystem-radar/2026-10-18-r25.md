### 1.0 为什么是这一轴（方法论点）

本轮不从「生态里有什么」出发，也不复用昨日的「自己的缺口」开场，而是做了一件更便宜的事：

> **把本仓现有的「正则型 Markdown 判定」逐条列出来，问「它漏了哪些 CommonMark 一级语法」，再去生态里找那个『本就以语法为唯一真源』的底层。**

结果立刻命中一处**真正的强化式集成**（判据③成立），而不是又一条「无 → 有」：

| 本仓位置 | 现有判定 | 漏掉 |
| --- | --- | --- |
| `dsh-zhiyun-vault/src/parse/links.js` `excludedRanges()` | 围栏 + 行内代码 + 行内数学 + URL | 缩进代码块 / setext 标题 / HTML 块 |
| `dsh-zhiyun-page-notes/src/client.jsx` L220 | `matchAll(/\[\[…\]\]/)` + 标签正则 | **上述全部**，连围栏都没排除 |
| `dsh-zhiyun-page-paper/src/citations.js` `protectedRanges()` | 只处理行内反引号与已有链接（单行） | 缩进代码 / HTML 块 |

前两处口径不同（vault 比页面严），本身就是一条**待修的内部不一致**；第三处是另一个页面。
三条都指向同一件事：**「这段文字该不该参与解析」这件事，本仓用正则近似，上游用 token 判定。**
