### 1.2 为什么跑这个轴：先读码找断环

上一轮（r55）刚做完「文献条目入水口」，补的是 `BibTeX → 文献库` 那一段。本轮接着往下读，
发现**入口补齐之后，库内检索这一段仍是空的**：

```bash
# ① 论文页的检索到底调了谁
grep -rn "search\|检索\|全文" packages/dsh-zhiyun-page-paper/src/*.jsx packages/dsh-zhiyun-page-paper/src/*.js
# → Paper.jsx:130  「转录成文本，让检索与问答能定位到原文」
# → SettingsSection.jsx:27/54/67/68  「检索重排」端点（可选）
#   即：检索**存在**，但它是**上游 @ggboy123/dsh-paper-reader 的 search_paper**，
#   本仓 page-paper 只提供了一个「重排端点」的配置项，没有自己的检索实现。

# ② 本仓有没有「跨文献」的检索（不是"在某篇 PDF 里找"）
grep -rniE "cross.?paper|多篇|跨文献|library.?search|corpus" \
  packages/dsh-zhiyun-page-paper/src packages/dsh-zhiyun-host-paper/src
# → 0 条。
```

**断环的形状**：`search_paper` 的回答单位是 **PDF 文件**（"在哪篇论文的哪一页"），
而学生真正问的是 **「我半年前在哪篇里看到过那个定义」** —— 回答单位应是
**段落 / 图表 + 出处（章节 / 页码 / DOI）**，且要跨**已上传 PDF + Zotero 文献库**两个来源。

这与 r53 / r54 / r55 **同形状（第四次）**：上游数据齐全（PDF 已在 `dataDir`、Zotero 库在本地）、
下游出口存在（论文页的「问答」抽屉），**中间缺一个「把两处正文编成一个可检索语料」的转换器**。

而「混合检索（BM25 + 本地向量）+ 出处定位」恰好是一个**该用底层库、不该自己写**的能力 ——
正是「强化式集成」三条判据要考的场景。于是本轮不去扫新的「论文阅读器 UI」（r20 已判簇内 ⛔），
而是**只找「检索底座」**。

| --- | --- | --- |

**与现有功能的关系：重复且可强化**（判定为非「重复无增益」的关键是 ③：换了检索底座，不是又加一个搜索框）。

   **不报错、不崩溃，只是"没有这个功能"**。这是 A 类候选的新一种失败形态：**静默降级**（与 r42 的
   「`apply()` 抛错 → 整个 bundle 起不来」相对）。
2. **Python 运行时是硬前置**。引擎是 `spawn` 出去的 `kb_engine.py`，首次使用还可能要下载 `bge-small` 模型
   （包内 `install.mjs` 默认注入 `--models`、失败自动切 `hf-mirror.com`）。
   本仓用户端是 Electron 桌面壳，**Python 不一定在 PATH 上** → 「装得上」不等于「跑得起来」。
3. **会往工作区写东西**：`<workspace>/.kb-rag/state.json`（会话默认值）与一个 `kb.sqlite`。
   与「笔记库只有 `.md`」的既有约定（r40 结论）**冲突**，须评审先裁决落点。

⚠ **自查**：本轮**没有** `pip install` 该引擎、**没有**跑过任何一次真实检索，因此
**不声称**检索质量优于现状；上面 ③ 是「换了一个混合检索底座」的事实陈述，不是效果承诺。
模型体积、首次索引耗时、中文召回率**均未实测**。

## 3. 骨架 `packages/dsh-radar-kb-rag`

A 类，效法 `dsh-zhiyun-paper` / `dsh-zhiyun-host-paper` 的写法：**锁版引入 + 外围兼容层，绝不改上游源码**。

```

├── package.json        # dependencies: { "dsh-kb-rag": "1.6.8" }  ← 精确版本，无 ^
├── cordis.patch.yml    # - insert: [{ id: radar-kb-rag, name: dsh-radar-kb-rag }]
├── src/index.js        # 占位；apply() 直接抛错；TODO-0 / TODO-1 / TODO-2
├── src/upstream.js     # 锁版凭据（UPSTREAM_PACKAGE / UPSTREAM_VERSION / 预期 exports / inject）
├── README.md           # 顶部「候选骨架·未评审·未接入 profile·不可直接使用」
└── OWNERS              # Owner: shared
```

### 5.1 ⚠ 搜索超限 1 次

### 5.2 ⚠ `git clone` 三次失败后的应对

首次 `git clone`（完整历史）连续 4 次 `fetch-pack: unexpected disconnect`（每次约 134 s 超时）。
改用 `--depth 1` 浅克隆第 1 次即成功。**代价**：本地只有 1 个提交，`ls-remote` 之外的本地历史全无，
且注册表/报告只能以「文件级」方式核对，不能 `git log` 追溯。

### 5.3 ⚠ 本轮产物经 Git Data API 送达，而非 `git push`

浅克隆 + 前几轮记录里「`git push` 返回 0 但远端未变」的静默失败，使得本轮改用
**Git Data API**（blob → tree → commit → `PATCH refs/heads/radar`）提交，
**以 `refs/heads/radar` 的实际 SHA 为验收依据**，不以退出码为准（沿用 r43 的教训）。
