## 1. 起点：先读码找断环，再定向搜

本轮起点**不是关键词**，是 `packages/dsh-zhiyun-core-lecture/src/polish.js` 的阅读。
读完发现两处「写了但没接上」的地方，其中一处经实测确认是**真缺陷**。

### F-1 · `maxChars` 对**单个知识点内部**完全无效（实测确认）

`chunkLectureForPolish()`（`polish.js:507`）注释写「单次请求的**最大正文字数**」，
但它的切分粒度是**整条 input**：只有当 `cur` 里已有内容时才会开新卷，**单条超限的知识点仍独占一整卷**。

实测（`node` 直跑 `chunkLectureForPolish` + `buildLecturePolishBody`）：

| 构造输入 | 卷数 | 每卷正文字数 | 实际请求体（含章节头/课件线索） |
| --- | --- | --- | --- |
| 2000 / 15000 / 2000 字（3 个知识点） | 3 | 2001 / **15001** / 2001 | 2100 / **15100** / 2100 |
| 单条 30000 字 | 1 | — | **30093** |

⚠ 注意：`maxTopics = 1`（默认值）本身就让每个知识点独占一卷，此时 `maxChars` **永远不可能触发**
（`cur.length > 0` 恒为假）—— 也就是说这个上限在默认配置下是**死参数**。

**后果**：一节 90 分钟的课，若某个知识点被连续讲到 1.5 万字（口语转写很常见），
那一次请求会带着一整段无切分的正文上模型，`kLecturePolishMaxTokens = 32768` 的输出预算
反而可能不够，表现为「这一章写成半截」，而 `failures` 里记的是一个笼统的失败。

**修法（不需要任何新依赖，约 15 行）**：在 `cur.length === 1` 且 `curChars > maxChars` 时按
**段落边界**（`\n`，其次句号）把这一条切成子段；子段用 `chapterNo/topicNo` 相同、加 `partNo/nParts`
标识，`source` Map 的键相应改成 `ch/t#part`，`buildFilledChapters` 按 part 拼回同一知识点。
**这一步是纯函数改动，可单测，不必等任何上游包。**

### F-2 · 讲义生成的进度「有通道、无出口」

| 层 | 现状 | 证据 |

| 装配器 | **已支持** `onProgress` | `polish.js:795` `async function assemble({ tree, blocks, context, signal, onProgress } = {})` |
| 进度上报 | 前缀和，按卷序报 | `polish.js:1031-1040` |
| 中转 | **丢弃**：`workbench.js:329` 调 `lecture.assemble({ tree, blocks, context: title, signal })` —— **没有传 onProgress** | — |
| 前端 | 只有一个布尔值 | `lecture-reader.jsx:43`：`state.lectureBusy ? '正在生成讲义…' : …` |
| CSS | `.zs-progress` 已就绪 | `dsh-zhiyun-page-study/src/style.css:27` |

`workbench.js` 有成熟的 `jobs` 进度机制（`start()` 里 `job.progress = p`、
`view(job)` 对外暴露 `progress`），**但只用在了「解析」上**；讲义走的是 `mutate()`
（一个 `Promise`，无进度字段）。同一节 20 个知识点 = 20 次串行 LLM 调用，
而用户看到的只有「正在生成讲义…」，无进度、无 ETA、无「第几章」、**无取消**。

📌 这是 r53（课表→ics）、r54（`endMs`）、r59（笔记→CC98）、r60（记录→日历）之后的
**第五次同型断环**：能力在、出口缺，缺的是一层接线，不是新库。

| 项 | 值 |

| 依赖 | **零**（`dependencies: null`，`peerDependencies: null`，Node ≥20） |
| ★ / 活跃 | ★0 / push 2026-09-24 |
| 注册面 | `shell.overlay` 一条 + **右侧栏 tab** + 设置卡 + 自己的一条路由 `GET /plugins/task-progress/state` |

**它做的是**：给「长时间脚本任务」开一条**第二条专用通道** —— 脚本往
`$DSH_PROGRESS_DIR/<task>.jsonl` 追加 JSON 行（`{"v":1,"task":"build","pct":42,"msg":"linking"}`），
宿主侧一个 1 s 扫描 + 2 s 轮询的只读路由把状态抛给浏览器，浏览器画成悬浮胶囊 + 右侧栏面板。
它的 README 开篇原话与 F-2 **是同一个诊断**：

> "DSH's `pwsh`/`bash` tools are not streaming: a foreground command's output appears only when it finishes… a ten-minute build is a black box to the human watching the GUI."

**为什么不是 🟢（三条强化判据逐条不成立）**：

| 判据 | 判断 | 理由 |
| --- | --- | --- |
| ① 仍是同一个面板 | ✗ | 它是**会话头/右侧栏的全局任务面板**；本仓的「讲义」是「学习」页里的一个子视图。接它 = 多出一个**新面板**，而不是让讲义那个面板变好 |
| ② 功能仍相似正交 | ✗ | 它消费的是**外部脚本写的文件**；讲义的进度是**宿主内 `assemble()` 自己算出来的**（`done/total` 现成）。两者数据源不在同一个世界 |
| ③ 底层多调了更优质实现 | ✗ | 它没有「更优的实现」可借 —— 它借给别人的是**约定**（jsonl 格式 + 文件位置），而约定层本仓已有（`onProgress`） |

**它真正教给本仓的是三件事（可以免费拿走，不必装包）**：

1. **进度要「按卷序报、不按完成序报」** —— 本仓 `polish.js:1031` 的注释**已经**这么写了
   （前缀和），说明作者遇到过同一个问题。这条**已验证，可放心沿用**。
2. **上报频率要钳制** —— 它把轮询 clamps 在 500–60000 ms。本仓 20 个知识点会在
   毫秒级连发 20 次 `onProgress`，前端如果直连 `setState` 会触发 20 次重渲染 → 应按 250 ms 节流。
3. **「报告了但没写完」要有兜底** —— 它对「超过 30 s 没有任何上报」的任务补一条提示。
   对本仓对应的是：`assembler` 每卷有 2 次重试，重试期间**没有进度**，UI 会卡在同一格 —— 应显示「第 k/20 卷重试中」。

> 📌 结论：**🔵 参考**。登记、不采用、不出骨架。它是「同轴上的正确做法示范」，不是可锁版接入的底座。

## 6. 建议人工 review 的重点

1. **F-1 是否按「bug」处理**：`maxChars` 在默认 `maxTopics=1` 下是死参数，且单条超限时整条直送。
   实测 30000 字 → 请求体 30093 字。这可能是「某章只写了一半」的根因之一。
2. **F-2 是否值得做**：20 次串行调用 vs 一个布尔值。工作量约 40 行（workbench 加 `progress` 字段 +
   model 轮询 + lecture-reader 渲染 `.zs-progress`）。**要不要现在就做**由人工拍。
3. **不要接 `dsh-task-progress` 的面板**：它的价值是「做法示范」（按卷序报 / 节流 / 超时兜底），
   不是「可挂载的底座」。
4. **`dsh-llm-rate-limit` 是部署层选项**，不是页面级强化 —— 若要接，应作为 profile 级依赖统一讨论。
