#### 1. `PerryLink/dsh-score` ★12 · Apache-2.0 ✅ · TypeScript · push 2026-10-12

> Multi-dimensional quality scoring for DeepSeek Harness plugins: scores a repo or npm package
> across install success (consuming dsh-test-drive results), maintenance activity,
> documentation completeness…

| 项 | 判定 |
| --- | --- |
| **类型** | **A · 原生 DSH 插件包**（带 Cordis 插件形态） |
| **学生场景** | 间接但关键 —— 学生装的插件质量不可知，直接决定工作台**能不能起来**（本仓 CONTRIBUTING 3.1 的核心风险） |
| **与现有功能的关系** | ✅ **重复且可强化（强化式集成）** |
| **分级** | **🟡 需移植改造** |

**为什么是「强化式集成」——三条同时成立：**

1. **仍是同一个面板**：落在既有「插件」页（`dsh-zhiyun-page-plugins`，侧栏第 7 项），
   **不新增导航项**。
2. **功能仍相似正交**：现有插件页回答的是
   「**我不用论文，能不能把论文那一整块关掉，而别把解析也弄坏**」——
   即**依赖关系与启停**；`dsh-score` 回答的是「**这个插件值不值得装 / 装得起来吗**」——
   即**质量与可信度**。两者同属「插件管理」域，但**不重叠**：一个是「关掉谁、会不会连坐」，
   一个是「装谁、它靠不靠得住」。
3. **底层多调了更优质实现**：本仓**完全没有**任何插件的质量评分能力
   （现有 `dsh-radar-plugin-audit` 骨架仅做审计占位；`profiles/zhiyun-bench/package.json`
   的 22 个 bundle 无评分来源）。引入 `dsh-score` 是**引入本仓没有的、更优的实现**
   （消费 `dsh-test-drive` 的安装实测结果 + 维护活跃度 + 文档完备度多维打分）。

**建议集成方式**：锁版挂载（效法 `packages/dsh-zhiyun-paper`）+ 外围兼容层。
骨架已生成 → `packages/dsh-radar-plugin-score`（**未评审、未接入、不可直接用**）。

**待确认**：上游 ★ 仅 12、fork 0，**属早期项目**；采用前必须先在隔离环境跑通，
并确认其评分的**数据来源是否可离线**（若依赖外部 API，需评估可用性）。

## 五、本轮方法论结论（供后续轮次直接引用）

> **① A 组并未枯竭，枯竭的是「功能域切片」，不是「生态连接切片」。**
> 当日第六、七轮在 B 组与跨校同型轴上均只捞到 1~3 条新候选并得出「薄」的结论；
> 本轮换轴后 10 次搜索捞出 **11 条新候选、2 条 🟡**，**产出率高出 3~5 倍**。
> **结论：A 组应以「与外部生态的连接面」为新主力轴** ——
> 跨 harness 互操作、插件分发/评分/审计、插件供应链安全、插件协议标准。

> **② 「插件市场」赛道已饱和，且已先登记。**
> 本轮单是 DSH 插件市场就命中 **6 个**（★296 / ★176 / ★154 / ★77 / ★70 / ★60），
> 全部与已登记骨架 `dsh-radar-dsh-market`（锁定 `dsh-market` ★6494）**功能重叠**。
> **除非出现明确更强的底层（★ 或能力代际差），否则该子轴不再重复评估** ——
> 后续遇同类项**直接判 ⛔ 重复且无增益**，只登记一行。

> **③ 「插件治理」（评分 / 安全审计）是本轮真正的空白，且是强化式集成的理想落点。**
> 本仓有 22 个 bundle 却**零质量/安全元数据**；而 `dsh-score` + `dsh-secure-audit`
> 恰好提供**「好不好 + 安不安全」**两个正交维度，且都落在既有「插件」页内。
> **建议把「插件治理」列为下一轮 A 组的优先深挖方向**
