## 1 · 本轮轴：为什么是「提醒」

前几轮 A 组把「插件本体能力」「输入通道」「MCP」等轴走完之后，剩下的最高频横切需求是**「我不在电脑前的时候，工作台能不能叫我」**。

这条轴在本仓**已经有一个骨架**：`packages/radar/dsh-radar-zone-notify`（r106，2026-10-30），锁 `dsh-plugin-notifications@0.1.0`，用途是把「今日」页的到期条目送到桌面。

它的阻塞项写得很清楚（README「接入前必须先做的事」第 2 条）：

> **解决「从哪拿包」** —— npm 上还没有这个包。要么等上游发版，要么锁 git 引用并接受构建步骤。**这一条不解决，本包不可能跑起来。**

**本轮的核心问题因此不是「再找一个通知插件」，而是：生态里有没有一个「npm 上真能装、且能替掉那个空转骨架」的更优底层。**

实测答案：**有能装的，但它接不了这条线。** 见 §3。

### 3.1 `chromoany/dsh-notify-me`：为什么是「看得上、接不上」

**它本身的质量在 A 组里属于第一梯队**，这一条要写清楚，免得评审按「🔵 = 次品」处理：

| 项 | 核实结果 |
| --- | --- |
| 版本 / 活跃 | **v1.17.0**，npm `modified 2026-10-28`，5 个连续版本（1.14.7→1.17.0） |
| npm 可 install | ✅ `registry.npmjs.org/dsh-notify-me/latest` → 1.17.0（**这正是 `zone-notify` 缺的东西**） |
| 依赖 | `dependencies: null`；`peerDependencies` 只有 `@deepseek-ai/dsh-client-locale`，带一段版本窗口 → **锁版可行** |
| 兼容矩阵 | `dsh.compatibility.dshReleases` 逐版标注，含 `0.2.0-rc.2 / 0.2.1-rc.2` |
| patch 形状 | `- insert: [{ id: notify-me, name: dsh-notify-me, config }]`；`hostFallback` / `relay` **两个可选宿主模块默认关** |
| 工程质量 | 宿主半 713 行 + 客户端半 4,842 行；`window.__dshNotifyMe.debug()`；只读 `credentialsFile` 不写明文密钥 |

**但三条判据里 ② 和 ③ 都过不了：**

| # | 判据 | 结论 |
| --- | --- | --- |
| ① | 仍是同一个面板 | ⚠ 它**自带一个「设置 → 通知提醒」分组**，与本仓 settings 主张叠了一层（同 r106「只挂宿主半边」的理由） |
| ② | 功能仍相似正交 | ❌ **触发域不同**：它推的是**会话事件**（`turn/end`、`approval/asked`），也就是「AI 这一轮跑完了」；`zone-notify` 要推的是**待办到期**（`time.js` 判出的过期/临期条目），属于**与对话无关的本地数据**。今天的待办到期时**没有任何会话在跑**，它不会响 |
| ③ | 底层多调了更优质实现 | ❌ **没有对外出口** |

判据③的证据（直接读 `lib/client.js` 的公开 API 面，不是看 README）：

```js
api.version    api.setConfig    api.resetConfig
api.test       api.decide       api.testExternal    api.debug
```

`showToast(kind,title,body,sessionId,quick)` 与 `deliver(...)` 都是**闭包内私有**，全局对象上**没有** `notify(title, body)` 之类的第三方入口；`onEvent` 是**消费**插件自己事件的方向（`__dshNotifyMe.onEvent` 由调用方注册），不是让别的插件**发**通知的方向。宿主侧 `lib/index.js` 只导出 `FOCUS_ROUTE`、`name`、`VERSION`、`apply` —— 没有 `ctx.provide`。

⇒ **它不是 `zone-notify` 的替代品，也不是它的底层**；两者只能并存为两个互不知情的通知源，且第二个还要抢 settings 分组。**不出骨架、不替换骨架。**

**可复用的只有工程经验**（写进 `zone-notify` 的 TODO，不动代码）：① 它的 `hostFallback.pageLeaseMs` + `/__dsh-notify-me/health`「页面在线租约」解决「页面和宿主谁发」的重复投递，正是 `zone-notify` TODO-4「节流与静默」缺的那一半；② 它的 `credentialsFile`（chmod 600、不进 patch 层）是本仓任何「外部网关」类插件都该照抄的密钥处置口径。

### 3.2 `Phant0Meow/dsh-meow-smooth`：形态冲突

★67、MIT、`dsh.bundle.patch` + `dsh.client`（platform `web`）、版本 `meow-smooth@0.8.1`。它 80% 的篇幅是**手机端 UI 手势**（边缘抽屉、返回手势、输入框折叠、按钮行不换行），通知只是其中一节。

- 切的是**宿主外壳的交互层**，不是任何业务面板 → 判据①不成立；
- 与本仓的关系是「两套布局主张并存」，正是 r106/r84 反复拒绝的那一类；
- 附带的 `web-push` 依赖（`^3.6.7`，**非锁版**）+ `prepare` 现场构建 → 锁版成本高。

⇒ 🔵 只登记。若将来做「手机端可用性」专门轴，它的**手势清单**可当需求表参考，但不摘代码。

## 6 · 对 `zone-notify` 的建议（本轮唯一的可执行产出）

**不建议换底层，建议先解阻塞。** 按影响排序：

1. **换锁版源**：`dsh-plugin-notifications` 在 npm 上仍 404（r106 记录），而 `dsh-notify-me@1.17.0` 可 install —— 但如 §3.1，它**接不了待办到期这条线**。所以正确动作是**等 `bertholomus` 发版**，或**锁 git 引用 + 本地 build**，而不是换成 `notify-me`。
2. **补 TODO-4（节流与静默）时照抄租约思路**：`pageLeaseMs` + 健康探针解决「页面开着时宿主又发一遍」的重复投递，这是高频运行下最容易踩的坑（每 3 小时一轮，通知风暴比漏发更烦）。
3. **评审时的第一个问题应是**「待办到期时用户到底在不在页面前」——若答案多半是「页面开着」，那这个骨架的价值会大幅缩水，应优先做页内角标（0 依赖、`document.title` 前缀）而非系统通知。
