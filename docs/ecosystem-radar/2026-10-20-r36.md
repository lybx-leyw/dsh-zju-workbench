## 3. 现场实测（本仓真实代码，不是推断）

夹具：两节课的 `blocks` 各含 1–2 句 + `tag.summary`；`layers` 取 `LayerId` 全集。

```js
import { searchLesson } from 'packages/dsh-zhiyun-page-study/src/layered-search.js';
```

| 查询 | 命中 | 顺序 | 说明 |
| --- | --- | --- | --- |
| `动量` | 3（teacher 1 / lecture 2） | teacher#0 → lecture | — |
| `守恒` | 2（teacher 2） | block#0 → block#1 | 两个都是子串命中，**同分并列**，顺序由数组决定 |
| `不等式` | 3 | block#0 → block#1 → block#1 | block#1 的**摘要**是「柯西不等式」，却排在 block#0 正文之后（**L-1**） |
| `柯西不等式` | 2（都在 block#1） | 正文 → 正文 | 摘要命中**根本没出条**（`titleBody` 档位） |

### L-1 · 排序层缺失（本骨架要解决的问题）

`layered-search.js` L155 是 `for (const block of blocks)` —— **块序遍历**，`hits.push` 按扫描顺序追加，
最后 `hits.slice(0, limit)` 直接截断（L300）。**没有任何重排**。
后果：查询「柯西不等式」时，命中列表里排在前面的是正文里顺带提到它的那句，
而不是**标题就叫这个**的那一节。这不是「排得不好」，是没有排序。

### L-2 · `layers` 归一化把「未指定」和「指定了空集」混为一谈（**上线阻断级**）

```js
const wanted = layers instanceof Set ? layers : new Set(layers ?? []);   // L128
```

- 全仓默认层集是 `layers.js` 的 `defaultSearchLayers`（`layers.js` 里是 `Set`）；
- `study-workspace.jsx` L449 写的是 `layers ?? defaultSearchLayers` —— **恰好**绕过了；
- 但任何**新调用方**（含未来的本骨架）只要不显式传全集，就会得到
  `empty:true, hits:0, counts:{}` **且没有任何错误**。

实测：`searchLesson(res, {query:"守恒", layers: []})` → `{"empty":true,"hits":0,"counts":{}}`。
**「搜不到」与「没指定搜索范围」在返回值里长得一模一样**，这正是本仓一直在防的那类沉默失败
（对照 `dsh-zhiyun-notes` 文件头「静默退化等于记笔记还在、重启就没了」）。

> ⚠ 顺带记录：`layers.js` 导出的 `defaultSearchLayers` 实测是 **`Set`（打印为 `{}`）**，
> 而报告 §1 的表格里我一度把它写成「数组」—— 复核后已改正。这条修正本身也是 L-2 的证据：
> 层范围的类型在不同文件之间已经不一致了。

## 5. 🟢 深度评估：为什么 `layered-search.js` 不能「整包换掉」

这是我写骨架时最重要的一个判断，必须写清楚，因为它决定了骨架的形状。

本轮的诱惑是：**把 `layered-search.js` 整个换成 minisearch**。这是错的，理由有三条，两条在代码里：

1. **「先筛后扫」是产品语义，不是性能优化**。文件头第 ②③ 条与 App
   `knowledge_store.dart` 逐条对齐：筛了 2×11 维之后，**只有块层能出结果**，
   页面层/主线/术语表没有块级标签，放行就是「假命中」。minisearch 的倒排索引里没有这个概念。
2. **档位决定的是「候选字段集」，不是排序算法**（第 ① 条）。`titleOnly` 不看正文，
   `tagFilter` 允许空关键词只筛选。把这三档翻译成 minisearch 的 `fields` + `boost`，
   会在「档位 × 层 × 维度」的三维组合上产生 20 多种情形，**每一种都要重新对齐 App**。
3. **10-19 第二十九轮的教训**：中文语义底层「结构对、边界错」。那一轮的中文数词解析
   两个上游库给出的错法**方向相反**（一个算多、一个算少），取交集也不成立。
   排序层同理：minisearch 能给**更好的顺序**，但不能替我们保证**命中集合不变**。

所以骨架的边界被收窄成一句话：**只对页面已算好的 `hits` 重排，不增删、不改字段、不改档位。**
这既是判据②（相似正交）的落点，也是「强化式集成 ≠ 简单集成」的分界线。

## 6. 本轮结论（四条）

**① 「检索」在 A 组已经裂成两半：搜索（饱和）与排序（空白）。**
12 次搜索里，**web search provider 有 15 家**、RAG 知识库 **16 家**、会话检索 **9 家**；
但**做「结果排序 / 相关度」的一家都没有**——它们全部止步于「能搜到」。
本仓也一样：`layered-search.js` 有 374 行，**没有一行**是排序。这是 A 组目前最干净的空地。

**② 本轮的产出不是「找到更好的库」，是「找到一个沉默失败」。**
L-2（`layers` 空集 → 零命中且不报错）与检索能力无关，但它决定了任何检索改造能不能上线。
建议人工优先处理，**优先级高于本骨架**：先让「未指定层」显式等同于 `defaultSearchLayers`，
或干脆让 `searchLesson()` 在 `layers` 为空集时抛 `INPUT` 错（本仓 `dsh-zhiyun-notes` 的做法）。

**③ A 类候选的瓶颈仍是「装得上」，且这轮再多一道：npm 根本没发布。**
`dsh-attachment-formats` 形态完美（patch 无 `!!js`）、许可干净（Apache-2.0 + NOTICE）、
能力对口（附件文本抽取是本仓真缺口）—— 死在 **npm 上不存在**。
第三十四轮把这类归为「可锁版」这一门，本轮证明它不止一种死法：
`private: true`（kb-sieve）、双名 404（上一轮的 `dsh-raw-html`）、**声明 public 却从未 publish**（本轮）。

**④ B 类候选的判据需要一条新规：必须先有「命中集合不变」的证明。**
本轮骨架用了整整一节（§5）来限定「只排序不增删」。建议写进 `CONTRIBUTING`：
**凡替换检索/解析底层的候选，差分测试的断言必须是「命中集合 ⊇ 旧实现」**——
10-19 第二十九轮（拼音）、第三十一轮（高亮）、本轮（排序）三轮各自独立地得到了同一条结论。

## 9. 建议人工 review 的重点

1. **先看 L-2，不看骨架**：`layered-search.js` L128 的 `layers ?? []` 会把「未指定」变成「零命中」。
   这是本仓花了大量注释去防的「沉默失败」，而且它现在**只被一处调用方侥幸绕过**。
   建议：`layers` 为空集时抛 `INPUT` 错，或把 `undefined` 与 `[]` 显式区分。
2. **骨架的边界是否收得太窄**：本骨架只重排、不增删。代价是「摘要能不能在 `titleBody` 档位下单独出条」
   这个缺陷（L-1 的第 2 条）**本轮没有解决**——因为它是 `layered-search.js` 的语义问题，
   改它就违反「不改上游源码」。如果要修，应单独提 issue，交给 `dsh-zhiyun-page-study` 的 owner。
3. **中文分词选型**（TODO-1）：`Intl.Segmenter` 零依赖但分词语料不可控（10-19 第二十九轮已证
   中文语义底层「结构对、边界错」）。建议评审时直接跑夹具：`动量守恒定律` / `∑a²` / `p=mv` / `a=b`。
4. **体积**（TODO-6）：`minisearch` unpacked 820 KB 里大部分是 UMD + sourcemap，
   进 bundle 的 ESM 份额未测。**先测再谈接入**，本仓首屏敏感。
