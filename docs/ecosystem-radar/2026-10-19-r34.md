### 为什么是这一轴

前三十二轮扫的是「页面能看见的东西」——今天、学习、论文、笔记、规划、插件。
每一轮都在问同一个问题：**这个页面能不能换一个更好的底层？**
本轮第一次把镜头移到**页面的下面**：几乎所有页面的每一次 AI 回答，都要经过同一条请求管线
（`@deepseek-ai/dsh-llm`）。那条管线上的「失败之后怎么办」在本仓**是一片空白**：

- `packages/*` 里 **没有任何一个包**依赖 `@deepseek-ai/dsh-llm`；
- profile 的 bundles 里**没有**显式 `dsh-llm-retry` 行（它来自 `@deepseek-ai/dsh-base`）；
- 也就是说：**provider 由用户在设置里选定，失败即失败**。学生在自习室用校园网、
  在手机上开热点、在深夜赶论文——只要那一家 provider 限流或鉴权失败，
  「问一问」和「论文助手」就是一条红字，且**没有任何降级**。

所以本轮的问题很具体：**DSH 生态里有没有人已经把这层做好了？**

### 4.2 强化式集成三条判据

| 判据 | 结论 | 依据 |
| --- | --- | --- |
| ① 仍是同一个面板 | ✅ **最严格意义** | **不存在新面板**：不新增页面、导航、设置分区（分区归属留作 TODO 3 二选一）。用户看到的页面与今天逐字相同 |

### 4.4 ⚠ 第四道门：**宿主版本窗口不相交**（本骨架最大风险，编号 R-1）

这是本轮最硬的一个发现，必须写清楚：

- 上游 26 项 peer 全部是 `@deepseek-ai/dsh-*: ^0.2.1-rc.2`；
- 本仓 `runtime.lock.json` 的 `hostVersions` 是 **`0.2.0-rc.2`** 与 **`0.2.1-alpha.1`**；
- 按 semver 的 prerelease 规则，`^0.2.1-rc.2` 的窗口是 **`>=0.2.1-rc.2 <0.3.0`**：
  - `0.2.0-rc.2` → 主版本号更低 → **不满足**；
  - `0.2.1-alpha.1` → 主版本号相同，但 prerelease 段比较 `alpha` < `rc`（字母序）→ **不满足**。
- 结论：**本仓当前锁定的两个宿主版本，都不在插件声明的窗口内。**
- 已核实：`@deepseek-ai/dsh-agent` 在 npm 上**有** `0.2.1-rc.2`（2026-10-17 发布），
  且上游发布（10-18）紧随其后 ⇒ 上游是按 `0.2.1-rc.2` 测的。

**因此本骨架的定位是「条件性 🟢」**：骨架照出（结构、边界、风险都已写全），但 **README 第一条风险就是
「装不上」**。评审只有两条路：**把宿主升到 `0.2.1-rc.2`**（需过 `scripts/test-host.mjs` 全量回归），
或**放弃本候选**。本 skill 明确禁止绕过 peer 声明（`--force` 之类），此路不通。

> 这条发现的价值可能大于骨架本身：**A 类候选的瓶颈已经从「找得到」变成「装得上」**。
> 过去十几轮出的 A 类骨架，有几个其实从未验证过 peer 窗口——建议对在册 A 类 🟢/🟡 候选做一次
> **批量 peer 窗口体检**（把所有候选的 `peerDependencies` 与 `runtime.lock.json` 求交集）。

## 5. 🟡 为何不出骨架：`loongsuite/dsh-plugin`（OTel 追踪）

Apache-2.0 ✅、★29、npm 可锁（`@loongsuite/dsh-plugin@0.1.3`，144 KB）、形态合规 —— 三门全过，判 🟡 而不是 🟢，且**不建 L2**，理由是**产品边界**而非技术：

1. **它没有界面**。它做的事是把每个 turn 变成 GenAI span 树，经 OTLP 发到 Jaeger / Tempo / Langfuse。
   本仓**没有**这样的后端；`OTLP endpoint` 是运维配置，不是学生功能。
2. **默认开启 = 把使用数据往外发**。本仓插件普遍遵循「纯本地」（`dsh-personal-center` 甚至把这一点写进描述）。
   接一个默认外发的追踪插件，与这条原则正面冲突。
3. **学生场景契合度低**。它的价值在「导师侧看学生卡在哪里」，那是**运营视角**，
   而不是「今天页 / 学习页 / 论文页」的能力升级。

→ 登记为 🟡「若做导师侧性能诊断的底层」，**本轮不建骨架**。这是判断，不是遗漏。

## 6. 本轮结论（四条，按价值排序）

**① 「请求管线」是 A 组最后一块没人占的空地，而且它真的空。**
本轮 2,200 条命中里，provider 接入有 11 家、网关有 10 家、用量统计有 13 家、通知有 10 家，
**只有 2 家**做「失败转移」。这说明生态的供给结构是「抢入口」（接更多 provider / 更多客户端），
而不是「补可靠性」。本仓恰恰在可靠性上是空的。

**② 三条子轴同时饱和，A 组进入「复刻期」。**
用量（13 家）、通知（10 家）、审计（9 家）——本轮 54 条新仓里 40 条落在这三簇，全是「第 N 家」。
**建议：这三轴封板 3 个月**；A 组的额度转给「管线类」窄词（fallback / retry / cache / queue / budget）。

**③ 判据③需要更硬的验收方式。**
本轮首次出现「结构上显然更优、但无法用现有手段证明」的候选。建议在 `CONTRIBUTING` 里补一条：
**强化式集成的 ③ 必须附一段可复现的差分样本**（输入 → 旧实现输出 → 新实现输出 → 为什么后者更好）。
本轮 R-3 就是这条规范的第一个待办。

**④ 宿主版本正在变成 A 类的真实天花板。**
`dsh` 在 20 天内从 `0.2.0-rc.2` 走到 `0.2.1-rc.2`，而插件作者全部按最新 rc 写 peer。
本仓 `runtime.lock.json` 只锁两个版本，**每接一个 A 类插件，都要多背一次宿主升级的回归成本**。
这是本轮最该让人类决策的一件事（见 §9）。

## 9. 建议人工 review 的重点

1. **R-1 先于一切**：`dsh-llm-fallbacks@0.6.7` 的 peer `^0.2.1-rc.2` 与本仓 `hostVersions` 不相交。
   **要么升宿主（0.2.1-rc.2，需全量回归），要么放弃本候选。** 在此决定之前，骨架不得接 profile。
2. **R-2 监听顺序**：上游要求 `dsh-llm-retry` **先**注册，它只在重试耗尽后介入。
   本仓 profile 无显式 retry 行（来自 `dsh-base`），须在实机确认顺序，否则会「还没重试就换模型」。
3. **默认值三条**：触发码集合（`RATE_LIMIT` 要不要默认开？换 provider = 换账单）、
   分时（默认关）、角色化（默认关且整块禁用）。三条都要能用单测钉死。
4. **A 组供给结构是否该换靶**（§6②）：用量/通知/审计三轴封板，额度转给管线类窄词。
5. **A 类候选的 peer 窗口批量体检**（§4.4）：建议一次性把所有在册 A 类候选
   （`dsh-market` / `dsh-web` / `modlens` / `modsearch` / `DSH-taskboard` / `evolve-modes` / `raw-html` …）
   的 `peerDependencies` 与 `runtime.lock.json` 求交集，把「装不上」的候选一次性标出来，
   避免每次接入都重新踩。
6. **`yuxino/dsh-blue-whale-maid`** 与 **`lanlandeli/dsh-usage-stats`**（均 `NOASSERTION`）
   需人工核一次许可证；本轮不采用、不摘码。
