| 判据 | 是否成立 | 依据 |

#### 4.2.2 可迁移的四条决策（**这才是骨架的价值**）

| # | 决策 | 上游怎么做的 | 对本仓意味着什么 |
| --- | --- | --- | --- |
| **C-1** | **按 id 契约返回，不接受自由文本** | `parse.ts` `parseTranslations(content, expectedIds)` 解析模型回复，**只收 `expectedIds` 内的 id**，产出 `{ found: Map, missing: string[] }`。容忍 Markdown 代码围栏（`^```(?:json)?`） | 句级对齐的**前提**。若让模型自由生成译文，就无法把译文钉回某一句。**本仓现有 `translateSelection` 是整段进出，没有 id 概念** |
| **C-2** | **字符预算分批 + 有限并发 + 缺漏单句重试** | `translator.ts` 头部注释即是规格：「cache lookup, batching by character budget, bounded concurrency, validation, and **per-sentence retries for missing ids**. **Only successful translations are cached**」。默认 `concurrency: 2`、`maxSentencesPerRequest: 40` | 直接决定「一页 60 句」时的成本与延迟。**「只缓存成功」**是易漏的一条——失败也缓存会让一次网络抖动永久留疤 |
| **C-3** | **逐句语言检测 + 已是目标语言就跳过** | `languages.ts` `detectLanguage()`：按书写系统（kana→ja、hangul→ko、han>0.5→zh、cyrillic→ru、latin→函数词打分）+ 简繁高频字表；`isAlreadyInLanguage()` 命中则不调模型 | **省钱**。中文论文段落、公式旁的中文注释、参考文献里的中文标题，全部不送模型。本仓 `isTranslatableSelection()` 只判「像不像英文」，粒度是**整段**，且不看目标语言 |
| **C-4** | **术语表进入缓存键** | `translator.ts` 持有 `#glossaryHash`，`cacheKey` 含其哈希；`prompt.ts` 有 `PROMPT_VERSION` | 改了术语表必须**自动失效**旧缓存，否则用户改完术语发现译文没变。本仓论文页翻译缓存是**内存缓存**，无版本/术语维度 |

**引擎无关是它最大的适配优势**：`providers.ts` 抽象出 OpenAI 兼容 / Anthropic / Azure / Bing / Google / 有道六种。本仓论文页走「宿主 llm + 内存缓存」（`Paper.jsx:168-170` 注释），**只需要实现 `ChatClient` 这一个接口**即可复用 C-1~C-4 全部逻辑。

#### 4.2.3 为什么判 🟡 而不是 🟢

1. **不可锁版**：未发 npm ⇒ 骨架 `dependencies` 必须留空（按 r155 §③ 定下的「B 类契约提取」口径）。
2. **上游是 VS Code 扩展**：`pdf-viewer-provider.ts` / `webview-collection.ts` / `webview/` 全部绑死 VS Code Webview API，**一行都不能搬**。能搬的只有 `src/translation/`（纯 TS，不 import `vscode`）。
3. **41 天无更新**：`pushed 2026-09-30`。功能完整但不是活跃项目，不排除有未修的边角问题。
4. **句级对齐的 UI 部分本仓要自己写**：上游「悬停句子 → 描边 → 箭头 → 译文同高」的坐标对齐在 `src/webview/` 内，与 VS Code 的 split-panel 布局耦合。本仓论文页是**同源 iframe**（`ReaderFrame.jsx`），文本层在 iframe 内 ⇒ 对齐要用 iframe 内 `getBoundingClientRect()` 回传，是**新代码**。
