**为什么是「重复且可强化」而不是「全新」** —— 三条判据逐条有实证：

1. **仍是同一个面板**：`packages/dsh-zhiyun-page-plugins/src/Panel.jsx:147` 已经在渲染一列「吃灰清单」，
   `usage.js` 里 `createLedger / recordUse / staleness / summarize` 已就位。本包只换它背后的数。
2. **功能仍相似正交**：仍是 `never / stale / active` 三态判定，`summarize()` 契约不变。上游自带的
   侧栏页（会话视图 / 全局面板 / SVG 趋势图 / 1/3/7/30 天筛选）**一律不挂**——挂上去就是「用量面板第 N 家」。
3. **底层多调了更优质实现**（本轮最硬的一条）：
   ```
   $ grep -rn "recordUse" packages/ scripts/ tests/ | grep -v packages/radar/
   packages/dsh-zhiyun-page-plugins/src/usage.js:53  ← 定义

   ```

   `count: 0`，**线上结论恒为「全部 never」**。这是一个**已经存在、但永远只会说「全都没用过」的面板**。
   上游有：会话日志回放（`session.jsonl` / `.zstd`）+ 实时订阅 `tool/call` + 按大小/mtime 增量缓存 +
   已删除技能标记 + **重放未完成时不把空快照当成 0**（恰好是本仓最缺的那条「别把未知当零」）。

**成本（评审必须面对）**：上游 `private: true`，**不在公共 npm**，只能 git / 本地 link；

## 4 · 本轮「值得单独摘出的一点」

**`dsh-radar-activity-heatmap` 的判据③（底层多调了更优质实现）现在可以补上了。**
该骨架 2026-10-24 生成时的定性是「全新（补缺视图），**非强化式集成**」，理由是
`grep -rniE "heatmap|热力|streak|打卡|contribution"` = 0 命中 —— 即「本仓无被替换的底层」。

**本轮发现这条理由不完整**：本仓确实**没有**热力图，但**有**一份「使用计数账本」（`usage.js`），
而这正是热力图的输入。问题不在于「没有可替换的底层」，而在于**那个底层的数据源是空的**。
所以同一条「强化」路径对本轮 🟢 项成立（上游给的是**计数**，不是图），
而对热力图骨架**仍不成立**（上游要给的是**作图**）。**结论：热力图骨架定性不变，维持「全新」。**
