## 3. 本轮实质发现：本仓的「重复」引擎是对的，入口与撤销是错的

### 3.1 F-1 · 引擎支持 `every: 2`，界面永远传 1（实跑）

```text
advanceBy('2026-10-25T15:59:00.000Z', { every: 2, unit: 'week', anchor: 'due' })
→ 2026-11-08T15:59:00.000Z     ✅ 正确（+14 天）
```

但 `client.jsx:1482` 是**字面量** `{ every: 1, unit: repeatUnit, anchor: repeatAnchor }`，
下拉里只有 `day / week / month` 三档（`client.jsx:1604-1610`）。
`local.js:63-64` 的注释写着目标是「每天 / 每周 / **每两周（某些实验）** / 每月」，`normalizeRepeat` 也校验了 `1..12`。
→ **目标写了、校验了、算对了，就是没接上**。修法：`client.jsx` 一处，加一档间隔选择。

### 3.2 F-2 · 撤销勾选不收回副本（实跑，本轮最重要）

```text
勾（10-25）      → 列表：原条目(done) + 下一次 11-01
取消勾（10-25）  → 列表：原条目(未完成) + 下一次 11-01   ← 那条没被收回
再勾（10-25）    → 列表：原条目(done) + 11-01 + 又一条 11-01（id 不同，都未完成）
```

- `setDone()` 的注释（`local.js:371`）确实写了「取消勾选不该生成下一次」，**这句话本身没错**；
  错的是它只保证「不**再**生成」，没保证「**收回上一次生成的**」。
- `tests/planning-repeat.test.mjs` **31/31 全绿**（本轮实跑），因为单测断言的是 `next === null`，
  而缺陷发生在**返回值被 `LocalStore.setDone()` push 进 items、又被 `client.jsx:494` 插进列表之后**。
  → **「单测绿」与「用户看到的对」之间隔着一层消费方**，这是本轮最可复用的一条教训。
- 根因不是算法，是**缺字段**：本仓条目没有「这条副本是谁生的」与「这一天的副本已经生过没有」。
  实跑确认生成的副本上 `originId` 为 `undefined`（该字段根本不存在）→ 撤销时**没有任何依据**找回那一条。
- 上游的 `materialized` + `originTaskId` + `alignSeries` 正好就是这两个概念（R8），这是判 🟢 的主证据。

### 3.3 F-3 · 「跳过假期」不能照搬上游（实跑 R2 / R6）

```text
R2  2027-01-04..02-15 每周一 + skipHolidays:true → 七个周一全部生成（学校已放假）
R6  2026-10-10（周六，法定补班日）→ isWeekend=true → 被跳过
```

上游的「假日」= 周末 **OR** 一张写死的 `PUBLIC_HOLIDAYS`（2025 官方 + 2026 预计）。
→ 本仓只借它的**结构**（假日判定与推进解耦），**内容**必须自建（用户自填起止日期）。

### 3.4 「今天」页不看重复，但这是对的

`grep repeat packages/dsh-zhiyun-page-today/src` → **0 命中**。一度想记成缺口，但读完 `due.js:39` 后撤回：
`collectDue()` 只挑「今天到期且未勾」的条目，重复任务在**被勾掉之前**本来就在列表里；
真正缺的是「跳过假期」后的**下一次日期**，那是 F-3，不是这一处。**不把设计写成缺陷。**

## 7. 方法论增量（供后续轮次复用）

1. **`radar-rotation.mjs` 的第二个缺陷：它以为「今天跑过 C、B」**。脚本只读 `group_runs` 的**累计值**，
   不知道「今天」C 已跑两次（r60/r65）、A 已跑两次（r61/r62）、B 已跑两次（r63/r64）。
   → 它的「同日判据」实质是**不可信**的。这是 L-1（UTC 取日）之外**独立**的第二处。建议改为从
   `rotation-state.md` 的**流水表**里按日期过滤（表格是 append-only，可解析）。
2. **「单测全绿」≠「用户看到的对」**（F-2）。本轮 31/31 全绿而缺陷真实存在，因为断言止于函数返回值。
   → 建议：凡「函数返回一个将被消费的对象」（`next` / `recalled` / `admitted`），单测必须再走一遍**消费方**。
   与 r62（`dedupe` 有单测但生产零调用）、r37（`recordAttempt` 有测试无调用方）同族，但这次更隐蔽：**调用了、测了、还是错**。
3. **「npm 上有同名包」≠「这个仓库发布了」**（第三次记录，形态更新）：
   `XiaoWind/dsh-cron` 的 npm `dsh-cron@0.1.0` 是**别人的** cron 解析库（`repository` 为空、description 完全不同）。
   → 锁版前必须核 `repository.url` 指向本仓库（r57 记过 `dsh-zotero` 撞名，本轮是**同名但不同物**）。
4. **A 类的第四道门（宿主窗口）本轮一次就过**：上游 README 主动声明 `0.2.0-rc.2`，与本仓 `preferredHostVersion` 一致。
   → 「README 里写清目标宿主版本」应作为 A 类的**加分项**记入 registry 备注，便于后续筛选。
5. **★ 高 ≠ 可接（第三次）**：本轮 ★96 的 `dsh-tool-todo-plus` 因 NOASSERTION 待核、★6 的 `todo-tree` 因同域判 🔵，
   而唯一 🟢 是 **★1**。判据始终是「有没有本仓没有的口径」。
6. **「复制宿主页面再打补丁」要单列为一条排除理由**：`dsh-schedule-tab` 的做法（pinned snapshot + row-actions patch）
   在 DSH 生态里不罕见，它技术上能跑，但与本仓「不搬运上游源码」正面冲突。→ 建议写进 skill 的硬边界清单。
7. **读码找到的断点，其价值高于候选**：本轮 10 次搜索只产生 1 个 🟢，而 F-1/F-2/F-3 三条（零依赖、可当场修）全部来自读码。
   与 r53/r54/r55/r57 同构，已是**第五次** —— 建议把「先读码找断环」定为 A 组派生轴的**默认起点**，而不是可选步骤。
