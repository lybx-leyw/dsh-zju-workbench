### 3.1 · 🟢 `bertholomus/dsh-public-plugins`（唯一实质命中）

**形态**：monorepo，`plugins/` 下 16 个子插件（`calendar`、`notifications`、`coordinator`、
`decisions`、`recall`、`wallpaper`、`discord`、`agent-terminals` 等），每个子包自带
`dsh.bundle.patch` **＋** `dsh.client`（platform `web`），即**完整原生 DSH 插件包**。

**为什么不是「重复且无增益」**：整仓接进来会与本仓冲突（见 §3.2），
但**子插件 `notifications` 单独看**恰好命中本仓一个可实证的缺口：

- 本仓 `dsh-zhiyun-page-planning/src/time.js:113` 明写「只统计**没做**的条目 ——
  勾掉的已完成内容不该进任何提醒」，`ticks.js` 还把「**不需要再被提醒了**」做成了
  持久化本机标记 → **本仓有「到期判定」，且很认真**；
- 但全仓 `src/` + `packages/`（排除 radar）实测 `new Notification` / `requestPermission`
  / `showNotification` **0 处** → **提醒只在用户自己打开「今日」页时存在**；
- 上游 `notifications` 提供的正是这一段：发送器降级链
  （`desktopRuntime` → 桌面窗口 Web Notifications → 浏览器标签页）、无窗可发时**留盘**、
  重启**不丢不重**——这是另一个产品级工作量，本仓不应自造。

**强化式集成三条判据**：① 仍是同一个面板（不新增页面 / 设置分组）✅；
② 功能仍相似正交（通知不参与判定「做什么」「哪件过期」）✅；
③ 底层多调了更优质实现（「零送达」→ 成熟桌面通知栈）✅。→ **成立，出骨架。**

**只挂宿主半边**：上游 `dsh.client.inject` 带 `@deepseek-ai/dsh-client-ui-settings` 等
一整组 UI 包，会**自己接管 settings 的一个分组**，与本仓「今日」页的布局主张冲突。
同一条判断在 `dsh-radar-market`（`dshmarket`）与 `dsh-zhiyun-host-paper` 已各写过一遍，
本轮是第三次 —— 结论一致：**挂宿主、UI 自写**。

**⚠ 阻塞项（必须点名）**：`registry.npmjs.org/dsh-plugin-notifications` → **404，上游未发版**。
骨架 `package.json` 已按 `0.1.0` 锁版（与子包 `package.json` 的 `version` 一致），但
**从哪拿包**必须先解决（等发版 / 锁 git 引用 + 构建），否则骨架不可运行。
这一点已写进 `README.md`「接入前必须先做的事」第 2 条与 `src/index.js` 的 TODO 2。
