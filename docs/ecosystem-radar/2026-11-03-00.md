| 学生场景 | **CC98 资料检索 / 课程资料** |
| **与现有功能** | **重复且可强化** ✅ |
| 分级 | 🟢 |
| 骨架 | ✅ `dsh-radar-cc98-material-search` |

**为什么是「可强化」而不是「全新」或「无增益」**——三条同时成立：

1. **仍是同一个面板**：强化的是 CC98 搜索面板（`dsh-zhiyun-source-cc98` 的 `cc98.search`），不新增页面；
2. **功能仍相似正交**：都是「按关键词列出 CC98 帖子」，不重复实现搜索本身；
3. **底层多调了更优质实现**：在既有标题匹配之上，多出**分拣 + 多楼层附件发现**两层，
   这是本仓**现在完全没有**的一步。

**本仓现状（已核对源码）**：`packages/dsh-zhiyun-source-cc98/src/index.js` 的
`METHODS` 里 `search` 直通 `GET /topic/search`，**只要标题命中就返回**，没有结果分拣，
也没有附件抽取。上游 README 的实测结论直击这个缺口：

> 实测**10 条里只有 1 条真有附件**；而且真正的资料帖标题往往不含课程名
> （叫「XX 资源楼」「XX 课程总结」），关键词搜索根本捞不到。

**两条值得直接吸收的实测结论**：

- **附件是 Markdown 链接**，不是 UBB 占位符：`[显示名](https://file.cc98.org/v4-upload/…/x.pdf)`。
  上游实测 24 帖 / 105 楼里 `[upload=…]` 出现 **0 次**。裸 URL 正则会吃掉结尾 `)`，必须先按 Markdown 结构切。
- **成本设计**：一级只取 floor 1 判有无附件，只有判定的才进二级抓全文 —— 20 条通常仅 2~5 条打第二轮。
  这个设计**必须保留**，否则 20 条 × 每帖全文会把接口打爆。

**下一步**：评审骨架 → 决定落点（倾向在 `source-cc98` 新增只读方法 `cc98.materialSearch`，
而非新建独立源包）→ 只提取纯函数，不引入 `chrome.*`。
