## 2. 读码结论（这是本轮的核心，先于候选）

### 2.1 纠错：第四十四轮的 R-2 在当前代码上**不成立**

第四十四轮（2026-10-21）记录 R-2「复载时丢弃作答记录」，依据是 `openQuizStore()` 只 `loadItems`、
不喂 `attempts`。**这条结论今天复现不出来**：

```js
// packages/dsh-zhiyun-study-core/src/workbench.js:375-380（当前代码）
openQuizStore(stored) {
  const store = createQuizStore();
  const loaded = store.loadItems(Array.isArray(stored?.quiz?.items) ? stored.quiz.items : []);
  if (Array.isArray(stored?.quiz?.attempts)) store.loadAttempts(stored.quiz.attempts);   // ← 这行是喂了
  return { store, loaded };
}
```

按这段代码**逐行复刻**并跑一轮「出题 → 采纳 → 三次作答 → 落库 → 再采纳另一题」：

| 步骤 | `attempts` 条数 |
| --- | --- |
| ① 落库那一刻 | **3** |
| ② 走一次 `changeQuiz`（采纳第二题）后再落库 | **3**（未丢） |
| ③ 随后 `masteryOf` | `近 3 次都错（共做过 3 题，错 3 题）` ✅ |

`git log -L 373,380` 显示该段自 `a66bcda`（2026-10-11「把出题和节笔记接到学习页」）起**就是这个样子**，
不是后来修的。**结论：R-2 应撤回**。它当时是在 `store` 层单独跑「`loadItems` → `snapshot`」推演出来的，
漏掉了 `openQuizStore` 里那行 `loadAttempts`。**这是「推演式缺陷报告」的风险样本**：
报告若只跑一半代码，就会把「没写全」误报成「写错了」。

> 同时确认 R-2 附带的那条「`opened.loaded.notes` 取到 `undefined`」也不成立：
> `loadItems` 返回 `{ loaded, notes }`（`store.js:736`），`outside` 取的是 `opened.loaded.notes` —— 是 `{...}.notes`，能取到。

### 2.2 新发现：归因的三个消费方，**全仓零调用**（本轮最重要的一条）

```
$ grep -rln "attributeByPoint\|masteryByPoint\|masteryOf" --include=*.js --include=*.jsx .
./packages/dsh-zhiyun-quiz/src/store.js      ← 只有定义
```

`store.js:632/678/701` 三个方法（错题归因、单点掌握度、批量掌握度，含「近 3 次都错」这类规则）
**没有任何调用方**，也没有任何测试。它们是第三十七轮 F-1「`recordAttempt` 无调用方」的**下游同胞**：
即使明天把作答接上，**归因结果也没有任何出口**。

### 2.3 就算被调用，现在也会**静默输出零**

这是本轮最有价值的一条，因为它决定了候选库能不能接。实测三组（脚本见 §7）：

| 场景 | 输入 | 实际输出 | 应该输出 |
| --- | --- | --- | --- |
| **A** 题还在，同一知识点作答 3 次 | `pointIdsOf → ['kp-1']` | `{kp-1: {attemptCount:3, wrongCount:3}}` | 同左 ✅ |
| **B** 题被删（`store.delete`），作答记录仍在 | 同上 | **`attemptCount: 0`** → `数据不足（做过 0 题，少于 3 题）`；`attempts` 仍有 1 条 | 应保留归因或**明示**「题已删」 |
| **C** 只有作答、没有题（换设备 / 题只在别处出过） | `attempts=1`，`items=[]` | `attributeByPoint()` 返回 **`{}`**，`masteryOf()` 返回 `数据不足（做过 0 题）` | 至少应能说「有 1 条作答但我归不了因」 |

根因是一行 `continue`：

```js
// store.js:685-686（masteryOf 与 attributeByPoint 同构）
const q = byId(a.quizId);
if (q === null) continue;        // ← 作答还在，但题没了 → 这条作答被静默丢弃
```

`store.js` 的注释说「明确跳过（不进任何知识点），**不猜**」—— 这个取向本身是对的
（不猜是对的），但**「跳过」被实现成了「静默归零」**：调用方拿到的是 `数据不足`，
而不是「有 N 条作答因题已删除而无法归因」。这与本仓自己写下的「**不许静默失败**」直接冲突。
**修法是一条返回字段（`unattributed: N`），不需要任何新库。**

### 2.4 归因的输入其实**早就断了**：`pointIds` 到不了题上

`generate.js` 把 `m.pointIds` 喂进出题请求体（`buildRewritePrompt` / `buildGenerationPrompt`），
`makeSourceBlock` 也收 `pointIds`（`model.js:263`）—— 但**落成的题不带**：

```js
$ node -e "… makeItem({…, pointIds:['kp-1']}) …"
makeItem 收 pointIds 吗: false
itemToJson 前 pointIds: (无)
```

`makeItem`（`model.js:381-403`）参数表里**没有** `pointIds`，`itemToJson` 也不序列化它；
`workbench.js:433` 构造 `materials` 时同样没填（`stored.blocks` 只有 `tag.summary/facets`）。

也就是说：`pointIdsOf(q)` 这个回调在真实数据上**永远只能返回空数组**，
归因、掌握度、「近 3 次都错」**全部恒为空**。**唯一的现实替代口径是 `blockIndex`**
（唯一非空锚点）—— 而 `blockIndex` 是「块」不是「知识点」，粒度更粗，
且上面 §2.3-B 的删题问题在块口径下**一模一样**（实测同样归零）。

> **这一条改变了本轮候选的定位**：接一个更聪明的模型（BKT/IRT）之前，
> 必须先让 `pointIds` 能落到题上、并让三个消费方有调用者。否则就是把一个
> 精确模型接到一根**断掉的线上** —— 印证第四十四轮已给的结论「先闭环，再接调度」。

### 4.1 为什么 🟢 是 `MasteryTrace` 而不是 `irt-js`

两条都是 MIT、都能算「掌握度」。决定性差别是**能不能锁版、锁了能不能用**：

| 检查项 | `masterytrace-cli@0.1.3` | `irt-js@0.2.0` |
| --- | --- | --- |
| 许可证（npm 元数据 + `LICENSE` 实文） | MIT ✅ | MIT ✅ |
| 安装实测 | `npm i masterytrace-cli@0.1.3` → **added 3 packages in 2s** ✅ | 未装（2017 年产物，ES5 CJS） |
| 运行时依赖 | `zod@^4.6.5` + `commander@^13.1.0`（**zod 是重依赖**，见风险） | **0 依赖** |
| 导出面 | `BktModel` / `IrtModel` / `runForwardRecursion` / `runScoring` … 12 个具名导出 | 3 个：`estimateAbilityEAP` / `itemResponseFunction` / `information` |
| 能力 | **BKT**（含 `pInit/pTransit/pSlip/pGuess` 四参数 + 网格拟合）+ **2PL IRT** | 仅 EAP 能力估计，**不含参数估计**（`zeta` 要调用方自己给） |
| 活跃度 | npm 2026-09-25 / 仓库 push 2026-10-20 | npm **2017-09-15** / 仓库 **2019-07-15** |
| 实跑 | 见 §4.2 | 未实跑 |

`irt-js` 的 `ability.js` 里 `ABILITY_PRIOR` 是**模块加载时**就生成好的 101 点网格，
`estimateEAP(answers, zeta)` 要求调用方先把题目参数（`zeta`）算好 —— 而本仓一道题的作答
可能只有 1–3 次，**根本估不出题目参数**。所以它「能算能力」但在本仓的数据量下**算不出有意义的值**。

### 4.2 实跑证据（BKT，3 次「忘了」）

```js
// 输入：同一知识点 3 次 selfRecall='again'
const events = [false, false, false].map((c, i) => ({
  learnerId: 'l1', skillId: 'kp-1', correct: c, timestamp: `2026-10-${10+i}T08:00:00Z`,
}));
new BktModel().fit(events).results[0]
// → params: { pInit: 0.4, pTransit: 0.3, pSlip: 0.1, pGuess: 0.2 }
// → posteriorHistory: 0.077 → 0.064 → 0.062
// → finalMastery: 0.062
```

对照本仓现有口径：`masteryLabel` 只能说「近 3 次都错（共做过 3 题，错 3 题）」——**定性、无趋势**。
BKT 给出的 0.062 是**同一个知识点的连续量**，能支撑「先复习哪几个」。这正是「底层多调了更优质实现」。

### 4.3 事件 schema 能不能承接本仓的作答

```ts
// masterytrace-cli dist/core/event-schema.d.ts
ResponseEventSchema = { learnerId: string, skillId: string, correct: boolean, timestamp: string }
```

四字段，本仓 `makeAttempt` 都能映射（`learnerId ← accountId`、`skillId ← pointIds[0]`、
`correct ← !countsAsWrong`、`timestamp ← at`）。**但两个前提必须写进骨架的 TODO-0**：

1. **`skillId` 必须真有值** —— 现在 `pointIds` 到不了题上（§2.4）→ 映射出来全是空串；
2. **一次作答只算一个技能** —— 本仓 `attributeByPoint` 明确支持「一道题挂多个知识点，每个都单独计数」，
   而 BKT 的输入是「一条事件 = 一个技能」。一题多点的场景需要**拆成多条事件**
   （拆是对的做法，但会让 `responseCount` 与真实作答次数不等，**必须在 UI 上说清**）。
