## 1. 本轮结论

**插件页的「叶」是这张图唯一允许你动手的那一格；而它对「上游提供者」的处理，会让一个真正在等宿主服务的包显示成「不依赖任何东西」。**

今天没有先找「哪个插件能加功能」，而是沿着 r78 §4 留下的那个问题往下：
r78 判定 `gating-hub` 为 🟡 的理由是「它要和本仓插件页**同时写 profile**」。那么，
**插件页到底凭什么说某个包「可以取消」？** 顺着这条线读 `page-plugins/src/runtime.js` 的 `buildView`，
在沙箱里用真输入实跑（§3），得到三条：

| 问题 | 现象（实跑） | 后果 |
| --- | --- | --- |
| **F-1** 旧骨架 `dsh-radar-plugin-graph` 的 `inject: ['slots']` | 插槽图的依赖方向是**外壳 ← 页面**（页面 `dependents`=0、外壳 `dependents`=1），页面这一侧**不 inject 任何服务** | 本包要等的是「页面已加载」，而 **`slots` 不是一个页面会提供的服务** → 这个 `inject` **等不到任何东西**，包会一直 pending 或根本不该等 |
| **F-3** 服务由**上游包**提供时 | `dsh-zhiyun-core-notes` inject `hostOffice`、提供者是 `@deepseek-ai/dsh-host-office` → `deps=[]`、`leaf=true`、`cancellable=true`、`waiting=[]` | 页面文案写「**不依赖本工作台的任何其他包**」，开关**可点**；而它其实在等宿主服务 |
| **F-4** 环里的层序违例 | `a↔b` 两条边都在图里、环也认出来了，但 `layerViolations` **只报 1 条**（`a→b`） | 页面上一句写「环内无法定先后」，下一栏却只按层序报一边，读者会以为另一边顺序没问题 |

一句话：**这不是「缺一个插件」，是「本仓这张图有两处口径没对齐」——上游生态再成熟也修不了它。**

### 2.1 为什么本轮没有 🟢

两个 🟡 的真实增量都成立，但都卡在**同一处权责问题**上（与 r78 的 `gating-hub` 同族）：

### F-1 · 旧骨架 `dsh-radar-plugin-graph` 的 `inject: ['slots']` 等的是不存在的服务（**已改**）

骨架 r73 版写的是：

```js
export const inject = ['slots'];
// 注释：`dsh-zhiyun-page-plugins` 是这张图的**消费者**……它停用时本包无事可做
```

实跑插槽边（`a` 填 `b` 声明的插槽）：

```
order         [ 'dsh-zhiyun-b', 'dsh-zhiyun-a' ]   ← b(外壳) 在先
dsh-zhiyun-b  deps []  dependents ['dsh-zhiyun-a']  ← 外壳被页面依赖
dsh-zhiyun-a  deps ['dsh-zhiyun-b']  dependents []  ← 页面不依赖任何东西
```

也就是说：**外壳依赖页面，页面不提供 `slots` 服务**。页面用 `ctx.slots.inject('<插槽名>', …)`
只是**调用**外壳声明的插槽，并不会因此成为 `slots` 这个 Cordis 服务的提供者。
所以 `inject: ['slots']` **等不到「页面已加载」**——这个前提在注释里被写反了。

**已改**（`packages/dsh-radar-plugin-graph/src/index.js`）：
`inject = []`，并把触发点移进新增的 **TODO-5**，推荐方案是「由 `page-plugins/src/host.js`
在返回 `graph` 前调一次纯函数」——那样本包**根本不需要是插件**。README 顶部同步标注了这处修正。

> 这属于「**骨架自己的接线缺陷**」，不是上游的问题；它待在 `packages/` 里没人启动，
> 所以从未在真机上暴露 —— 正是这类「不跑就永远不报错」的占位代码最需要被复核。

### F-3 · 上游提供者被静默丢弃 → 「叶」与页面文案同时说反

```js
const provider = serviceProviders.get(service);
if (provider !== undefined && provider !== row.name) addEdge(row.name, provider);
// addEdge 第一行：if (from === to || !inScope.has(from) || !inScope.has(to)) return;
```

提供者 `@deepseek-ai/dsh-host-office` 不在 `inScope`（只收 `dsh-zhiyun-` 前缀）→ 这条边**被丢弃**。
但 `unresolved` 只按「`service in fiber.store`」判，服务是**已解析**的，于是 `waiting` 为空。

实跑（`dsh-zhiyun-core-notes` inject `hostOffice`，提供者为上游包）：

```
waiting=[]  deps=[]  leaf=true  cancellable=true
```

页面会渲染成：`不依赖本工作台的任何其他包` + 「叶」徽标 + **开关可点**。
而它其实依赖宿主的 office 服务 —— 取消它会 pending。**图说得越肯定，错得越不含糊。**

### F-4 · 环里只报一条层序违例（`Set` 插入顺序决定报哪条）

实跑 `a↔b`（profile 层序 `a` 在前）：

```
cycles          [['dsh-zhiyun-a','dsh-zhiyun-b']]      ← 环被认出来了
edges           a→b, b→a                                ← 两条边都在图里
layerViolations [{dependent:'a', dependency:'b'}]       ← 只有 1 条
```

`layerIndex(b)=1 > layerIndex(a)=0`，所以 `b→a` 按定义不算「依赖排在消费者之后」——
**这一条不是 bug，是定义**。真正的问题是**页面把两件事并排展示**：
上面写「环内无法定先后」，下面这一栏却按层序只报一边，读者会得出「另一边顺序没问题」的结论。
（同一份输入若边按 `b→a` 先插入，报出的会是另一条 —— 已验证：单边 `a→b` 时报 1 条、环里也只报 1 条。）
