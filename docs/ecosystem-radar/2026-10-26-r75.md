## 1. 本轮结论

**「笔记」页的库内检索，现在只能搜文件名。补上正文命中的正确做法是接 `minisearch`，
但必须先解决三个陷阱（中文分词、过度切分、版本与既有骨架冲突）。**

| 判据 | 结论 |
| --- | --- |
| 现有实现 | `page-notes/src/client.jsx` `buildRows()`：过滤分支只做 `e.path.toLowerCase().includes(query)` |
| 数据其实在手边 | `tree` 每条已返回 `preview`（正文前 120 字）与 `chars`，**没被用于匹配** |
| 候选 | `lucaong/minisearch`，npm `minisearch@7.2.0`（MIT ✅，`dependencies: {}`） |
| 与现有功能关系 | **重复且可强化** —— 同一个过滤框，同一个「在库里找一篇」，底层多调了分词 / 加权 / 打分 |
| 是否可强化 | ✅ 三条判据全成立（同一面板 / 同一问题 / 底层更优） |
| 分级 | **🟡 需移植改造**（不是 🟢：中文分词必须外接，且需两层策略控制精度，§3） |
| 骨架 | `packages/dsh-radar-note-search`（锁 `minisearch@7.2.0`，只写适配点与 TODO，不写业务逻辑） |

### 1.1 为什么不给 🟢

🟢 意味着「装上去就能用」。本包**不满足**：

1. **默认分词对中文完全无效**（查「动量」→ 0 条），必须外接 `Intl.Segmenter`；
2. **外接后又过度切分**（「弹道学」→ `弹道|学`），会产生假阳性，`combineWith:'AND'` 兜不住，
   必须再加一层原文子串复核；
3. **正文从哪来没定**：`preview` 只有前 120 字（搜不到第 3 句），要全文就得改宿主半边加一条方法。

三条都是**改造**，不是配置。故 🟡。

## 2. 本仓实测校准（三条，全部可复现）

### N-1 · 笔记页过滤只匹配 `path`，正文零参与（**本轮的起点**）

`packages/dsh-zhiyun-page-notes/src/client.jsx` `buildRows()`：

```js
if (query !== '') {
  return entries
    .filter((e) => e.type !== 'folder' && `${e.path}`.toLowerCase().includes(query))
    ...
}
```

复刻该分支，喂三篇笔记（`path` / `preview`）实跑：

| 查询 | 现实现命中 | 正文里其实有 |
| --- | --- | --- |
| 动量 | 1（`课程/动量守恒定律`） | 1 |
| 守恒 | 1 | **3** |
| 定律 | 1 | **3** |
| **碰撞** | **0** | **1**（`课程/动量守恒定律` 正文首句就是「碰撞前后…」） |

> 「碰撞」是这篇笔记最自然的搜法，现实现返回**空**，并且不确定时说「没有匹配的笔记」。

### N-2 · `minisearch` 默认分词对中文无效；接分词后过度切分需要第二层

两种分词，同一批文档：

| 查询 | 默认分词 | `Intl.Segmenter('zh')` | 原文复核后 |
| --- | --- | --- | --- |
| 动量 | **0** | 3 | 3 |
| 守恒 | **0** | 3 | 3 |
| 碰撞 | **0** | 1 ✅ | 1 ✅ |
| 注意力 | **0** | 1 | 1 |
| Attention | 1 | 1 | 1 |

过度切分的假阳性（文档 x=`弹道学基础`、y=`弹道导弹的学理解释`）：

```
分词「弹道学」→ 弹道|学
查「弹道学」      → [x, y]      ← y 是错的
combineWith:'AND' → [x, y]      ← 兜不住（y 的 terms 是 ['弹道','学理']）
加原文子串复核     → [x]  ✅
```

> **结论**：只做「分词召回」会假阳性，只做「原文 includes」就是现在的实现。
> **两层同时存在**才是正解 —— 召回求全、复核求精。这条已写进骨架 TODO-4。

### N-3 · 双链解析**不需要**外部库（负面结论）

本仓 `createResolver()` 的三级解析（精确路径 → 同目录 → 全库唯一 basename）与
`renameLinks()` 的三形态改写（`[[名]]` / `[[名|别名]]` / `[[名#锚点]]`），在库规模
「几千篇」这个量级上**已经是合理实现**。本轮搜到的双链解析仓库最高 ★36（且是 Go），
其余多为 ★0–7 的脚本 —— **没有一个值得锁版引入**。

> 因此**不建议**为双链解析引入任何依赖。这条与 §1 的候选**不矛盾**：
> 检索要的是「分词 + 打分」（本仓确实没有），解析要的是「路径规则」（本仓已有）。

### N-4 · 索引器算出的 `unresolved` / `orphans`，服务面有、页面没有

`dsh-zhiyun-core-vault/src/index/vault-index.js` 的 `buildIndex()` 产出 `unresolved`
（含 `missing` / `ambiguous` 两种 `reason`）与 `orphans`；`host.js` 也暴露了
`case 'unresolved'` / `case 'orphans'`，`describe` 里还统计了 `unresolvedCount` / `orphanCount`。
但 `page-notes/src/client.jsx` **一次都没调用**（`grep` 结果为空）。

> 这是**下一个**该做的功能（「笔记页显示断链与孤立笔记」），但它**不需要外部候选**，
> 纯属本仓 UI 缺口。本轮**不生成骨架**（骨架只给有上游的），仅在此登记为线索。
> 记在这里而不是悄悄放过：数据已算好、服务已暴露、就是没显示 —— 这种缺口最容易一直沉底。
