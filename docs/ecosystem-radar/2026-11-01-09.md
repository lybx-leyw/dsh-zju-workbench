**② PDF `ToUnicode` CMap 还原 —— 两个真实陷阱，实测都对**

| 陷阱 | 它怎么处理 | 我在沙箱的复现结果 |
| --- | --- | --- |
| **数组式 `bfrange`**：`<4E13> <4E15> [<5f20> <4e09> <674e>]` 里相邻的 `<hex> <hex> <hex>` 会被**误读成递增区间**（start=0x4E13 end=0x4E1A），把整个编码空间污染 | **先**处理数组式，并把它**替换成空格抹掉**，再跑递增式 | `array-form => 3 entries; 4E13=张 4E14=三 4E15=李` ✅ 未污染 |
| **递增式 `bfrange`**：`<0010> <0012> <674E>` | `String.fromCodePoint(dst + (code - start))` | `10=李 11=杏 12=材` ✅ |
| **多字体串字**：不同子集里相同编码指向不同汉字 | 按 `/Fx n Tf` **跟踪当前字体**，各读各的 `ToUnicode` | 代码注释明确写了这一点（`:readCMap` 由 `pdfToText` 逐字体调用） |

> 第 1 条是 PDF 文本抽取**最经典的错**：如果先跑递增式，`<4E13> <4E14>` 会被吃掉成区间，
> 结果是「看着能出字、其实大面积乱码」。它把这条坑写进了注释并逆序处理 —— 这是**实践经验**，
> 不是查文档能查到的。
