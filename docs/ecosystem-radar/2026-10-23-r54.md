```bash

grep -rniE "pomodoro|番茄|focus session" --include=*.js --include=*.jsx packages \
  | grep -v "packages/dsh-radar-"        # → 0 行

# ② 「时间」这件事在本仓只有两个函数
#    packages/dsh-zhiyun-page-planning/src/time.js
```

也就是说：**「规划」页知道「哪些事在逼近」，但不知道「今天还剩多少整块时间」**。

### 2.3 ⚠ 本轮真正值得看的东西：`xstate` 的两个「静默」边界

这一节的结论**比候选本身重要**，因为它决定了骨架能不能写出来。

| # | 实测 | 现象 | 后果 |
| --- | --- | --- | --- |
| **M3** | `after: ({ context }) => ({ [context.remain]: 'x' })` | 注入时钟**一次都没被调用**，actor 停在原状态，**不抛错、不告警** | 若照 v5 文档写「动态延时」，番茄钟**永远不会到点**，而页面上看起来「正在计时」 |
| **M4** | `getPersistedSnapshot()` 的 JSON | 只有 `{status, output, error, value, historyValue, context, children}`，**没有 deadline / 剩余量** | 刷新页面后上游把 `after` 当**从头开始**；「还剩多久」必须由本包自己存 |
| **M5** | 暂停 3 分钟再恢复 | 上游确实 `clearTimeout` 了定时器（M6 日志证明），但 `Date.now()` 照走 | 若沿用旧 `deadlineMs`，一次 3 分钟暂停会让「本该剩 10 分钟」变成**一恢复就到点** |

> M3 在 CJS `require` 与 ESM `import` 两种入口各复现一次，结论相同。
> 与 v5 文档「delay 可写成参数」的说法**不一致** —— 本轮**只能陈述现象，不给结论**：
> 可能是用法不对，也可能是 5.33.3 的回归。**评审若要采用，必须先答这一点**（见拍板项）。

## 4. 读码结论与方法论

### 图 · 「今天还剩多少时间」的数据链

```
课表节次  ── source-classroom.getSchedule() ──→ { startAt, endAt, courseTitle }(秒)
                │
                ├─ 今天页：projectAgenda()  →  { startMs, endMs }  ✅ 已有
                │
                └─ 规划页：focusOf(due)     →  五档计数            ✅ 已有
                            │
                            └─ 「今天还剩多少整块时间」            ❌ 缺（本轮要补的）
```

### 结论 1 · 「能力已在、出口没有」第五次复现，但这次**判别线要再切一刀**

r37 / r49 / r50 / r53 与本轮都是「数据已在、出口没有」。但本轮暴露一件事：

> r53 的判别线（「缺一行调用 → 补接线；缺一套规范实现 → 接依赖」）**没有覆盖第三种情况**：
> **缺的是一层保证**（「暂停期间时钟不被回溯」这种不变量）。
> 这种情况下，接进来的不是「工具函数」，而是一个**模型** ——
> 而模型的价值恰恰在于它的**边界**（M3/M4/M5），不在它的 API。

建议把判别线改成三条：
1. 缺一行调用 → 补接线（r37 / r49 / r50）；
2. 缺一套规范实现 → 接依赖（r53 iCalendar）；
3. **缺一层不变量 → 接模型，但必须先把模型的边界测出来**（本轮）。

### 结论 2 · 本篇最有价值的产出是 M3，而不是候选

M3（函数形式 `after` 静默失效）与 r53 的 R1/R2/R3、r51 的 R3、r50 的 F-1 是**同一类**：

> **「不报错的错」**。产物语法合法、页面看起来正常，只是结果是错的。

这已经是第五轮在同一类问题上撞见候选的内部缺陷。建议把这条写进 README 的强化式集成小节：
**凡引入「调度 / 序列化 / 时钟」类上游，验收必须包含「同一输入两次结果逐字相同」与「不变量在暂停 / 恢复 / 重载三种转移下守恒」两条断言。**

### 结论 3 · GitHub 上「专注计时」没有可用的底层，只有成品

8 次搜索、约 2,900 条命中，**没有一条**是「可锁版的 JS 专注计时库」：
- ★ 高的全是**成品应用**（`super-productivity` ★23k、`pomatez` ★4.9k）—— 有宿主、不可嵌；
- ★ 低的全是**单页 demo**（★≤398，多为 2018–2023 停更）；
- 计时底层（`performance.now` polyfill 那一类）停在 2014–2016，且**许可证多为 `null`**。

→ 与 r40「图算法要按 npm 包名找」、r41「中文分词按 npm 找」**第三次同构**：
**基础能力在 npm 上，GitHub 只用来发现新包。** 本轮真正该锁的是 `xstate`，不是任何一个 pomodoro 仓库。
