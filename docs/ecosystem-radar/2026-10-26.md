## 2. 本轮实质产出：本仓两个缺陷的修复 + 一次自我证伪

> **所有结论都来自 `import` 本仓模块实跑**（r69 的方法论教训：复算只能解释、不能下判断）。

### 2.1 F-1（已修）：每月 31 日的重复，夹到 2 月末之后**日号永久塌缩**

**症状**（实跑 `setDone` 连续 8 代）：`1/31 → 2/28 → 3/28 → 4/28 → 5/28 …`。
「每月最后一天交月报」的人，从 2 月起**每年只有 28 号那次是对的**，3/31、5/31、7/31 全丢。

**根因不是 `advanceBy`**。`advanceBy('2026-01-31', {every:1,unit:'month'})` 返回 `2026-02-28`
是**定义正确**的（2 月没有 31 号，夹到月末）。错的是**用法**：夹过的结果又被当成下一次的起点，
于是 2 月的 28 被当作"原日号"，3 月自然是 28。**错误的传播发生在调用链上，不在算子内。**

**修法**：`nextOccurrence` 对 `unit === 'month'` **直接算目标月**，日号取「原日号 vs 目标月长」的较小者，
不再"先夹再推"。

```js
const target = addMonths(head.getUTCFullYear(), head.getUTCMonth(), step);
const lastOfTarget = new Date(Date.UTC(target.y, target.m + 1, 0)).getUTCDate();
const day = Math.min(original, lastOfTarget);
```

**原日号从哪来**：`anchorDayNumber(base, item)` 优先读 `item.repeatDay`，否则用 `base` 的 UTC 日号。
`repeatDay` 是**新增字段**（`REPEAT_DAY_FIELD = 'repeatDay'`），只在「目标月装不下原日号」时才写入
（由 `carriedDay()` 判断），装得下就删掉 —— **不制造冗余字段**。

**实测**（`tests/planning-repeat-chain.test.mjs`，8 代）：`[28, 31, 30, 31, 30, 31, 31, 30]`，且每一代的
`repeatDay` 恒为 `31`。`advanceBy` 的旧行为被**专门写一条测试钉住**（「夹住是定义，不是 bug」），
防止下一轮有人把它当缺陷改掉。

### 2.2 F-2（已修）：勾完成 → 取消 → 再勾，同一截止日**两条副本**

r66 记过这个现象但没修。实跑确认：

1. 勾完成 → `setDone` 返回 `{item(已完成), next(下一期)}`，store 落盘 2 条；
2. 取消勾选 → **只把 item 改回未完成，`next` 没人收**；
3. 再勾一次 → 又生成一条 `next'`。

→ 同一 `due` 上出现 **2 条未完成副本**（`同 due 副本数 2`），用户看到的是"这条任务变成两条"。

**修法**：给每条派生条目加 `repeatFrom`（**恒指回第一代**，不是上一代 —— 否则链一长就收不全），
新增 `recallGenerated(items, current)` 在**同一次 `save()`** 里收回。store 与 client 同步接线，
`local-done` 路由返回 `recalled` 数组。

**判定顺序里有个坑**（本轮踩了 40 分钟）：取消勾选会清掉 `doneAt`，于是
**「勾错原始那条」和「勾错副本」留下的条目完全同形**，只能靠 `due` 区分。
第一版判据先比 `due` 再比 `id`，在「被撤的就是原始那条」这条**真实路径**上等于拿自己比自己，
`at > mine` 恒假 → 一条都收不到。改成**先判 `id`、`due` 相等的一律不收**后通过。

> **同 `due` 的两条副本是症状，不是可收的对象** —— 收掉它等于随机删用户一条待办。
> 所以「撤销副本本身」这一路径**返回空**，由「撤销原始条目」这条路径兜住。这是设计取舍，不是遗漏，
> 已写成一条断言把它钉住（`撤销「刚生成的那一条」：结构上无法判断，不收任何东西`）。

**实测**（store 端到端，不看返回值）：勾 → 撤 → 列表 **1 条**、`done=false`、**重开读盘仍是 1 条**。

### 2.3 F-3（**撤回**）：我以为的时区缺陷，站不住

第一版报告写「`datetime-local` 按浏览器本地时区解释，宿主不在东八区时『23:59 截止』会落到上海时间第二天」，
并造了 `due-shape.js` / `checkDueShape()` 去检。**两版都不成立**：

| 版本 | 判据 | 为什么错 |
| --- | --- | --- |
| v1 | 「上海 00:00 必须是 UTC 16:00，否则算漂移」 | **假阳**：把合法的上海 00:00 判成漂移；**假阴**：UTC 设备存的 23:59 反而通过 |
| v2 | 「墙钟分钟必须等于存储分钟」 | **零判别力**：实跑 `Asia/Shanghai` / `UTC` / `America/New_York` / `Europe/Berlin` / `Asia/Tokyo`，**全部存出 `:59`** |

→ `due-shape.js` **已删除**，只留一条测试把这个"为什么撤"钉住，免得下一轮又造一遍同一个检查器。

**真实结论**：存储的 ISO 里**没有任何信息**能反推设备时区。真要修只能在**写入侧**钉死 `+08:00`
（改 `datetime-local` 整条链路），那是产品决策，不是本轮能顺手做的。记为 **TODO-1**，不伪装成已完成。
