## 一、本轮判定轴：通知的「读到」与「送到」之间是断的

B 组前几轮把 cc98 的**读**（r131 标签语义）与**写**（r132 草稿同步）都做完了。本轮不再找第三个 cc98 客户端，换轴：
**本仓已经读到的东西，有多少从来没被送到用户眼前？**

### 1.1 一手实测（逐条 `grep`，非推断）

| 事实 | 位置 |
| --- | --- |
| cc98 有通知读侧，连 `/me/unread-count` 都查了 | `packages/dsh-zhiyun-source-cc98/src/reads.js:366` |
| 学在浙大有通知读侧 `notices({unread_only})` | `packages/dsh-zhiyun-source-xxt/src/reads.js:348` |
| **两处读侧在 `packages/` 内 0 个调用方** | `grep -rn "\.notifications("` / `"notices("` → 除定义处无命中 |
| 全仓**无**通知/收件箱面板 | `ls packages/ \| grep -i "notif\|inbox\|message\|notice"` → 空 |
| 全仓 `new Notification` / `requestPermission` **0 处**（与 r107 一致） | 同上 |
| 已有两个通知骨架都卡在 npm 404 | `zone-notify/src/upstream.js:81`、`notify-push/src/index.js:16` |

**结论**：缺口不是「再找一个通知库」—— 数据层已经有了，执行器骨架也有两个，
**但它们都不起版**。真正缺的是「**先判定此刻能推到哪一级**」这一层，它不需要任何上游包。

### 1.2 与「重复且无增益」的边界

若本包是「第三个通知执行器」→ 与 `zone-notify` / `notify-push` 重复且无增益（⛔）。
但它判的是**执行器之前的可用性**：三级降级链里，第三级（页面内角标）**零外部依赖**，
即使两个执行器永远起不来也能单独落地。这是「从 0 到 1」，不是并列替换 → 判据③成立。
