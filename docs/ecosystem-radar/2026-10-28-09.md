## 2 · 审计先行：`english` 字段 0 命中，**不是漏读，是有一条链断在前面**

### 2.1 复核结论（逐条可复现）

```bash
grep -rn '\.english\b' packages/ --include=*.js | grep -v node_modules
# → 仅 1 条命中，且是 radar 骨架自己的注释（dsh-radar-media-captions/src/index.js:30）
```

**断言成立：`english` 字段确实从未被任何消费端读取。** 生产端在：

```js
// packages/dsh-zhiyun-source-classroom/src/models.js:63-64
export function subtitle(row) {
  ...
  return { startMs, endMs, text: str(row.Text).trim(), english: str(row.TransText).trim() };
}
```

`TransText` 是浙云课堂 API 自带的中英对照列。也就是说：**数据从上游拿到了、映射到对象上了，
然后再没有下一个读者。** 这不是「字段名写错」，是**整条消费链缺一环**。

### 2.2 顺着往下读，发现更靠前的一处断链（本轮新发现）

`english` 没人读，很容易被当成「加个 UI 就行」。但读「字幕」页的渲染路径后，问题比这早一步：

| 层 | 位置 | 状态 |
| --- | --- | --- |
| 采集 | `source-classroom/src/models.js:63` `subtitle()` | ✅ 产出 `{startMs,endMs,text,english}` |
| 归档 | `core-classroom` → `core-study` 的课堂数据 | ⚠ **本轮未逐字段追到底**（见 §2.3 边界说明） |
| 渲染 | `page-study` 的「字幕」tab（`contentTabs` 第 5 项） | ⚠ 只消费 `text`，`english` 无读者 |
| 终稿 | `core-study/src/workbench.js` 的 `join("")` 拼接 | ⚠ **F-1 仍在**：相邻 cue 无分隔直接相连 |

结论：**`english` 是这条链上**最后一个**没人要的字段，但链上还有多处问题（F-1 无分隔拼接、
F-2 无标点恢复）。本轮只确认了「字段无读者」这一个事实，**没有**把「只要接一个双语渲染库就能修好」
当成结论 —— 因为 F-1/F-2 会让双语轨与中文轨**同时**是坏的。

### 2.3 边界说明（避免过度断言）

- `grep` 只覆盖 `packages/*/src/**/*.js`；`apps/` 与 `deploy/` 未纳入。若双语渲染写在 `apps/` 里，
  本结论不成立。**建议下轮补一次 `grep -rn 'TransText\|\.english' apps/ deploy/`**（本轮时间预算用于搜索）。
- 未实际拉取一堂课的真实 `subtitle` 响应，因此**未验证** `TransText` 在**所有**课程上都非空。
  上游字段存在 ≠ 每节课都有英文。这是**必须人工核验的前置条件**，不做假设。

### 2.4 与 10-20 第三十轮的关系

第三十轮（`dsh-radar-media-captions` 的出处）已把 F-3 列为「上游只补一半」。
本轮的增量是：**把「补齐 F-3」的先后顺序修正了** —— 先修 F-1（分隔）再上双语，
否则双语只是把「无分隔的中文」变成「无分隔的中文 + 无分隔的英文」。

### 3.1 关于 `rockbenben/subtitle-translator` 派不上用场的那部分

它的 `pipeline.ts`（91 KB）/ `registry.ts`（**245 KB**）是 27 家 LLM 供应商的适配矩阵 ——
**与 DSH 的模型层完全重复**：本仓已有 `core-llm-error` 的错误分类与降级，且 DSH 本身管模型调用。
若把这套接进来，就是 skill 明令禁止的「简单集成重复功能」。
**有价值且不重复的只有一件事**：它的 README 首句点名的那个设计 ——
> 「字幕翻译器在本地把时间轴剥离，**只把台词发给引擎**——时间线从物理上就碰不到」

对应到 `subtitle.ts` 里就是：`detectSubtitleFormat()` → `filterSubLines()`（记下每条可译内容的**物理行号**）
→ 翻译 → `assembleSubtitle()`（按行号**原位回填**）。
**这套「行号保位」的做法，正是本仓 F-1 / F-2 修复时该采用的结构**（先切分、再逐条处理、最后按原索引拼回）。
但这是**方法**，不是代码 —— 按「不搬运上游源码」，本轮**只记方法、不抄实现**。

## 5 · 结论

1. **本轮无 🟢，0 骨架。** 不是「没找到好项目」，是**这个方向的好项目都不是 JS 库**：
   `subtitle aligner`(109) / `bilingual subtitles`(422) 的前排几乎全是 Python 工具或独立 App。
   「字幕」在 JS 生态里**没有可锁版的底层库** —— 在册的 `media-captions` 是唯一一个，且已出过骨架。
2. **`subtitle-translator` ★1181 是一个「高星但不可用」的典型**：星数最高，核心价值最贴，
   但它**是 App 不是库**（无 `main`/`exports`）、核心文件 83 KB 单文件、只 1 个仓内依赖 → 移植即抄源码。
   建议：**以后遇到「高星 + 单一巨型源文件」先看 `package.json` 有无 `main`/`exports`**，
   没有就不必再读实现（与 r89 `dsh-synapse` 的「先看 `files` 字段」是同一类教训，**字段名不同、判据相同**）。
3. **`english` 字段的 0 命中，本轮从「注释里的一句话」变成了「可复现的审计结论」**，
   并**修正了修复顺序**：F-1 在前，F-3 在后。这比再记三个 🔵 有价值。
4. **方法沉淀**：**「窄词 total=1」三次复现**（第 5/6/9 次搜索）。
   文档说 total=0 才放宽；实测 **total=1~5 同样没有信息量**（剩下的是 ★0 新仓或非 JS）。
   建议把放宽门槛从「=0」改为「**< 5 且前排无 JS 库**」，并对放宽后「只会回到已扫过的宽词」
   的情形**显式放弃**（本轮即如此，非疏漏）。
