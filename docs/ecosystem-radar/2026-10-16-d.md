```text

```

`app/zjuauth.js` 头部注释完整写明了它对**智云 SSO 链路的逆向结论**（已逐行核对）：

```
casapi auth/login → cas/oauth2.0/authorize → cas/login(输账密)
→ POST(username + RSA(密码反转) + execution) → ticket
→ callbackAuthorize → tgmedia get-info?code=ST-xxx
→ 该响应 Set-Cookie: _token=<Yii签名>{... "eyJ...JWT..." } → 302 classroom
JWT 即藏在 _token cookie 里。
```

**这一段是本轮最有价值的发现，也是判它 🟢 的唯一理由**，逐条对照本仓现状：

| 本仓 `dsh-zhiyun-classroom/src/auth.js` 现状 | 上游 `zjuauth.js` 的做法 | 差异性质 |
| --- | --- | --- |
| `rsaEncrypt()` 明文字节 → hex → 整块 BigInt 幂 | `encryptPassword()` **先反转密码**、再**分块**、每块 `modpow` 后拼十六进制 | **算法同族但实现不同** —— 上游注释自称「已对真库逐字节验证」 |
| 手写 cookie 处理，散在 transport 里 | 独立 `CookieJar` 类，**含 `domain` / host-only / `path` 匹配** | 上游更完整 |
| 只有 CAS 单一路径 | 额外走 `casapi` → `oauth2.0/authorize` → `tgmedia get-info` | **登录链路不同**（本仓是 CAS 直连，上游是 OAuth2 授权码中转） |
| 只服务智云 | 同上（也服务智云），但**取 JWT 的落点不同**（`_token` cookie） | 同目标、不同抓手 |

⇒ **这是典型的「同一个面板 + 功能相似正交 + 底层多调了更优质实现」**。
两者都服务智云课堂，但**上游多了一条我们没走过的授权码链路，
且其 RSA 分块实现与 cookie jar 的成熟度高于本仓手写版**。

> **⚠ 三条必须人工拍板的前置问题（不拍板不得推进）**
>
