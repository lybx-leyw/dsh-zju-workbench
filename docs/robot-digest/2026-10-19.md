## F-005 · 规划页加载过慢（A 类，已实现）

### 一个前提：规划页是主干刚合进来的

上一轮日报里写「本仓库没有叫『规划』的页面」—— 那是**当时的**事实。主干在 10-18 合并了
**PR #22 `feat/planning-page`**，新增 `packages/dsh-zhiyun-page-planning/`。本轮 `fetch` 把它带了进来，
于是这条需求第一次有了可分析的对象。也说明：**判断"仓库里有没有某个东西"之前，先确认分支是不是最新的。**

### 定位过程

页面侧只用一次 `GET /_dsh/zhiyun-planning` 拿全部数据（`client.jsx` 的 `load()`），
所以慢的一定在宿主这边。宿主 `snapshot()` 一次要集齐四份东西：

```text
中转站条目  ← 用户自己在魔搭创空间部署的（HTTP，冷启动要几秒，超时 15s）
学在浙大待办 ← omni xzzd.todos   （校园网，走 CAS）
拼题A 题集   ← omni pta.problemSets（校园网，Cookie）
本地留存     ← 本地 JSON（不慢）
```

`snapshot()` 原本写成对象字面量里逐个 `await`：

```js
const snapshot = async () => ({
  entries: store.list(),
  remote: await sync(),          // 中转站
  todos:  await loadTodos(),     // 学在浙大 + 拼题A
  pta:    await ptaStatus(),     // 拼题A 配置状态
});
```

对象字面量的字段是**顺序求值**的，于是三个互不依赖的远程读取被串成了一条链：
**总耗时 = 三者之和**。而 `loadTodos()` 内部同样是先 `xzzd` 再 `pta`，两次校园网往返也是相加的。

这与用户那句「相比本项目其他服务明显过慢」完全对得上：**其他页面最多等一路远程，这一页要等四路。**

### 量化（注入固定延时，测改动前后）

| 场景 | 注入延时 | 改前实测 | 改后实测 | 理论下限 |
| --- | --- | --- | --- | --- |
| `snapshot()` 三路 | 3s / 2s / 1s | **6005 ms**（= 6s，串行） | **3002 ms**（= 3s，并行） | 3000 ms |
| `loadTodos()` 两路 | 1.5s / 1.2s | 2700 ms（串行） | **1500 ms**（并行） | 1500 ms |

脚本在沙箱临时目录（未进仓库），用注入的假 `fetchRemote` / 假 `omni` 计时，
延时的绝对值不重要，**"耗时是相加还是取最大"**这个结构才重要。

### 改动：只有并发，没有别的

`packages/dsh-zhiyun-page-planning/src/index.js` 两处：

1. `snapshot()` —— 三路改 `Promise.all`；
2. `loadTodos()` —— 学在浙大与拼题A 改 `Promise.all`，`finishPta()` 由"回填整个 result"
   改为"只返回 `pta` 那一栏"（并行时两路不能互相写同一个对象）。

**刻意没动的东西**（都是产品决策，不是我能单方面定的）：

- **没有去掉"每次打开页面都同步一次中转站"** —— 这是这一页既定的取数语义；
- **没有加缓存 / 分页 / 懒加载 / 缩短超时** —— 那些是策略取舍，各有代价，要人拍板；
- 没有碰 `client.jsx`、没有改协议、没有加依赖。

### 一个容易写错的点（记录在代码注释里）

`entries` 与 `config` **必须在并发之前取值**。改动前 `store.list()` 求值时同步还没发生，
页面看到的是"本次同步**前**的本地内容"，新增几条由 `remote.added` 单独报出。若放到并发之后再取，
新增条目会被算进 `entries`，两处就说成同一件事了。已单独验证：本地先有「旧条目」、
中转站新来「新条目甲/乙」时，`entries` 仍只有「旧条目」，`remote.added === 2`，
而本地留存已吸收两条新的（下次打开才可见）。

## F-004 · 中转站一键部署（B 类，已转请示）

用户要的是：无中转站时，能让 AI 拿着用户提供的魔搭 API + 本仓库的示例，替他搭一台。

**技术上确实可行** —— 魔搭有 Studio OpenAPI：`POST /openapi/v1/studios` 建创空间、
`POST /studios/{o}/{r}/deploy` 部署、`POST /studios/{o}/{r}/secrets` 灌密钥，另有 `ms` CLI
与 `modelscope_hub.HubApi`；统一用 `Authorization: Bearer $MODELSCOPE_API_KEY`。

但**要拍板的不是"能不能"，而是"做成什么样、凭据怎么走"**，所以按 B 类处理：

- 交付形态有三种合理取舍（文档指引 / 可执行脚本 / 工作台内引导 UI）；
- 用户的魔搭 Token 怎么交给 AI 或脚本、要不要落盘、如何确保不进仓库 —— 属安全取舍；
- 建完还要把 `deploy/relay-service/` 推上去（魔搭 Studio 代码走 git，默认分支 `master`），
  并写 `WRITEKEY` / `READKEY` 两个平台 Secret（**变量名不能有下划线**）—— 这一步是否也一并自动化；
- 引 `modelscope` SDK 还是标准库直连 HTTP，代价不同。

**机器人当前无法验证**：沙箱没有真实魔搭 Token，任何一条 OpenAPI 调用都跑不通，
写脚本等于交一份没验证过的东西，违反「不编造」红线。因此只调研、不实现。

已按格式追加进 `docs/robot-open-questions.md`（含三个候选方向与相关位置），状态保持 `open`。
