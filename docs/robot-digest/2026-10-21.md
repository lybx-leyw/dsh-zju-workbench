## 同步情况

沙箱是全新的（没有上一轮的本地仓库），所以本轮是**重新 clone**，不是沿用。

| 步骤 | 结果 |
| --- | --- |
| `git -c http.version=HTTP/1.1 clone` | **成功**，拿到全部远端分支（含 `robot`、`jzh`、`radar`） |
| `git fetch origin --prune` | **失败**：`Failed to connect to github.com port 443`，卡满约 133 秒 |
| `git ls-remote --heads origin robot` | **成功**，确认远端 `robot` 存在 |
| `git checkout -B robot origin/robot` | **成功**，HEAD = `e40516a` |
| `git merge --no-edit origin/main` | **Already up to date**（`robot` 已包含 `656a849`） |
| `ls-remote` 复核（写稿时） | **失败**：无返回，窗口关闭 |

**为什么 fetch 失败也不影响本轮**：`clone` 已经把完整 refs 带下来了（clone 本身就是一次全量拉取），
所以 `origin/main`、`origin/robot` 在 clone 完成那一刻就是最新的。`fetch` 在这里只是"再确认一次"，
失败了也拿不到比 clone 更新的东西。这与 10-19 那轮"fetch 一次成功"的情况不同，但结论一致：
**git 到 github.com 的连接是间歇性的，与命令本身无关**（10-19 已排除 HTTPS / IPv6 / 令牌权限）。

沿用 10-19 那条经验：**别在窗口关着的时候拿 push 去硬撞**（一次要卡 130+ 秒才失败），
先用几秒内能返回的小请求探路。本轮 push 前会先跑 `ls-remote`，返回了才推；
若多次探测都无返回，则本地提交保留、据实报告"未推送"。
