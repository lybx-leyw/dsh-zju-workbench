## 本轮的同步事故：clone 中断 + 浅层历史导致合并冲突

### 过程

1. `git -c http.version=HTTP/1.1 clone` 整包克隆，**两次失败**：
   第一次卡满约 133 秒后 `Failed to connect to github.com port 443`，
   第二次换成 `--depth 1` 后报 `GnuTLS recv error (-110)`。
   同一时间 `curl --http1.1` 访问 github.com 与 codeload 都是 **200**，说明**不是网络不通，
   是 git 的大 pack 传输走不通**。
2. 改用分步：`git init` → `git remote add` → `git fetch --depth 1 origin robot`。
   **一次成功**（约 2 秒），`git checkout -B robot origin/robot` 建立工作分支。
3. `git merge origin/main` **爆出大面积 `add/add` 冲突**（`scripts/test-host.mjs`、
   `tests/css-order.test.mjs`、`tests/profile.test.mjs` 等）。原因不是代码冲突：
   两侧都是 depth 1 的浅层快照，**历史被截断后互为 unrelated histories**，
   git 只能把同名文件当成"两边各自新建"。
4. 中止合并，`git fetch --depth=60 origin robot main` 加深历史后重新 merge ——
   **零冲突自动合并成功**，HEAD = `bb28c7f`。
5. 加深后确认 `origin/main` 确有 `robot` 未包含的新提交（PR #18、#19），本轮合并把它们正式带入分支。

### 结论与教训

- **`clone` 不可靠，`fetch --depth` 可靠**。这个沙箱对 GitHub 的**大传输**会中断，
  轻量请求正常（本轮 `ls-remote`、`fetch` 全通）。以后同步直接走
  「`init` + `fetch --depth`」，不要指望 `clone`。
- **浅层历史会让 `merge` 变成假冲突**。`--depth 1` 只够看代码，不够做合并；
  要合并主干就得先把历史加深到能找到共同祖先（本轮 depth 60 足够）。
  看到满屏 `add/add` 冲突先别去解，先怀疑深度。
- 10-17 那轮建议的「用 `git rev-parse --verify origin/robot` 代替 `ls-remote` 判分支存在」
  本轮**仍然适用**，且本轮没有再踩误重置的坑（先 `fetch`，本地已有 `origin/robot` 引用才 `-B`）。
- 指令文档里「所有 git 网络操作都必须加 `-c http.version=HTTP/1.1`」是对的，
  但**它解决不了大 pack 传输中断** —— 本轮全程带了这个选项，`clone` 照样失败。
  真正的解法是绕开 `clone`。
