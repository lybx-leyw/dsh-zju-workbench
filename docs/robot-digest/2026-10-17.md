## 本轮的事故：分支被误重置，已恢复

### 过程

1. `git clone` 失败：目标目录 `/workspace/dsh-zju-workbench` 已存在且非空 —— 是上一轮留下的仓库。
2. `git fetch --prune` 正常，取到 `origin/robot`（`e76940c`）与 `origin/main`（`0ed30db`）。
3. 判分支是否存在的 `git ls-remote` **未带 `-c http.version=HTTP/1.1`**，撞上沙箱到 GitHub 的
   HTTP/2 传输问题，**卡满约 134 秒后失败返回非零**。
4. 于是脚本走进 `else` 分支，执行 `git checkout -B robot origin/main` —— 本地 `robot` 被**强重置**
   到 `origin/main`，10-16 那轮因推送失败而滞留本地的 3 个提交（`bbad8c1`、`6a836d4`、`f81bf1a`）
   从分支上脱落。
5. 用 `git reflog` 定位到 `f81bf1a`，依次 `merge origin/robot` 与 `merge f81bf1a`，
   两次合并均无冲突，**历史完整恢复**，HEAD = `9555152`。

### 结论与教训

- **事故性质**：不是代码冲突、不是令牌问题，是**判存在的那一步没走 HTTP/1.1**导致的误判。
  指令文档里「所有 git 网络操作都必须加 `-c http.version=HTTP/1.1`」这句话是对的，
  但阶段 1 的示例命令里 `git ls-remote` **漏了这一个** —— 照抄示例就会踩。
- **判定分支存在与否，不要用 `ls-remote`**：`fetch` 之后本地已有 `origin/robot` 这个远端跟踪引用，
  直接 `git rev-parse --verify origin/robot` 即可，**零网络开销、不受抖动影响**。
- **`-B` 会强重置，丢历史是静默的**：以后同步若必须用 `-B`，重置前先确认
  本地没有未推送的提交（`git log origin/robot..robot`）。
- **已验证无实际损失**：恢复后 `git diff origin/main...HEAD` 只剩
  `docs/robot-digest/2026-10-16.md` 一个文件（138 行），
  即 10-16 那轮的全部本地独有内容，与 digest 记录一致。
