# 待开发者决策的问题

反馈机器人**做不了主**的问题记在这里 —— 判断依据是：策略不止一种合理取舍，或需求本身过宽，
或修它会越过「某一页自己的样式表/代码」这条边界。

每进来一条都**追加在末尾**，不覆盖历史。开发者拍板后，机器人的下一轮按结论执行。

---

## 2026-10-14 · F-003-a 提交按钮悬停时的可辨识度

- **诉求**：「提一条新需求」按钮悬停时，背景色与字体色太接近，看不清。
- **为何复杂/宽泛**：这个按钮的悬停色取外壳变量 `--zy-action-hover`，而外壳变量是**全工作台共用**的。
  实测（白字 `#fff`）：亮色主题常态 8.79:1、悬停 10.75:1（越悬停越清楚，没有问题）；
  暗色主题常态 6.39:1、悬停 `#2b70c3` 只有 **4.99:1** —— 仍过 AA 的 4.5:1，但比静止态掉了一大截，
  观感上就是「悬停后字发糊」。要在本页单独改，会跟工作台其他按钮的悬停语言不一致；
  要改外壳，就波及全部页面。
- **待开发者决策**：
  1. 只在本反馈页覆盖悬停色（代价：本页按钮与其他页面悬停方向相反 —— 全域暗色是「悬停变亮」，
     本页若要更清楚就得改成「变深」）；
  2. 改外壳的 `--zy-action-hover`（暗色下降低提亮幅度或改走加深，代价：全工作台按钮一起变）；
  3. 不动背景色，改用文字/描边做区分（代价：同样要在本页开特例）。
- **相关位置**：`packages/dsh-zhiyun-page-feedback/src/style.css` 的 `.zfb-submit:hover`；
  变量定义在 `packages/dsh-zhiyun-shell/src/style.css`（`--zy-action` / `--zy-action-hover`）。

## 2026-10-14 · F-003-b 「提新需求」与「追踪已有」两种模式形同虚设

- **诉求**：表单顶部的「提新需求 / 追踪已有」两个模式没有实质性区别。
- **为何复杂/宽泛**：现状下两者唯一的差别是「选追踪时多显示一行提示文案」和「发布后列表上多一个
  '追踪' 标签」，表单字段、校验规则、提交目标完全相同 —— 选哪个都不影响结果。要让它真有区别，
  等于要**重新定义「追踪」这个动作是什么**，这是产品层面的取舍，不是改几行 CSS。
- **待开发者决策**：
  1. 干脆合并成一个模式，去掉这组切换（最小改动；但也就放弃了「追踪」这个语义）；
  2. 让「追踪已有」真起作用：单独的目标编号输入（校验 `F-00X` 是否存在）、提交后不去建新条目，
     而是作为评论挂到那条需求下面（改动最大，需要动 `board.js` 的提交路径与服务端）；
  3. 保留两种模式，但把差别落到表单内容上（例如追踪模式必填「你要追踪哪一条」）。
- **相关位置**：`packages/dsh-zhiyun-page-feedback/src/client.jsx`（`EMPTY_FORM`、`form.kind`、
  `publish`、`zfb-choice`）；`packages/dsh-zhiyun-page-feedback/src/board.js`（`submitIssue`、
  `checkIssue`、`ISSUE_KINDS`）。

## 2026-10-15 · F-002-c 反馈卡片边界辨识度不足（**补录**）

> 补录说明：这两项是 2026-10-13 那一轮处理 F-002 时遗留的，当时只在评论串里向开发者提出，
> **漏登这份日志**。2026-10-15 这一轮核对数据时发现缺项，按原格式补齐；**代码未动**，
> 两项今日重新核算后的数据与当时的口径一致（见下）。

- **诉求**：反馈列表里每一张卡片的边界看不清，找不出条目之间的分界。
- **为何复杂/宽泛**：规范对非文本要素（分隔线、卡片边界）要求 **3:1**，实测远未达到 ——
  亮色主题边框 `--zy-line` `#e1e3e5` 对卡片底 `#fff` 只有 **1.29:1**、对页面底 `#f7f7f5` 只有 **1.20:1**；
  暗色主题 `#363b43` 对卡片底 `#22262b` 只有 **1.35:1**。而卡片底与页面底之差同样撑不起分界：
  亮色 `#fff` 对 `#f7f7f5` 是 **1.07:1**、暗色 `#22262b` 对 `#191c20` 是 **1.12:1**。
  也就是说**底色这条路走不通，边框是唯一线索，而这条线索是失效的**。要修就得动 `--zy-line`，
  它是外壳（shell）变量、全工作台共用 —— 越过「本页样式表」这条边界，不是机器人该单方面决定的。
- **待开发者决策**：
  1. 只在本反馈页用 `color-mix` 就地加深边框色（代价：本页卡片与其余页面卡片边界语言不一致）；
  2. 改外壳 `--zy-line`（收益最大，代价：全工作台所有分隔线/边框一起变，需全站回归）；
  3. 不动边框，改用「底色差 + 阴影」承担边界识别（代价：亮色主题底色可用余量极小，效果有限，
     且阴影会改变整页的视觉重量）。
- **相关位置**：`packages/dsh-zhiyun-page-feedback/src/style.css` 的 `.zfb-item`、`.zfb-thread`、
  `.zfb-comment`、`.zfb-tag`、`.zfb-kind`；变量定义在 `packages/dsh-zhiyun-shell/src/style.css`
  （`--zy-line` / `--zy-surface` / `--zy-bg`）。

## 2026-10-15 · F-002-d 字号未进「舒适阅读」区间（**补录**）

- **诉求**：同属 F-002「屏幕工效学」，指界面整体字号偏小、读起来费眼。
- **为何复杂/宽泛**：现状是**能看清但不够舒适** —— 辅助文字 11px、正文 12–12.5px、列表标题 13px
  都过了可辨下限（16′ ≈ 10.6px），但正文没到舒适阅读的 20′（≈13.2px）；而列表页是「一屏快扫很多条」
  的任务性质，标题按规范该按 24′（≈15.8px）算。再往上调就要**脱离外壳的基准字号**，本页会和其余
  页面观感不一致、一屏条目数也会下降 —— 这是取舍，不是单纯的技术问题。
  **另有一层口径上的不确定**：那些弧分值源自拉丁字母的 cap height，中文是方块字，直接套 cap height
  会低估约三成，规范本身没有给中文口径。所以不拿它当硬指标去改字号。
- **待开发者决策**：
  1. 本页整体上抬一档（辅助 11→12px、正文 12.5→13.5px、列表标题 13→15px）—— 最贴近规范，
     代价：脱离外壳基准字号，本页显得比其余页面大；
  2. 只抬列表标题（快扫任务按 24′ 算），其余保持不动 —— 折中，改动最小；
  3. 维持现状，先补一份**中文方块字**的视觉高度换算口径再定 —— 最稳，但本问题本期无解；
  4. 做「用户可调字号」（规范 ch07 支持用户可调参数）—— 体验最好，代价：要外壳先支持这套机制，
     属跨包改动。
- **相关位置**：`packages/dsh-zhiyun-page-feedback/src/style.css`（`.zfb-item` 标题、`.zfb-summary`
  摘要、`.zfb-meta` / `.zfb-field` / `.zfb-counter` 辅助文字、`.zfb-back`）；基准字号与排版变量在
  `packages/dsh-zhiyun-shell/src/style.css`。

## 2026-10-19 · F-004 中转站一键部署

- **诉求**：中转站要用户自己在魔搭创空间上建一台，门槛偏高。希望无中转站时，用户可以选择
  「让 AI 拿我提供的魔搭 API + 本仓库的示例，替我搭一个」，以此降低上手门槛。
- **为何复杂/宽泛**：**技术上可行**（魔搭确实有 Studio OpenAPI：`POST /openapi/v1/studios`
  建创空间、`POST /studios/{o}/{r}/deploy` 部署、`POST /studios/{o}/{r}/secrets` 灌密钥，
  另有 `ms` CLI 与 `modelscope_hub.HubApi`；均需 `Authorization: Bearer $MODELSCOPE_API_KEY`），
  但**要拍板的是形态与凭据处理，不是能不能做**：
  - 交付形态有多种合理取舍（文档指引 / 可执行脚本 / 工作台内引导 UI）；
  - 用户的魔搭 API Token 怎么交给 AI 或脚本、是否落盘、如何不进仓库 —— 属安全取舍；
  - 建完还要把 `deploy/relay-service/` 的代码推上去（魔搭 Studio 代码走 git，默认分支 `master`），
    并写入 `WRITEKEY` / `READKEY` 两个平台 Secret（**变量名不能有下划线**，见
    `deploy/relay-service/README.md`），这一步是否也一并自动化；
  - 引入新依赖（`modelscope` Python SDK）还是用标准库直连 HTTP，是两种不同代价。
  **机器人当前无法验证**：沙箱里没有真实的魔搭 API Token，任何一条 OpenAPI 调用都跑不通，
  写脚本等于交一份没验证过的东西 —— 违反「不编造」红线，所以只调研、不实现。
- **待开发者决策**：
  1. 先做**文档形态**：写一份「给 AI 的部署作业指导书」（步骤 + 可复制的 curl/git 命令 +
     密钥填写位置），用户把 API Token 给自己的 AI 照做 —— 零代码、零依赖、无需验证，代价最低；
  2. 做**脚本形态**（如 `scripts/deploy-relay.mjs`，标准库直连 OpenAPI，Token 只从环境变量读、
     不落盘）—— 体验最好，代价：新增一条可执行路径，需真 Token 联调后才能说可用；
  3. 在工作台「个人 → 设置 → 规划数据源」里加一个**引导入口** —— 与第 1/2 条叠加，
     属跨包 UI 改动，范围最大。
  另需定：免费档硬件名（现用 `platform/2v-cpu-8g-mem`）是否写死、创空间重名时怎么提示。
- **相关位置**：`deploy/relay-service/`（`server.py` / `Dockerfile` / `ms_deploy.json` / `README.md`）；
  对应文档 `docs/modelscope-as-cloud-server.md`（第 4 节「部署细节（照做版）」是现成的手工步骤）；
  消费端 `packages/dsh-zhiyun-page-planning/src/index.js`。
