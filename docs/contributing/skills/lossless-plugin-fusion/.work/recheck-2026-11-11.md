## 二、X 类：审批通过后请求发不出去（已修）

这一类与 `coverage-gaps.md` 的 X-1（`pta` 死链）同源：**代码看起来是好的**，
工具注册了、审批通了、错误文案还很有道理，只有真跑一次才知道发不出去。

### X-3 · `tyys` 的预约与取消**100% 不可用**

**根因**：`writes.js` 的 `execute()` 调的是 `client.request('POST', …)`，
而 `VenueClient.request()` → `request_()` 的第一道闸就是：

```js
if (FORBIDDEN_WRITES.has(endpoint)) {
  throw new TyysError('CONFIG', `「${endpoint}」是写操作（会改场馆上的预约记录），本数据源不提供：请在工具包里完成。`, …);
}
```

`/api/reservation/order/submit` 与 `/api/venue/finances/order/cancel` 都在这张表里。
于是**两个写动作在任何情况下都抛「本数据源不提供」**。

这个错误特别难发现，因为：

1. 文案是一句**听起来像分层设计**的话（「请在工具包里完成」），不是崩溃；
2. `FORBIDDEN_WRITES` 本身是**对的**（只读入口确实该拒绝写接口）；
3. 修的时候很容易只测 `prepare()` —— 那条路径完全正常。

**实测**（修复前）：

```
book execute:   CONFIG | 「/api/reservation/order/submit」是写操作…本数据源不提供
cancel execute: CONFIG | 「/api/venue/finances/order/cancel」是写操作…本数据源不提供
```

**修法**：给 `VenueClient` 加一条**写专用入口** `submit()`，它串行化 + 登录 +
把业务码翻成错误，但**不查** `FORBIDDEN_WRITES`、**不自动重放**（重放会重复建单）。
只读入口 `request()` 的闸**原样保留** —— 修死链不能顺手把分层防线拆掉。

**回归验证**（三条新测试，都做过「改坏 → 红灯 → 恢复」）：

| 改坏点 | 结果 |
| --- | --- |
| `bookVenue` 改回 `client.request` | **红 1 条** ✅ `bookVenueExecute：审批通过后真的把订单提交出去` |
| `cancelVenue` 改回 `client.request` | **红 1 条** ✅ `cancelVenueExecute：取消预约也真的发得出去` |
| 拆掉只读闸 | **红 1 条** ✅ `只读入口仍然拒绝写接口` |

测试断言的是「**请求真的发了**」（检查 `POST` 调用的 path 列表），不是「没抛错」——
死链的形态恰恰是「抛了一个听起来像设计决定的错」，只看 `rejects` 会把它当成预期行为。

### X-4 · `tyys` 取验证码题面这一步就过不去

`writes.js:141` 取题：

```js
await client.request('POST', '/api/reservation/captcha/check', { … })
```

而只读入口的 `READ_POSTS` 只有 `/api/reservation/order/info`，所以这句会被
「本数据源不支持对这个接口用 POST」拒掉。

**实测**：

```
captcha/check 被拦: CONFIG | 本数据源不支持对这个接口用 POST：/api/reservation/captcha/check。
```

也就是说：**需要验证码的场地，连取题都过不去**。上游 `venue.ts:20` 的 `READ_POSTS`
是四个（含 `captcha/check` 与两个 `buddy_no`），本仓只留了一个。

**这条没有修**，原因见下：它挂在「验证码到底该不该存在」这个未决问题上
（第五节 K-1）。若裁定保留验证码，`READ_POSTS` 补一行即可；若裁定删掉，
`captcha.js` 与 `writes.js` 那段一起走 —— 补 `READ_POSTS` 反而是白改。

## 三、Z 类：拒绝一次之后，那个动作永久不可用

**这是本轮最严重的一条，因为它不是「没实现」，而是「用一次就坏」。**

### Z-1 · 审批被拒 → 写会话卡死 → 该动作此后一直报 `WRITE_BUSY`

`writes.js` 的 `pair()` 是这么写的：

```js
prepare: async (args) => {
  if (session.prepared) throw new ClassroomError('WRITE_BUSY', '…上一次还没执行完…');
  const { summarized, run } = await build(args);
  session.set(summarized, run);   // ← 参数存进来了
  return summarized;
},
execute: async (signal) => {
  try { return await session.run(signal); }
  finally { session.clear(); }    // ← 只有 execute 才清
},
```

而工具层（`tool/campus-write`）的顺序是 **prepare → 审批 → execute**。
`guardWrite()` 在审批不通过时**直接抛错，不会调 execute**：

```js
await requireApproval({ … });   // 抛 WriteRejected
return act(signal);             // ← 走不到
```

于是 `session.prepared` 永远留着 → 该动作的**下一次 `prepare()` 恒报
`WRITE_BUSY`** → 用户批准也不行，重试也不行，只有重启进程才恢复。

**实测（走真实工具层 + 真实 source 写工厂）**：

```
第 1 次（用户点「拒绝」）: 未执行: WRITE_NOT_APPROVED
第 2 次（用户点「批准」）: prepare 失败: WRITE_BUSY
第 3 次再试:               prepare 失败: WRITE_BUSY
```

**波及范围**：七个包全部（`WRITE_BUSY` 在 7 个 `writes.js` 里各出现一次）：
`cc98` / `zdbk` / `lab` / `pta` / `sztz` / `tyys` / `xuezai`。逐个复现：

```
cc98.signIn:          未执行 execute 后再 prepare → WRITE_BUSY
zdbk.dropCourse:      未执行 execute 后再 prepare → WRITE_BUSY
lab.cancelLab:        未执行 execute 后再 prepare → WRITE_BUSY
sztz.signupActivity:  未执行 execute 后再 prepare → WRITE_BUSY
```

**影响面**：用户点了「拒绝」（最常见的动作之一）→ 这个能力的**整个会话周期内**
都不能再用。`sztz` 报名、`tyys` 预约、`zdbk` 退课这类动作出错时，
用户看到的会是「上一次还没执行完」，而他其实刚刚只是拒绝了一次。

**为什么没有测试抓到**：`tests/*-writes.test.mjs` 每条都 `prepare()` 一次就
`execute()` 一次，从来不走「prepare 之后不 execute」。工具层测试用的是假 source。
**又是同一种「每层各测各的」**。

### 为什么本轮不修

修法有两条，方向相反，且都动**已发布契约**：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A** | source 暴露 `cancelPrepare()` / `abandon()`，工具层在审批失败时调它 | 7 个包各加一个方法，`tool/campus-write` 的 `guardWrite` 要改成「失败也要清理」；服务面方法表变化 |
| **B** | `prepare()` 改成「后一次覆盖前一次」，并靠消息 id / 一次性令牌保证「批准的是哪一次」 | 放弃现有的「并发 Prepare 被拒」保护，那条是防「批准 A、执行 B」的，动它风险更高 |
| **C** | `prepare()` 记下时间戳，超过 N 秒自动作废 | 治不了「刚拒绝就重试」这个主要场景 |

A 与 B 都改变调用方预期（工具层 / 服务面），按本仓规矩要先定方向。
**建议 A**：它保留「并发 Prepare 被拒」这条安全性质，只是补上「放弃」的出口。
但这是契约变更，不该由我在这张票里单方面定。

**这条已记 `coverage-gaps.md` 的 Z-1，等裁决。**

### K-3 · `package-lock.json` 与 `package.json` 不同步

## 六、给接手的人：这个仓最容易再犯的三件事

按本轮实际踩到的顺序排：

1. **「prepare 通过」不等于「这条能力能用」。**
   本轮两条死链都能通过 `prepare()`。测写操作必须跑到 `execute()`，
   而且要断言**请求真的发出去了**（检查 fetch 收到的 path），
   不是断言「没抛错」——死链会抛一个很像设计决定的错。
2. **每层各测各的，中间那道缝没人测。**
   上一轮漏的是「工具层传给 source 的参数」（Y-13），
   这一轮漏的是「审批失败后 source 的会话状态」（Z-1）。
   修完任何写操作，问一句：**这条链路上还有哪一段是只有我自己知道它是对的？**
3. **注释与 README 里的「只读 / 不做」，是这个仓最贵的谎。**
   `coverage-gaps.md` 第五节已经为「不做」立过规矩，但没管住「只读」这个词。
   README 里写「本包只读」「不含写代码」之前，先 `grep writeMethods` 一次。
