# 尽可能无损融合重构外部同类插件的尽可能全面的功能到本项目

**目标读者**：要把一个外部同类插件的能力搬进本仓、又不想在搬运过程中悄悄丢功能的执行者（人或 agent）。

**这个 skill 存在的原因**：融合失败通常不是「代码写错了」，而是**没人知道原插件到底有多少条处理路径**。缺的那条路径不会报错，它只是安静地不存在 —— 直到用户在某天发现「为什么它没有这个功能」。所以本流程把「先把全貌画出来、用图校验、再由用户逐层剪枝」当成不可跳过的前置。

**本 skill 的名字是描述性的，不是标识符**。frontmatter 的 `name` 用的是 ASCII slug `lossless-plugin-fusion`，因为 skill 要能被 `/name` 调用、被模型在目录里精确引用；中文全称作为标题保留在上面。

---

## 硬规则（违反任一条，本流程视为未完成）

1. **不替用户裁决。** 数据源集成多少、处理链路剪哪条、以及**四类终端的落法（page / tool / preset / skill）**，全部由用户决定。你可以给推荐方案与理由，但不能把推荐当成已定；tool 与 preset 的挂法尤其不能顺手定 —— 那两者决定「谁在什么时候看得见这些能力」。
2. **不静默省略。** 任何「这个不重要所以没画 / 没比 / 没做」都必须写进产物，并标明理由与影响。省略一条链路要用户点头，不是默认。
3. **不把「看起来能用」写成「已实现」。** 本项目现状一栏必须由源码/测试支撑；没有证据的写「未核实」，不写「已有」。
4. **无下游的模块画虚线。** `provide` 存在但没有任何 `get` / `inject` 消费者的服务，在图上必须是虚线并注明「仓内 0 处取用」。把它画成实线等于宣称它在链路上。
5. **引用可复核。** 图与清单里的服务名、路由、包名，都要能在仓库里搜到；推测写成推测。

## 工作流

### 1. 画泳道图

产物：`docs/show/<外部插件名>-fusion-lanes.html`

**不要手写 HTML。** 本 skill 带了一个生成器：[tools/lanes.py](tools/lanes.py)。把结构写成 JSON，它渲染成与本仓
[examples/architecture-full-chain.html](examples/architecture-full-chain.html) 同款的页面（那份可以直接打开看效果）。

```bash
cd docs/contributing/skills/lossless-plugin-fusion

# 从示例规格起草
cp examples/fusion-spec.example.json /tmp/my-spec.json

# 渲染
py tools/lanes.py /tmp/my-spec.json --out docs/show/xxx-fusion-lanes.html

# 只看结构（前驱 / 后继 / 终端），不生成 HTML
py tools/lanes.py /tmp/my-spec.json --report

# 校验（有错误时退出码 1，可以串进 CI 或 agent 自检）
py tools/lanes.py /tmp/my-spec.json --check

# 临时剪几条，不改 spec 文件
py tools/lanes.py /tmp/my-spec.json --prune L4,L6 --out /tmp/preview.html
```

`python3` 不可用时用 `py`；Windows 上别用 `python`（本机可能被别的发行版占掉）。

**为什么用生成器而不是手写**：真实的失败方式不是「不会写 HTML」，而是**每次剪枝都要重抄一遍**。节点一多，
手改必漏改某处箭头或某个 side chip；剪枝后忘记更新前驱后继更是常态。用 spec 之后，剪枝只是把 `cut`
从 `false` 改成 `true`，结构由工具重算。

画法要点（spec 怎么填）：

- **一条泳道 = 一种数据从源头走到终端的完整路径**，不是一层、不是一个模块。
- **每个节点写 `in` / `out`（入什么形态 → 出什么形态）**，不写「做了什么」。做了什么是实现细节，形态变化才是契约。
- 节点右下角的 `pkg` 让人能搜到源码位置。
- 一条泳道内的多条支流用 `rows` 拆开，不要靠自动折行 —— 折行位置不可控，读者会读错归属。
- 终端用 `kind` 区分：**`ui`（给人）/ `tool`（给 agent 调）**。`preset` 与 `skill` 通常挂在 `side` 的 chip 里，
  由第 9 步人工确认 —— `--report` 的「终端」一栏只统计 `ui` / `tool` 两类节点。
- 明确断点：外部插件有、但它自己也没接通的部分，`kind` 用 `ghost` + `arrow: "cut"`。
- 与本次任务无关的目录（如本仓的 `vendor/*`、`radar/*`）不画，但在 `footer` 里说明为什么不画。

**判据**：`--check` 通过，且不看图就能说出「这个插件有几条独立的数据流、每条的起点和终点」。

---

### 2. 校验遗漏

对**每一条可执行入口**（路由、IPC、CLI、导出函数、cron、事件订阅、按钮点击、prompt 入口）做一次映射：

| 入口 | 位置 | 落到哪条泳道 | 状态 |
| --- | --- | --- | --- |
| `POST /api/xxx` | `src/routes/xxx.ts:12` | L3 · 讲义 → 题目 | 已画 |
| `lib/foo.ts#run()` | `src/index.ts` 导出 | —— | **未映射** |

- 未被映射的入口 = 遗漏，必须补画，或明确标注「不可达 / 未实现 / 与本项目无关」并写理由。
- **必须声明探索范围**。README、demo、所有 `src/**` 入口、配置文件里的注册点，都算范围内；没读到的目录要写进「未探索」，不能默认它没有功能。
- 补画后再跑一次映射，直到范围内 0 条未映射。

**判据**：范围内未映射项 = 0；范围外用一节列出「没读什么、为什么」。

---

### 3. 把泳道图交给用户

- 用 present 交付 HTML，并在消息里点明：**哪几条泳道是断的、哪几个模块在本仓没有下游、哪几处是推测**。
- 不要用文字复述图 —— 图已经在了。文字只补图上看不出的东西（判据、风险、待决问题）。

---

### 4. 询问数据源模块要集成多少内容，按选择剪枝

问用户，并且要求可执行粒度：

- 集成哪些数据源；
- 每个数据源集成到什么程度：**全量 / 只读子集 / 只取某几个接口 / 不集成**；
- 该数据源在外部插件里承担哪些泳道。

按回答剪枝：

- 被剪掉的泳道在 spec 里写 `"cut": true`，**渲染成删除线，不物理删除** —— 后续要能复核「这是剪的还是漏的」。
  物理删掉之后，看图的人分不清「这条是剪掉的」还是「这条从来就没画」。
- 剪枝后跑 `--check`：它会把「剪了前置但留着后继」判为错误（`L4 已剪，但仍向未剪的 L6 供数`），
  把「未剪但前驱已剪」判为悬空起点。这正是第 4、5 步最容易漏的地方。
- 前置没了，后继要么一起剪，要么改成从别的来源取数，并在 `footer` 里写明。

**判据**：`--check` 通过，即每条保留泳道的起点仍然有数据来源。

---

### 5. 对剩下的数据处理链路再问一遍，剪还是留

逐条泳道问，并要求用户这样回答：

> **泳道编号 + 泳道名**，以及它的 **前驱是什么、后继是什么**。

**先跑 `--report`，把输出贴给用户。** 它会打印每条泳道的编号、名称、前驱、后继、终端、剪枝状态 ——
用户不需要凭空回忆箭头指向，只要在现成的清单上写「留 / 剪」即可。这一步的产物就是裁决记录本身。

例如合格的回答：

> 「剪掉 L4『讲义 → AI 教学课件』这条。它的前驱是 L2 输出的阅读讲义，后继是学习页课件栏与 pptx 导出。前驱保留，后继一起剪。」

不合格的回答（必须要求用户重写，不得自行脑补）：

> 「课件那块不要了。」—— 指代不明，可能指 L4 整条，也可能指 L4 里的媒体分支。

- 每次剪枝后**重算前驱后继**（改 spec 的 `cut` 再跑 `--report`），避免留下引用了已删节点的泳道。
- 用户说「全留」也要记录成明确决定，不能因为没有分歧就跳过这一步。
- `--report` 同时会告警「既无 ui/tool 终端也无后继」的泳道 —— 那是画到一半断掉的流，
  第 9 步不会有任何东西可裁决，必须补终端或标成 `cut`。

**判据**：`--check` 通过；每条保留泳道都有用户明确说过的「留」，或用户在上一轮明确表示全部保留。没有默认值。

### 6. 列清单，作为后续裁决的唯一依据

| # | 泳道 | 保留节点（按顺序） | 类型 | 本项目现状 | 待办 |
| --- | --- | --- | --- | --- | --- |
| 1 | L1 课堂 → 讲义稿 | 源 → 识别 → 标记 → 建树 → 重构 → 入库 → 服务 | src/proc | 已有，与外部实现算法不同 | 比对裁决 |
| 2 | L2 … | … | proc/ui | 无 | 直接集成 |

- 「本项目现状」必须有证据（包名、文件、测试名）。没有证据写「未核实」。
- 清单一旦定稿，第 7–9 步只围绕清单里的条目裁决，不再回头改画图。

---

### 7. 比对数据源

分两种，处理方式不同：

**A. 本项目里不存在的数据源**

- 直接新建数据源包（保持本仓分层：数据源只提供事实，不做变换，不含 UI）。
- **必须询问用户：新建的数据源要不要走 WebVPN？** 不要按「都是浙大站点」默认接管 —— 有的站点在校内可达、有的需要网关改写、有的只需代理，三者代价不同。
- 新建前确认：鉴权方式（一卡通 / 自有账号 / 无鉴权）、是否需要 CAS、是否只读。

**B. 本项目里已存在的数据源**

- 认真比对：外部插件需要的字段/接口，本项目的数据源有没有暴露。
- 结论三选一并**告知用户**：无需扩展 / 需要扩展（列出要新增的方法与返回字段）/ 本项目数据源模型不兼容（说明冲突点）。
- 扩展接口协议属于对外契约变更，要按本仓的版本与引用规则同步（改内部包版本号前先全局搜谁引用它）。

---

### 8. 比对 core 链路

把清单里每条 `proc` 节点与本项目已有实现对照，分成三类：

**A. 本项目明显没有这条链路 → 可以直接集成。**
仍要说明它依赖哪些数据源与服务，避免集成完发现上游没接。

**B. 与本项目 core 链路相近，但算法/代价不同 → 必须给用户裁决。**

对比项写成**可核对的量化项**，不写「更复杂」：

| 维度 | 本项目 | 外部插件 | 差在哪 |
| --- | --- | --- | --- |
| 时间/空间量级 | | | |
| 单次调用的模型请求数 | | | |
| token 预算（输入/输出） | | | |
| 并发上限与背压 | | | |
| 缓存命中面（键、失效条件） | | | |
| 失败粒度（整条 / 单页 / 单块） | | | |

同时判断**是否需要为此扩展数据源接口协议**（例如外部实现要吃分页字幕，本项目的数据源只给整段），需要就一并向用户说明。

**C. 与本项目 core 链路相近且有区别，可作为互补/加强 → 给利弊，交用户裁决。**

- 写清：它补的是本项目的哪块缺口；代价是什么（多一份维护、多一次模型调用、两套产物如何共存或互斥）。
- 「互补」与「加强」要分开说：互补是两条链路各管一段数据，加强是用它的实现替换本项目某一步。二者的回滚代价不同。

**判据**：清单里每条 `proc` 都落在 A/B/C 之一，且 B、C 两类都有用户明确裁决记录。

---

### 9. 终端裁决：page / tool / preset / skill 四类统一交用户

**四类都是终端，都交用户。** 每类给出推荐方案 + 一句理由，但决定权不在你。

**page（UI 展示链路）**

- 两个选项：**集成进已有 page** / **新开 page**。
- 推荐依据：它与已有 page 是不是同一件事（同一对象、同一时间尺度、同一操作序列）。同一件事硬开新页会让用户在两个页面间来回跳。
- 说明：新开 page 要占导航项、要单独处理空状态与权限；集成进已有 page 要处理布局冲突与谁的插槽优先。

**tool（agent 可调用的工具）**

- 两个选项：**新建工具** / **并入已有工具表**。
- 推荐依据：这个工具服务的是不是已有工具服务的同一批对象。同一批对象拆成两套工具，模型要自己判断该调哪个，误选率会上升。
- 必须写清**注入点**：本仓的约定是工具包只 `ctx.tools.register`，**不带自己的挂载行**；「什么时候把这些工具给 agent」由 preset 决定。写进 profile 的 bundles 会让所有 preset 都看到。

**preset（工具何时出现）**

- 两个选项：**新增 preset** / **并入已有 preset**。
- 推荐依据：这批工具是不是只对某一类任务有意义。只对「读课程讲义」有意义的工具挂在主机平面，会让**每个** preset 的 agent 都看到，既占工具表又增加误选概率。
- 说明代价：新增 preset 是新增一个用户可见的模式；并入已有 preset 意味着这些工具在所有该模式的会话里都占工具表。

**skill（agent 先读后做的指令）**

- 两个选项：**新增 skill** / **并入已有 skill**。
- 推荐依据：触发条件是否与已有 skill 重叠。同一个触发条件下两个 skill 都命中，模型只会加载其中一个，等于另一个白写。
- 说明代价：skill 占的是模型每次请求都要读的目录，条目越多每轮成本越高；合并进已有 skill 会让那个 skill 变长但目录更短。
- 若目标 skill 目录不在任何扫描根里（本仓 `docs/contributing/skills/` 就是这种情况），必须说明「放进仓库 ≠ 会自动生效」，生效要用户自己复制到扫描根。

**四类的共同要求**

- 每条都要同时给出**推荐方案**与**反面代价**（选另一个会损失什么），否则用户没法裁决。
- 用户选了推荐之外的方案，照做，并在裁决记录里写上「与推荐不同」及用户理由 —— 后续维护时这是重要信息。
- 图上四类终端用不同颜色区分；合并进已有终端时，图上画成「并入 <已有节点名>」而不是新节点，避免图中出现两个实际是同一个东西的方块。

**判据**：四类终端每一条都有用户的明确选择记录；没有用户的「都行」，就没有进入实现。

## 产物清单

一次完整执行至少留下：

1. `docs/show/<外部插件名>-fusion-lanes.html` —— 泳道图（由 spec 渲染，剪枝后仍保留被剪节点的删除线版本）。
2. spec 文件本身 —— 后续想改图只需改它再重渲染，不用碰 HTML。
3. 入口 → 泳道 映射表（可放进图的 `notes`，或单独 md）。
4. 最终整合清单（第 6 步的表格）。
5. 裁决记录：每条 B/C 类链路与四类终端，谁裁决、裁决成什么、理由。可直接取用第 5 步的 `--report` 输出。
6. 未探索范围与已知缺口。

## 常见失败方式

| 现象 | 真实原因 |
| --- | --- |
| 集成完发现少了个功能 | 第 2 步没做入口映射，或没声明探索范围 |
| 用户中途反复改主意 | 第 5 步允许了模糊剪枝，前驱后继没重算，每改一次图都对不上 |
| 上线后工具在别的模式下也出现 | 第 9 步把工具包写进了 profile bundles，而不是只给 preset |
| 「无损」变成了「重写了一遍」 | 第 8 步没做量化对比，直接按印象判断新旧实现等价 |
| 新建数据源要返工 | 第 7 步没问 WebVPN，事后才发现站点在校外不可达 |
| 剪枝记录说不清 | 手写 HTML 时把节点删了 —— 用 `cut: true` 保留删除线，`--check` 会替你盯悬空起点 |
