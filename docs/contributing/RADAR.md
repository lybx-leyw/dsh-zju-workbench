# 生态雷达的转正约定

> 本文规定：`packages/radar/` 下的候选骨架**如何变成正式包**，以及**不转正时如何处置**。
>
> 适用范围：`packages/radar/dsh-radar-*` 全部包。正式包的写作规范仍见
> [CONTRIBUTING.md](./CONTRIBUTING.md) 第 2–3 章；本文只补它没覆盖的那一段。

---

## 0. 先理解一件事：骨架不是代码资产

`packages/radar/` 下的包，README 第一行都写着「候选骨架：未评审、未接入 profile、不可直接使用」，
`OWNERS` 一律是 `shared`，从不进入任何 profile。它们的性质是**评估工件** —— 记录「这个上游值不值得接、
接进来长什么样、要先回答哪些问题」，不是等着被完善的产品代码。

由此推出本文的两条基调：

1. **转正 = 新建一个正式包 +（有条件地）删除骨架**，不是把骨架原地「升格」。
   原地改状态，等于让一个从未被评审过的东西直接继承候选身份。
2. **删除是破坏性的，所以默认不删。** 见第 3 章的保守废弃原则。

---

## 1. 转正的三种结局

| 结局 | 含义 | 落点 | 骨架处置 |
| --- | --- | --- | --- |
| **A · 提取（Extract）** | 只要某项能力，不要这个包 | **已有的**目标包 | **视情况**：能力全部被提取 → 删；还有剩余 → **标记，不删** |
| **B · 移植（Port）** | 整个包搬到正式位置 | **新建**正式包 `dsh-zhiyun-<slug>` | **直接删**（整包搬迁，骨架里不再有任何独有内容） |
| **C · 驳回（Reject）** | 评估完发现不值得做 | 不落地 | **不删**，标记 `rejected` + 理由（见 3.3） |

只有 A 和 B 叫「转正」。C 是「评估结论」，两者在 registry 里用不同状态区分。

### 1.1 两种模式不可混用

这是最容易犯、也最难发现的错 —— **它不会让任何测试变红**，只是让某个包悄悄多背一份不属于它的依赖。

| | **移植（B）** | **提取（A）** |
| --- | --- | --- |
| 前提 | 整个包都能用 | 只有某几项能力成立 |
| 落点 | **新建**包 | **已有**包的源码目录 |
| 骨架 | 删除 | 保留 + 标 🅿️ |
| 典型反例 | 把整个包塞进某个已有包的子目录（如 `page-notes/src/graph/`） | 把一项小能力单独开成一个新包 |

**判定顺序**：先逐项核能力清单（见 3.2）——

1. **每一项都成立**（或成立的那部分就是它的全部价值）→ **移植**：新建包，整包搬过去，删骨架。
2. **只有部分成立** → **提取**：把成立的那几项写进**已有的**目标包，骨架**保留**并标记，剩下的项写进能力清单。

为什么反例是错的，用一次真实返工说明：把 `note-graph` 整包放进 `dsh-zhiyun-page-notes/src/graph/` 后，
`page-notes` 的客户端 bundle 内联了 1.3 MB 的 cytoscape —— 而「画图」并不是这个页面的职责。
依赖错位不影响功能、不报错、不失败，只是让下一个想动这个页面的人以为那份依赖是必需的。
正确做法是新建 `dsh-zhiyun-graph-render`，页面只 `import` 它。

> **一句话**：移植的产物是一个**新的包**；提取的产物是**已有包里的几行代码**。
> 若你发现自己在给一个新目录「起名」，那它就应该是一个包，而不是某个包的子目录。

## 2. 转正的门槛

四条，全部满足才能开转正 PR：

| # | 门槛 | 怎么验 |
| --- | --- | --- |
| 1 | **有人认领** | 正式包的 `OWNERS` 不是 `shared`；新包按 CONTRIBUTING 2.3 写 |
| 2 | **有测试** | `tests/<名字>.test.mjs`，`npm test` 通过；涉及插槽/导航/主题再跑 `npm run test:host` |
| 3 | **前置问题已答** | 骨架 README「接入前必须先做的事」逐条回答或划掉，**不留 "后续再说"** |
| 4 | **profile 起得来** | 按 CONTRIBUTING 3.1 先本地接入验证，再提交；`npm run check:css` 视改动而定 |

> 门槛 2 是当前最有效的一道筛子：仓库里 71 个骨架，有测试的是 0 个。
> 这不是苛刻，是「没测试的包别人不敢动」这条判断的直接落地。

### 2.1 命名

正式包必须叫 `dsh-zhiyun-<slug>`。`build.mjs` / `profile.mjs` / `check-css-order.mjs`
只认这个前缀 —— 转正时**必须改名**，不能保留 `dsh-radar-` 前缀。

## 3. 保守废弃原则（本文最硬的一条）

> **只有包的所有能力都被提取，或者用户明确要求，才删除骨架包。**
>
> 若只是从多个 radar 包里批量提取了**部分**能力，而骨架里还具备很多其他能力，
> **一律不删，只做标记**。

这条原则的理由：骨架的价值不在代码，在**它记录了多少个还没做的判断**。
批量提取时顺手删包，等于把「这个上游还有 6 项能力没试过」这件事一起删掉了 ——
下一轮雷达会把它当新候选重新扫一遍、重新评估、重新出骨架。**删除的成本是重复劳动，标记的成本是一行状态。**

### 3.1 删除的唯一两种情形

| 情形 | 判定标准 | 例子 |
| --- | --- | --- |
| **① 能力已清空** | 能力清单里**每一项**都标 `已提取 → 去向`，无一项为 `未做` | 整个包被移植到 `dsh-zhiyun-x`（B 类） |
| **② 用户明确要求** | 有人（通常是维护者）明确说「删掉这个包」 | 维护者清理时点名 |

**其他任何情况都不得删除** —— 包括「看起来没用」「占地方」「已经很久没动」。

### 3.2 能力清单：让「是否清空」可以核对

骨架 README 必须维护一张能力清单。**这是保守原则能被执行的前提** ——
「还有没有别的东西」不能凭记忆判断。

```markdown
## 能力清单

| # | 能力 | 状态 | 去向 |
| --- | --- | --- | --- |
| 1 | OAuth2 授权码链路 | 已提取 | `dsh-zhiyun-classroom/src/auth.js`（`entry:'oauth'`） |
| 2 | `_token` → JWT / Bearer 头 | 已提取 | 同上，`live.js` |
| 3 | CookieJar 显式 domain/path 处理 | 作废 | 本仓 `tough-cookie@6.0.2` 已覆盖 |
| 4 | RSA 分块密码 | 未做 | — |
```

状态只有四种：`已提取`（写明去向）/ `作废`（写明为什么不需要）/ `未做` / `不做`（写明为什么不值得）。

**只有全表为 `已提取` 或 `作废` 时，才调用 3.1 情形 ①。** 出现任何一行 `未做`，就是「还有能力」，只标记不删。

清单维护责任在**提取者**：谁提取了哪项，就在同一个 PR 里把那一行改成 `已提取` + 去向。

### 3.3 不删时的标记

骨架不删除，但要把它「降级为已处理」的状态写清楚，避免下一轮把它当新候选：

1. **registry 状态**改为 `adopted`（部分提取）或 `rejected`（驳回），`备注` 写明提取了什么、剩余什么。
2. **骨架 README 顶部**加一行：

   ```markdown
   > 🅿️ **部分提取，保留待后续**（2026-10-28）：能力 1/2 已进 `dsh-zhiyun-classroom`；
   > 剩余能力 4 未做。**本包不删除**，按 RADAR.md 3.2 保守废弃原则保留。
   ```

3. **`src/index.js` 顶部注释**同步一句，避免有人直接看代码时以为是全新骨架。

### 3.4 什么时候可以再谈删除

只有下面任一条件成立时，才重新考虑删除一个已标记的骨架：

- 清单里 `未做` 的项被逐项处理完（转为 `已提取` / `作废` / `不做`）；
- 上游项目本身消失、改协议到不可用、或明确弃坑，剩余能力失去意义；
- **用户明确要求**。

### 3.5 清空之后必须履行删除（否则就退化成「永久标记」）

保守原则保护的是「**还有能力没做完**」的包。能力清空之后，保留就没有任何理由了 ——
此时**不再需要额外授权**，提取者应在**同一个 PR 内**删掉骨架。

反例（真实发生过）：`dsh-radar-zju-recorder` 的能力清单三项都已 `已提取` / `作废` / `已修正`，
README 顶部写着「**已并入，本骨架待删**（2026-10-18）」，而包到今天仍在仓库里 ——
「待删」变成了一个没有执行人的待办。**这就是标记退化成堆积的方式**：
先 `待删`，再没人管，最后变成「不知道为什么在这」。

因此：**`待删` 不是一个合法状态。** 清理清单时需要区分两种标记：

| 标记 | 含义 | 是否该存在 |
| --- | --- | --- |
| 🅿️ **部分提取，保留待后续** | 还有 `未做` 项 | ✅ 正确用法 |
| ✅ **已清空** | 全部 `已提取`/`作废`/`不做` | ❌ 不该出现在 profile 里，应直接删 |

**每轮雷达扫描**（r90 起）应顺带列出「✅ 已清空但仍存在」的骨架清单，交给维护者一键清理。

## 4. 转正 PR 的检查清单

开转正 PR 时，描述里逐条勾选：

- [ ] 新建了 `packages/dsh-zhiyun-<slug>/`，`OWNERS` 已写（非 `shared`）
- [ ] `tests/<名字>.test.mjs` 存在且 `npm test` 通过
- [ ] 骨架 README「接入前必须先做的事」已逐条回答
- [ ] 本地接入 profile 验证过，`npm run test:host` 通过
- [ ] 骨架的能力清单已更新：`已提取` 项写明去向
- [ ] **删除判定**：清单全为 `已提取`/`作废` → 删骨架；否则 → 只标记（按 3.3）
- [ ] registry 该行状态已更新，`备注` 写清提取/剩余情况
- [ ] 若整理了上游代码，按 CONTRIBUTING 3.3 记 ATTRIBUTION
- [ ] 无凭证泄露、无本地绝对路径（CONTRIBUTING 3.4）

## 5. radar 分支的机械约束

radar 分支的产出由自动化轮次生成，不能只靠提示词自我约束。以下两条在 CI 里拦截：

| 规则 | 理由 |
| --- | --- |
| **radar PR 不得修改 `profiles/`** | 骨架从不接 profile；改了就是绕过评审 |
| **`packages/` 根不得出现 `dsh-radar-*`** | 全部必须在 `packages/radar/` 下 |

这两条成本极低，但能把「靠自觉」变成「靠机制」。
