## 决定：不 vendor Cordis，保留 DSH 插件身份（本地变更先攒着）

### 背景

`dsh-pages` 要让「原生 DSH client 群」和「我们自己的页面」共存在同一套槽位树里。最初的设想是把整个 UI 视为一个 page 树：

```text
page.<name>...     我们的槽位
page.dsh.<name>... 嵌入的 DSH 应用的槽位
<name>...          同一个 DSH 槽位的物理写法
```

### 曾考虑的方案：vendor `ui-slots` 并改造

技术上查清了两件事：

1. **`SlotCore` 的槽位表是全局扁平的** `Map<string, SlotRecord>`，没有命名空间字段。
2. **Cordis 在服务层禁止替换已有服务**：
   - `ctx.reflect.provide('slots', …)` → 抛「already provided in this scope」（`reflect.ts:37-38`）
   - `ctx.reflect.accessor('slots', …)` → 抛「already declared as service」（`reflect.ts:282`）

所以「接管 `ctx.slots`」这条路被框架堵死。当时得出的结论是：vendor `ui-slots`，在 `SlotCore` 里加命名空间。

**这个方案最终没有执行。**

### 为什么不 vendor

代价不只是「追版本」，而是**身份的改变**：

| | 继续做 DSH 插件 | vendor 并 fork |
|---|---|---|
| 装社区插件 | ✅ | ✅ |
| **我们的插件进 DSH 社区** | ✅ | ❌ |
| 被更广泛使用 | ✅ | 只有本仓用户 |
| 依赖 DSH | 表面依赖 | 无依赖，但要自己维护 |

**关键的不对称**：fork 之后我们只能「消费生态」，不能「贡献生态」。一个已编译的第三方插件装进来照常能跑（因为 63 个 client 包的 peer 依赖只有 `cordis`，运行时通过 `ctx.slots` 服务协作），但反过来我们的包发不到 DSH 市场——它们依赖改过的 vendored 源码。

而 `zju-workbench` 的价值里有一条是**成为 DSH 生态的一员、被更广泛使用**。fork 会把这条路关掉。

**结论：保留作为 DSH 插件的关系，不 vendor。** 用运行期的命名规则解决问题，而不是改框架源码。

### 最终实现：`page-slots.js`（不是 bridge）

按命名规则实现，而不是靠改写 key：

- **`page.<name>...`** —— 我们自己的槽位，**必须**带前缀。
- **`page.dsh.<name>...`** —— DSH 槽位的**真实地址**。
- **`<name>...`** —— 同一个槽位的物理写法。因为嵌入的 DSH 应用直接调 `ctx.slots`，我们的代码看不到那些调用，改不了它们的 key，所以物理拼写只能保持原样。

不是「给 DSH 加前缀」，而是「**无前缀是 DSH 分支的物理写法，一种约定特例**」。

两边的处理刻意不对称：

| | 我们的槽位 | DSH 的槽位 |
|---|---|---|
| 写法规约 | 必须 `page.<name>` | 不带前缀 |
| 注册时 | 原样存储 | `page.dsh.x` → `x` 翻译 |
| 写错 | **抛错**，提示正确写法 | 不可能写错 |

`register({ name: 'sidebar' })` 直接抛错——这样我们的 typo 不会静默撞上 DSH 的同名槽。

两个翻译函数把「同一槽位、两种写法」表达清楚：

```js
toCanonicalKey('sidebar')          // → 'page.dsh.sidebar'
toPhysicalKey('page.dsh.sidebar')  // → 'sidebar'
```

### 为什么这个方案可行

63 个 client 包的 `peerDependencies` **全部只有 `@deepseek-ai/cordis`**，所有对 `ui-slots` / `ui-renderer` 的依赖都在 `devDependencies`（仅类型）。所以 DSH 的 UI 层运行时只依赖 Cordis，**我们不碰框架源码也能维持兼容**。
