## 集成路径（**与前几个 A 类骨架不同，评审请注意**）

`dsh-radar-better-markdown`、`dsh-radar-context-lens` 挂的上游都带 `dsh.client`，
有现成的浏览器半边。**本上游没有** —— 它只在宿主侧注册：

1. `plugin_audit` **工具**（输入 `{ path, format }`，输出权限画像卡片 + JSON 摘要）；
2. `tools/pre-execute` **哨兵**（工具调用触到凭据路径 / 未知主机时返回 `ask`）。

因此本骨架**不是**「挂上就有一块画面」，而是**宿主侧取数 + 页面侧自绘一列**：

```
上游 plugin_audit（宿主侧）  ──取数──▶  本包适配层  ──追加列──▶  「插件」页依赖图
                                            （缓存 / 增量）
```

工作量比另两个骨架**高一步**：需要把审计结果变成结构化行数据。
上游同时提供 `format: 'json'`，**优先用 json，不要解析 markdown 卡片**。

## 需要人工裁定的事项

1. **审计入口能否被程序化调用（最大未知项）** —— 上游对外是 **agent 工具**
   （`plugin_audit`），不是文档化的库 API。若只能经工具调用通道取数，
   「宿主侧取数 + 页面侧追加列」这条路的成本会显著上升。
   **建议评审时优先核实这一条**，它决定方案 (a) 是否成立。

2. **运行时哨兵**应**默认关闭**（`sentinelEnabled: false`）——
   上游哨兵会在**每一次工具调用**上追加一次审批询问。本仓是**学生日常使用**的
   学习工作台，不是安全运维台：默认开哨兵会把「问一问」变成手续。
   静态画像（只读、不介入调用）才是本仓真正需要的那一半。
   → **本骨架只取静态画像，不启哨兵。**

3. **定向扫描的成本控制** —— 本仓约 30 个自有包 + profile 里的第三方插件。
   不该每次打开插件页就全量扫（上游扫描上限 400 文件 / 单文件 256 KB）。
   需要缓存 / 增量策略与明确的扫描范围。

4. **同域取优不叠加** —— 本轮 A 组同时命中 `rogerdigital/dsh-vet`（★2，MIT，
   `dsh.seams` 声明）、`chuanxuWei/dsh-trust-center`（★0，MIT，npm 未发布）、
   `Evhye38496/dsh-perfscope`（★2，MIT，npm 可锁版）。
   四者**都在做「插件装前 / 装后体检」**，属同一簇。
   本骨架选上游 `dsh-plugin-audit` 的理由：**有带行号证据的静态画像 + npm 可锁版 +
   明确的权限口径**。但这仍然是**簇内取一**，评审时可换。

5. **文案口径** —— 上游自述 *"The audit is an aid, not a verdict"*。
   界面**不得**把 `risk` 渲染成判决或「不安全」标签，应为**证据提示**口吻
   （与「插件」页现有的中性徽标风格一致）。
