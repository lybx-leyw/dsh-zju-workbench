## ⚠️ 接入边界：三个必须先裁定、否则不应动工的问题

### 【1】技术栈错配（最大障碍）

上游是 **Python 管线**，本仓是 **DSH 工作台包（JS）**。**不能直接挂载。**

| 路线 | 做法 | 代价 |
| --- | --- | --- |
| **(a) 能力提取 + 本仓自建**（**推荐**） | 只取**对齐设计**与**证据模型**（`slides_grounded.json` 的形状），ASR/OCR 由本仓既有通道承担 | 需自行实现对齐；但无 Python 运行时耦合 |
| (b) 外挂本地管线 | 把上游 Python 管线作为本地进程运行，本包只调用与呈现 | 引入 faster-whisper / torch / GPU 依赖，**与本仓无 GPU 环境冲突** |

> **建议优先 (a)**：上游价值在**设计与证据链模型**，不在其具体实现。
> 且本仓**已有 `dsh-zhiyun-parser`（三阶段解析器）**，
> 这类"原始材料 → 结构化文本"的入口**应当复用**，而不是再起一套。

### 【2】本地算力假设与隐私（**红线**）

- 上游假设「本地 GPU 跑 Whisper」，本仓运行环境**未必有 GPU**。
- 课堂录像/录音属**个人学习资料**。若上传第三方做转写，
  **须先确认本仓的数据出境与留存策略** —— **这条不能由雷达替答，须人工拍板。**
- **未确认数据策略前，不得动工。**

### 【3】"对齐"的期望管理

上游自述目标是 **traceability（可追溯）**，**不是 accuracy（准确）**。
对齐必然有误差。

> **若把它当"自动生成准确讲义"用，一定会失望。**
> 建议 UI **明确标注"对齐仅供参考"**，并把逐字稿作为
> **可核对的原始证据**呈现，而非作为结论本身。
