## 一句话

本仓有**四处**从模型响应里脱围栏的实现，口径互不一致、且**一处都没有测试**；
本包给出一份「能同时处理尾随说明」的口径，作为评审的对照物。

## 现状：四份实现，三种行为（已实测）

`node --input-type=module -e` 直跑四个真实导出，输入同一组样例：

| 样例 | `lecture/polish.js:538` | `quiz/generate.js:678` | `parser/core.js:4` | 本骨架 |
| --- | --- | --- | --- | --- |
| ```` ```json\n{"a":1}\n``` ```` | `{"a":1}` | `{"a":1}` | `{"a":1}` | `{"a":1}` |
| ```` ```json\n{"a":1}\n```\n谢谢 ```` | **原样（围栏没剥）** | `{"a":1}` | **原样** | `{"a":1}` |
| ```` ```js\nif (a) {\n```\n}\n``` ```` | `if (a) {\n```\n}` | 同左 | 同左 | **`if (a) {`（截短 ← 缺陷）** |
| ```` ```json {"a":1} ``` ````（单行） | 原样 | 原样 | 原样 | 原样 |
| ```` 前言\n```json…``` ````（有前缀） | 原样 | 原样 | 原样 | 原样 |

两条可复核的结论：

1. **`lecture` 与 `parser` 对「围栏后多一句口语」完全不剥**。它们的正则锚定 `^…$` 整串。
   走到「讲义」终审时，模型在 JSON/标记块后附一句「以上。」是常见行为 →
   `parseAgentLectureText` 拿到的是以 ```` ``` ```` 开头的文本，抛
   「终审结果缺少可读取的知识点，已保留上一版讲义」—— **错误信息指向模型没给内容，
   真实原因是多了一句道谢**。同样的输入在「出题」页是正常的（`quiz` 那版处理了）。
2. **本骨架第一版与它要修的那个 bug 一模一样**：初版判据是「最后一条非空行必须是 ```` ``` ````」，
   于是 ```` …```\n谢谢 ```` 被判为「不是围栏」、原样返回。测试 4 第一版是红的，
   改成「从尾部数到第 2 个整行 ```」后才绿。**这条保留在 README 里，是因为它说明
   「照抄一个正则」不足以证明口径正确，必须逐样例跑。**

## 已知缺陷（本版未修，且不应带病上线）

「从尾部数第 2 个整行 ```` ``` ````」这个判据**无法同时满足**：

- ```` ```…```\n谢谢 ```` → 想剥（尾随说明）；
- ```` ```…\n```\n…\n``` ```` → 想保留正文里的 ```` ``` ````。

两者在「只看文本、不看上下文」的前提下**不可区分**。本版选了前者（因为尾随说明更常见），
代价是正文含整行 ```` ``` ```` 时会被截短（测试 5 记的就是这个代价）。
→ 真正的修法是**按链路分别定判据**：JSON 链路（quiz）可以用「第一个能 `JSON.parse` 成功的
闭区间」，标记文本链路（lecture/parser）用「最后一个整行 ```` ``` ````」。这需要
**先拿到真实模型响应样本**，本轮**没有采集**（见下）。

## 未做的事（诚实清单）

- **没有采真实模型响应样本**。上面的样例全部是**构造**的。判据该选哪条，
  取决于真实响应里「尾随说明」与「正文含整行 ```` ``` ````」哪个更常见 —— 本轮没有数据。
- **没有跑全仓回归**。改动 `polish.js` / `core.js` 会波及讲义与解析两条链路，
  本包只保证自己的 12 个用例；接入前必须补跑两边的既有测试。
- **`dsh-zhiyun-parser/src/core.js:4` 是一行内联实现**，没有独立函数名可替换，
  接入时需要先把它提成具名导出，代价比另外三处高。
- **未核 `vision.js` 的调用语义**：它把 `stripFences` 用在「页」标记解析上，
  若改成「尾随说明也剥」，可能改变它切分页面的行为 —— 本轮只读了函数签名，没有跑。

## 建议（评审时按成本排序）

1. **最小改动**：只把 `polish.js:538` 的正则从整串锚定改成「行尾锚定」——
   即 `quiz` 的做法。成本 1 行，不需要新包，不需要动 `parser`。
2. **不推荐**：把四处抽成共享包（本骨架的形态）。只有当「口径必须统一、且要能单独测」
   成为明确需求时，这一步才有价值；否则是给三个包加一层依赖换一个函数。
3. **值得单独做的一件事**（与本包无关）：给四处各加一个「尾随说明」用例。
   今天它们一条测试都没有，所以两边行为分叉了多久没人知道。
