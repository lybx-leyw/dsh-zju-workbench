| --- | --- | --- |

| `ddj`（首字母） | 1 | **0** |
| `daodejing`（全拼） | 1 | **0** |
| `lzddj`（全拼首字母） | 1 | **0** |
| `lisao`（全拼，繁体文本） | 1 | **0** |
| `ls`（首字母，繁体文本） | 1 | **0** |

## 强化哪个现有功能（三条判据）

1. **同一个面板**：不新增导航项。「学习」页（`dsh-zhiyun-page-study`）的检索结果区、
   层过滤条、`limit` 截断位置都不变。
2. **相似正交**：现有回答「这段正文里有没有这几个**字**」；新增回答「这段正文里有没有这几个**音**」。
   同一问题的另一种读法，不是另一件事。
3. **更优底层**：本仓只有 `toLowerCase().indexOf()`；上游有 27KB 拼音字典 + DP 音节切分
   （`wordBreak` / `getAllSolutions`）+ 多音字（`u/v` 与 `ü` 归一、`lv/nv/ju/qu/xu` 特例）+ 繁简双字典。
   这是本仓从零写不出来的量级，且**上游一行源码都不用改**。

## 已知风险（评审重点）

### R1 · 不是「上游能全覆盖」，而是「有覆盖空洞」—— 快路径仍须先行

我最初据一次实测写了「上游对 `数字+汉字` 混排会回 false」，**复核后是错的**：
`match('123曾经沧海难为水', '23曾') → [1,3]`，是正确的。那次 `false` 来自我另一次
用了带**普通空格**的查询串，属于上游的分词器把空格当分隔符（`README` 的示例里
`'zengji ng cang'` 是刻意用空格分词的写法）。

**真正成立的结论是另一条**：上游的 `match()` 是「整串按拼音切分 + 顺序对齐」，
**只要有一对字符切不开就整体回 `false`**。所以：

- `lzdj`（把「老子道德经」的「子」漏掉首字母）→ false；字面也不会命中。可接受。
- 「文本含繁体 + 全拼查询」在**简体入口**上 → false（见上表 `lisao`）。需繁体入口兜底。
- 「文本含稀有字（不在 27KB 字典里）」→ 该字按字符原样参与，拼音查询在此处断掉。

因此实现**必须**：

```
先 findIn(字面)  → 命中就返回（保持现状，零回归）
落空才走 pinyin   → 只增不减
```

并要求一条**集合包含关系**的差分测试：同一 query 下，新实现的命中集合 ⊇ 旧实现。
这条测试是「强化式集成」的可验证判据 —— **上游不是无脑更强，只在读音维度上更强**。

### R2 · `matchEnd` 的闭/开区间

本仓 `findIn()` 回 `{ matchStart: at, matchEnd: at + len }`（**开区间**，供 `previewOf()` 切片）；
上游回 `[start, end]`（**闭区间**）。转换时 `matchEnd = end + 1`，漏掉则预览**少一个字**且不报错。

### R3 · 繁体入口是否要静态加载

实测结论：**简体入口只对「文本里含待匹配简体字」有效**。
「離騷 屈原」配 `lisao` / `ls` 在简体入口下 **false**，繁体入口才对；而同一段文本配
`離騷` 字面，两个入口都命中（字面模式不走字典）。
建议：默认只装简体入口（27KB），繁体入口**懒加载**（首次拼音查询未命中、且文本含繁体字符时再 import 86KB）。

### R4 · 与 `limit` 的交互

命中变多 → 同一 `limit` 下会更早截断。这是**可感知的行为变化**，必须在 PR 说明里写明，
并确认各分支的 `limit` 是否需要按「字面优先」重排（本轮**不做**排序，见下）。

### R5 · 不引入相关度排序

上游只回区间、不回分数。一加排序就会改变「结果先后」这一既有契约 —— 属于另一个议题，
本轮**不做**，也不应该在评审里顺手加上。

## 为什么不选 `opencc-js`（同轮候选，🟡）

[`nk2028/opencc-js`](https://github.com/nk2028/opencc-js)（★361，**MIT AND Apache-2.0**，`1.4.2`）
是简繁转换的正解，实测 `cn→twp` 能把「头发 → 頭髮 / 里面 → 裡面 / 后来 → 後來」转对。

但它要解决的是**另一件事**：要么「查询前把整库转繁再索引」（常驻 **1.1MB** 字典 + 改变正文显示形态），
要么「查询侧先转再比」。前者体积不可接受（学习页是浏览器端首屏），后者会**改写用户输入的语义**
（`头发`→`頭髮` 后再匹配，等于替用户决定了用字）。本轮只做「查询侧多一种**读法**」，
不替用户改写文本 —— 所以 `opencc-js` 记为 🟡，留待「讲义自带简繁切换」这一独立需求时再评估。
