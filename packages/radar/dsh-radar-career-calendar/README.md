### ⚠ 三个必须先裁定、否则不应动工的问题

#### 【1】版权归属异常（**最高优先，先查清再谈集成**）

上游 `LICENSE` 正文写的是：

> `MIT License`
> `Copyright (c) 2026 大连理工宣讲日历贡献者`

而仓库名、描述、采集目标**全是浙大**。两种可能：

1. **模板复制未改归属**（无害，但须确认）；
2. **由他校同类项目 fork 改写**（则**署名与 ATTRIBUTION 写法必须相应调整**）。

→ **在查清之前，不得摘取任何代码。** 这是动工前提，不是收尾项。

#### 【2】采集合规性（**红线**）

采集器抓的是公开宣讲信息，但**"公开"≠"可抓"**：

- 目标站点 `robots.txt` / ToS 是否允许抓取？是否设了限速？
- 数据**是否含个人联系方式**（HR 手机号 / 邮箱）？
  **若有，一律不得入库** —— 本仓是学生工作台，
  **不承担个人信息处理者角色**。

→ **建议**：只借鉴「数据模型 + 订阅导出逻辑」，**采集通道由本仓自建并加限速与过滤**。

#### 【3】`engines.node >= 24`

上游要求 Node ≥ 24，本仓运行时可能低于此（沙箱实测 22.13）。
→ 若走「能力提取」，本包**不继承该约束**（只取其设计，不用其构建链）。

### 需要人工裁定的其他事项

1. **承载方式（决定本包性质）** —— 「独立页」还是「今天页第二条时间线」？
2. **数据来源** —— 本仓自建采集通道（建议），还是接上游已采集数据？
3. **数据模型** —— 宣讲会字段（院系 / 企业 / 岗位 / 时间 / 地点 / 线上 / 投递截止 / 来源 URL）
   应与「今天」页的**学业事件模型分开建**（两者语义不同源）。
4. **时区** —— 日历类项目最容易错的地方。上游有 `clock-check.mjs` 暗示其处理过，
   本仓实现时须一并考虑。
5. **与既有提醒能力的关系** —— 宣讲提醒可否复用既有提醒通道？
6. **stars 为 0** —— 按 B 类判据（"高 stars **或** 明确面向浙大"），
   它靠**"明确面向浙大"**达标；但**独苗项目**，作者弃坑则无人维护，需人工判断。
