## 增强哪个现有功能

**`packages/dsh-zhiyun-host-paper`（论文阅读页）× `packages/dsh-zhiyun-core-notes`（笔记域）
之间那条「读完 → 留下结构化笔记」的通路。**

这条通路**当前是断的**：

| 环节 | 现状 |
| --- | --- |
| 论文阅读页 | 能**读**（iframe 承载上游 PDF 阅读器）、能**译**（选中即译 / 整篇翻译），**读完就完了** |
| 笔记域 | `dsh-zhiyun-core-notes` 是**被动存储域**（零 UI、零解析、零长文策略），只能存人已经敲进去的内容 |
| 中间段 | **解析 + 长文精读 + 结构化产出 —— 本仓完全空白** |

接上游后**同一条通路**补齐：
解析（PDF 等）→ 分段精读（MapReduce 收敛长文）→ Schema 约束的结构化 Markdown
→ 落进既有笔记域（`dsh-zhiyun-core-notes`）。

**为什么不是简单集成**：本仓**没有**深度阅读/解析能力，不存在「重复造轮子」风险；
上游产出形态（结构化 Markdown）**正好接得上**已有笔记域 ——
属于典型的「某功能已有、外部有更优底层时接进来增强它」。

## 接入边界（重要）

本骨架**只做锁版引入 + 承载**，不碰上游源码，也不改他人 `OWNERS`。

**最需先确认的一点**：上游 `dsh` 字段**只声明了 `bundle`，没有 `client`**。
对比 `dsh-voice-mode`（`dsh.client.inject` 注入 9 个 UI 分包）可知二者形态不同 ——
本上游大概率是「**给 Agent 加一个工具**」，而**不自带 UI**。

- 若确为 tool 形态 → **本包不应新增任何 UI**，只在既有页面按钮上调用该工具。
  这反而**更贴合**「仍是同一个面板」的强化式集成判据。
- 若实际带 UI 而未在 `dsh` 字段声明 → 评审时须重新核实，**勿凭猜**。

真正把产出接进笔记域的那一步属于**编辑性质**，**不在本骨架内完成** ——
待评审通过后，由独立的编辑流程处理。

## 需要人工裁定的事项

1. **上游是 tool 还是 client** —— 决定「不新增 UI」还是「挂 UI」（见上）。
   这是本骨架最优先待确认项。
2. **材料类型收窄** —— 上游覆盖书 / 论文 / 视频 / 网页四类。
   本仓明确只需要**论文**；书与网页可视需要保留；
   **视频**与既有 `dsh-zhiyun-core-lecture`（讲座）不是同一域，**是否开放需裁定**。
3. **token 成本** —— 长文精读会**多次调用模型**（MapReduce 分段）。
   本仓是学习工作台，需确认一次「精读」不会把额度打满，并设上限。
4. **产出落点** —— 精读结果写进哪一节的笔记？
   建议按文献 id 建节，与 `dsh-zhiyun-core-notes` 的 `账号.节次` 键约定对齐。
5. **与 `dsh-radar-better-markdown` 的关系** —— 两者**不重复**（一个管「怎么读」、
   一个管「怎么显示」），但同挂到论文页时需确认**加载顺序**。
6. **上游 `lockedRuntime` 风险** —— 上游自述「工具语义随 DSH 升级变化」，
   需确认本仓当前 DSH 版本是否满足 `engines.dsh >=0.1.0-rc.6`。
