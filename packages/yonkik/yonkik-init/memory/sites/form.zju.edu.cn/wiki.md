## 一句话结论（死站还是活站）

**活站。** 三条硬证据：

1. **`/formInfo.js` 返回 1908B 真实配置**，里面有 2 个在册表单短码（`n8ymTRwq`、`35dU2mb6`）和完整的状态码文案表。死站不会返回这个。
2. **第二个表单的 `'200'` 文案被改成「测试！测试！测试！」**（第一个是正常的「表单提交成功！」）—— 这是有人在维护/自测的痕迹。
3. **`/umi.d895a68c.js` = 21,825,378B（21MB）**，含完整业务路由（表单设计器、报表、审核、数据视图、模板上传、水印配置…）。这是正在跑的产品，不是占位页。

**但它是「低存在感活站」**：CC98 只有 2 帖，且其中一帖是「进不去」。原因见下一节 —— 它技术上活着，体验上很容易被判定为坏。

## 免登录可读的东西

**只有一个真东西：`/formInfo.js`（1908B）。**

```javascript
window.formInfoPus = [
  { sUrl: 'n8ymTRwq', formInfo: { '0':'表单ID异常！', '1':'未找到表单配置！', '2':'表单已停止收集！',
      '3':'表单未开始填报！', '4':'表单已过填报时间！', '5':'表单数据收集已达上限！',
      '7':'暂无表单填写权限！', '8':'请输入表单访问密码：', '9':'访问密码异常！',
      '10':'已提交，不允许修改！', '11':'已提交审核，周期范围内无法修改！',
      '12':'已提交，不允许修改！', '13':'已提交，不允许修改！',
      '14':'限定次数大于当前限定（周期）提交次数！', '15':'已提交审核，周期范围内无法修改！',
      '100':'未获取到用户登录信息！', '200':'表单提交成功！',
      '400':'表单提交失败，可尝试刷新页面重新填报' } },
  { sUrl: '35dU2mb6', formInfo: { ...同上..., '200': '测试！测试！测试！' } },
];
```

**这份表本身信息量很大**，它能反推产品能力：
- 支持**访问密码**（'8'/'9'）→ 可设私密表单
- 支持**开始/截止时间**（'3'/'4'）→ 定时收集
- 支持**提交上限**（'5'）与**周期内次数限制**（'14'）
- 支持**审核流**（'11'/'15'）与**提交后不可改**（'10'/'12'/'13'）
- 支持**需登录**（'100'）→ 存在匿名可填与实名可填两种模式

**但没有任何表单内容。** 表单题目、选项、提交数据都不在免登录范围内 —— 只有「短码 → 状态码文案」这一层。

## 「点开就是空白」的成因

CC98 6112974（2025）「进不去了，点开就是空白」。实测成因（不是站点坏）：

1. **`<title>` 为空**（实测 `<title></title>`）。浏览器标签页显示空白，第一眼就像坏了。
2. **主 bundle 21MB**。冷缓存下要下载 21MB 才渲染，弱网/校内出口拥塞时长时间白屏。
3. **渲染依赖内网 API**（`../dfi/nsiTaskPush/...` 等），若 WeLink 登录态过期 → 页面壳在、内容不出。
4. **`robots.txt` 也返回同一个 5256B HTML 壳**（nginx history fallback）—— 说明路由层是「任何未匹配路径 → index.html」，所以**任何错误的深链接也返回 200 白屏**，不会给你 404 提示。

→ **判定：白屏是「21MB bundle + 空 title + 内网依赖」三件事叠加，不是站点下线。** 换浏览器/清缓存/重登 WeLink 大概率恢复。

**帖量只有 2 帖说明什么**：这个站的使用场景是**被组织者发链接给填写者**（短码直达 `/#/formDetailMobile?...`），学生不会主动「上这个网站」。它没有「首页入口」的概念 —— 打开首页本来就是空的。所以「存在感极低」是产品形态决定的，不是站死了。

## 坑

1. **`/robots.txt` 不是 robots 文件**，返回的是 5256B 的 index.html 壳（nginx history fallback）。据此判定「有 robots 规则」是错的。
2. **任何未匹配路径都返回 200 + 壳**，不给 404。所以「HTTP 200」在这里完全不说明路径存在。**必须看内容**。
3. **`<title>` 是空的**，任何靠 title 判断「页面加载成功」的逻辑都会误判。
4. **21MB 单文件 bundle**。抓一次就 21MB，不要重复抓。静态分析一次缓存即可。
5. **bundle 里唯一能看到的业务后端是写操作**：`POST ../dfi/nsiTaskPush/pushProcess?dataWid=..&formWid=..&messageCatalog=form&sendType=fillToFlowAudit&entry=..` —— 这是「推送表单到流程审核」。**属写，不调。**
6. **真正的表单读取/提交 API 前缀没定位到**。bundle 21MB 里被 webpack 拆得很散，静态 grep 只捞到上面的写操作。已记为 unverified，**不猜、不试**。
7. **`localhost:8000` / `127.0.0.1` 类 dev 残留**：bundle 里含 `http://example.com`、`https://yy.xx.edu.cn/...` 等占位配置 —— 是产品模板的默认值，不是可用端点。别当真。
8. **本机必须 `node:https`**（env 代理）。

## 本次探了什么 / 还剩什么

**已探（5 次只读请求）**：`/` · `/robots.txt` · `/formInfo.js` · `/umi.d895a68c.js`（21MB，一次）· `/city.js` `/themes.js` 等静态资源未逐个抓（由首页 script 标签已确认存在）。

**未探 / blocked**：
- **表单读取与提交 API** —— 未定位，且需 WeLink 登录态。
- **能否创建表单** —— 需登录 + 写操作。
- **两个在册短码（`n8ymTRwq` / `35dU2mb6`）能否打开** —— 需浏览器渲染 21MB JS。**这个验证人可以 30 秒做完**：在浏览器打开 `https://form.zju.edu.cn/#/formDetailMobile?...` 或问组织者要直达链接。agent 不必越界。

**脚本**：**未写 `crawler.mjs`。** 理由：本站免登录只有 1 个可读端点（`/formInfo.js`），无检索、无列表、无分页，写爬虫没有可复用的 op。与其凑一个只有 `forminfo` 一个 op 的脚本，不如把这一步（`GET /formInfo.js` + JSON 剥壳）记在这里，下次一行 curl 就够。

**判定它是死站还是活站 —— 活站。** 三条证据（formInfo.js 有在册表单 + 有人在自测 + 21MB 活跃 bundle）都指向「在用」。CC98 的 2 帖低存在感来自产品形态（组织者发短码给填写者，没有首页入口），不代表站点退役。
