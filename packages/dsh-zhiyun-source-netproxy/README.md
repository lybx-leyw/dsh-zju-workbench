# dsh-zhiyun-source-netproxy

智云 Pro 的**分域网络代理**宿主半边。

## 它解决什么问题

DSH 实例会继承全局代理设置。对 DeepSeek 官方接口这类海外目标，走代理是对的；
但智云（`*.zju.edu.cn`）是国内站点，绕道海外代理既慢又不稳 —— 本工作台曾因此
出现「我的课 / 学习」页长时间停在加载态。

更根本的是：**环境变量表达不了分域路由**。`HTTP_PROXY` / `NO_PROXY` 只能给出
「一个代理 + 一串绕开名单」，没法让「域 A 走代理 1、域 B 走代理 2」。所以本包
不靠环境变量，而是让所有出口流量经过一个本地中继，由中继按配置分发：

```
  页面取数 / agent 抓取 ─► 宿主的出口策略 ─► 本中继 ─┬─► 代理 A（如海外）
                                                   ├─► 代理 B（如校园）
                                                   └─► 直连
```

代理地址、域名规则、默认策略**全部由用户在「个人 → 网络代理」里填写**，
代理数量不设上限。本包不预设任何代理地址或域名。

## 为什么是一个中继，而不是给每条通道装分域 dispatcher

宿主的 `@deepseek-ai/dsh-http-proxy` 有一条硬约束（其 README 明写）：
`proxyForUrl()` 与「已安装的 dispatcher」**绝不能对同一个 URL 给出不同答案** ——
否则 `dsh-web-fetch-http` 会把请求钉在策略从未放行的地址上。

所以这里只暴露**一个**代理端点（本中继），让两条通道都指向它。分域逻辑全部
收在中继内部，「策略层的答案」因此永远只有一句「走本中继」—— 从构造上就
不可能不一致。附带的好处：不依赖环境变量，且一行日志就能看清每个请求的去向。

## 配置形状

落在 `<profile>/data/zhiyun-net-proxy/config.json`：

```jsonc
{
  "enabled": false,
  "proxies": [
    { "id": "oversea", "label": "海外代理", "protocol": "http",
      "host": "127.0.0.1", "port": 7993, "username": "", "password": "" }
  ],
  "rules": [
    { "match": "zju.edu.cn", "target": "direct" },
    { "match": "github.com", "target": "oversea" }
  ],
  "fallback": "direct"
}
```

`target` 是 `"direct"` 或某个代理的 `id`。**规则按顺序匹配，先命中先用** ——
这比「按具体度自动排序」更容易预测：用户把宽规则放前面，它就赢。

### 域名匹配支持的写法

| 写法 | 含义 |
| --- | --- |
| `example.com` | 本域 + 全部子域（`api.example.com` 也命中） |
| `.example.com` / `*.example.com` | 同上 |
| `192.168.` | 前缀匹配（等价 Windows 的 `192.168.*`） |
| `*` | 命中全部 |

不做 CIDR：宿主自己的绕过匹配器也不做，保持一致比多支持一种写法更重要。

## 热更与生命周期

- 中继**始终**监听，端口**终身不变**。启用/停用切换不改变端口 —— 宿主里有些
  组件是模块级单例、构造时读一次地址并长连接池化，端口一变它们会连到死端口
  且永不自愈。
- 保存配置后中继**每连接实时读**新配置，因此改路由不需要重启，也不需要重装
  出口策略。
- 卸载时按「先摘路由与服务 → 还原出口 → 停中继」的顺序收尾。

## 它管得了什么，管不了什么

启用后，**服务端这一侧**的出口不再受终端环境变量或系统代理设置影响 —— 实测过：

| 通道 | 启用本包后 | 依据 |
| --- | --- | --- |
| 终端环境变量（`HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` / `NO_PROXY`） | **不再影响** | 宿主的 `installProxyFromEnvironment` 会把这些名字**就地改写**成中继地址（`applyPolicyEnv` → `writeProxyEnv`，大小写都写），并在卸载时还原 |
| Windows 系统代理（浏览器/IE 设置里那套） | **不再影响** | Node 侧从不读它；实测把它指向一个死端口，`courses` / `schedule` 取数照常 |
| 页面自身的同源请求（`/_dsh/...`、插件静态资源） | **不受影响** | 走 Chromium 自己的网络栈，回环由浏览器隐式绕过；实测系统代理指向死端口时 29 条请求零失败 |
| agent 的 `web_fetch` | **跟随本包路由** | 与 `globalThis.fetch` 共用同一份策略（见 `src/egress.js` 的说明） |

**管不了的**（如实说明，避免误以为它能包办一切）：

- **DSH Desktop 右侧的「浏览器」页面**（Electron `<webview>` guest）。它的代理策略在 Electron 主进程的 session 上，而插件宿主是主进程拉起的子 Node 进程，够不到那个 session。它始终跟随 Windows 系统代理 —— 这是 DSH 的架构限制，单靠插件侧无法修复。第三方插件 `dsh-net-proxy` 也记录了同一个限制（其 issue #6）。
- **不是本进程发起的流量**：别的程序、别的浏览器、系统的其他网络活动，一概与本包无关。
- **模型写出的脚本所起的子进程**：宿主不会把可能含凭据的代理地址交给它们（这是宿主刻意的安全取舍）。

## 安全边界

- 中继只监听 `127.0.0.1`，无鉴权，与用户自建的回环代理同级。
- 设置路由只接受回环 Host（防 DNS rebinding），写操作必须带自定义头
  `x-zhiyun-net-proxy`（防 CSRF —— 跨站简单请求带不了自定义头）。
- 读配置时密码一律打码；前端回传打码值表示「未改动」，服务端保留原值。

## 只用宿主已有的东西

本包不引入任何第三方运行时依赖：HTTP CONNECT 与 SOCKS5 握手由 `src/connect.js`
自己实现（协议是公开标准），出口接管用宿主自带的 `@deepseek-ai/dsh-http-proxy`
与 Node 内置 `undici`。
