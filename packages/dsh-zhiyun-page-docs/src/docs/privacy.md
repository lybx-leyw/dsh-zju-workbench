# 个人信息与提交

**本仓库是公开仓库。** 推送出去的任何内容都会立刻可见，并可能在很短时间内被
自动化工具抓取扫描。所以**每次推送前都必须先检查一遍**，范围是本次要提交的全部
改动：代码、注释、文档、测试夹具，以及提交信息。

## 六类红线

**个人凭证** —— 学号、密码、Cookie、API key、token，以及 `.temp_env`、`.env`、
`*.dpapi` 这类凭据或会话文件。不要写进代码、文档、注释、测试夹具，也不要写进
提交信息。

**本地绝对路径** —— 形如 `C:\Users\<用户名>\…`、`/Users/<用户名>/…` 的路径
常因带用户名而暴露身份，同时让别人无法使用。代码与文档里写相对路径或占位符，
例如 `C:\Users\me\dsh-host`。**这一条最容易漏在注释、文档和测试夹具里**，
不要只看源码。

**个人数据** —— 真实的课程、成绩，以及从智云解析出的私人内容。

**姓名等身份信息** —— 带自己或组员姓名、学号、头像、联系方式的资料不要推送，
包括名单、分工安排、会议记录这类交流材料。**仓库内组员之间的交流文档一律用
GitHub 用户名指代，不写真实姓名。**

**提交者信息** —— 它同样进入公开的提交历史：

```bash
git config user.name     # 应为 GitHub 用户名
git config user.email    # 会写进每一条公开提交
```

`user.email` 用哪个取决于账号本身：**如果这个邮箱本来就是该 GitHub 账号的注册邮箱，
用它没有问题**，不必为了藏学号特意改掉；只有在这个邮箱不是账号注册邮箱时，
才应改用 GitHub 的 noreply 地址（形如 `ID+用户名@users.noreply.github.com`，
在 GitHub 设置里可查）。

**`git add -f`** —— `.gitignore` 已覆盖 `.env`、`.temp_env`、`*.dpapi`、`.runtime/`、
`artifacts/` 等路径，正常情况下这些文件不会被提交。但**不要把个人凭证放进会被提交的
文件里，也不要为了省事用 `git add -f` 强行加入**。

## 不确定就按不能公开处理

某个值无法判断能否公开时，先删掉或改成占位符，并告诉用户。宁可少一个有用的例子，
也不要多一条泄露。

## 如果真的泄露了

**一旦发现凭证已经推送出去，应立刻作废并重新申请。** 抓取是自动的，
只从历史记录里删掉并不够 —— 它可能已经被复制走了。历史既已推送过的泄露，
要如实说明它仍在历史中，由用户决定是否重写历史。

## 推送前先跟人确认

**提交与推送前必须先和用户确认，不得擅自提交。**

改动完成、自检通过后，先停下来说明三件事：改了哪些文件、验证了什么、准备用的提交信息
与目标分支。等用户明确同意后，再 `git commit` 与 `git push`。

推送前按上面几节完成信息泄露检查（范围是本次要提交的全部内容，不是本次改动的全部内容），
并把检查结果一并汇报。

`main` 已设置分支保护，**不要直接向 `main` 推送**，推送到工作分支后走 PR。推送到其他
分支同样适用上面那条 —— 一句话概括：**用户没确认，就不产生新的提交或远端更新。**

## 共享仓库只有一个

```text
https://github.com/lybx-leyw/dsh-zju-workbench.git
```

`origin` 必须**逐字符**等于上面这个地址。不一致（不存在、指向 fork、指向别的项目、
用 SSH 别名或跳转链接写法）一律视为错误配置 —— 停下来向用户说明差异，
由用户决定是否修改远端，不要默默继续，也不要凭自己判断"纠正"成别的地址。

推送与开 PR 都受上面那条「先确认」的约束。
