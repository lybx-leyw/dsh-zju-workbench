# Owner 机制

每个目录由一份 `OWNERS` 声明"谁可以改这里"。三种模式，**只约束"谁能改代码"，
不表示上下级关系**。

## 三种模式

| 模式 | 谁能改 | 责任与裁决 |
| --- | --- | --- |
| `shared`（默认） | 所有人 | 修改者对自己的改动负责，相关回归测试必须通过，实际使用不得破坏已有功能 |
| `@负责人` | 仅名单内成员 | Owner 决定实现方向及破坏性变更；名单外成员有需求时直接联系 Owner，由 Owner 修改 |
| `@负责人 + Open` | 所有人 | 修改者负责验证与修复；Owner 负责事后审查，对该区域的最终状态负责，有权保留、调整或撤销他人的改动 |

指定 Owner 且未标 Open 的区域，限制针对**修改行为本身** —— 名单外成员不能先改
再交给 Owner 审批。需要开放协作时，先改成 Open 再说。

Open 区域的撤销权是真实的：与 Owner 确认过的职责、接口或实现方向不符的改动，
Owner 有权撤销，包括破坏性撤销。所以大改之前直接沟通一句，比改完返工便宜。

## 声明放在哪、怎么继承

- 每个目录最多一份 `OWNERS`，文件名就是 `OWNERS`（无后缀），默认作用于该目录及其
  子目录的**全部**内容 —— 源码、测试、配置、文档都算。
- 找某个文件的归属时，从它所在目录**逐级向上**找，第一个遇到的 `OWNERS` 就是它的声明。
  子目录覆盖父目录，根目录那份只覆盖没有自己 `OWNERS` 的区域。
- 一路到仓库根都没有 `OWNERS` 时按 `shared` 管理。插件包与基础设施（脚本、公共测试、
  根配置）适用同一规则，基础设施不单独设例外表。
- **暂不使用 `CODEOWNERS`**：`OWNERS` 是本项目的团队约定，GitHub 不识别、不会自动
  请求评审、也不展示负责人。将来需要时由 `OWNERS` 汇总生成，不另立一份真源。

## 声明格式

每个 `OWNERS` 只写一行 `Owner:`，三种写法选一种：

```text
Owner: shared
Owner: @alice, @bob
Owner: @alice, @bob + Open
```

`shared` 与 `Open` 用固定拼写；`Open` 必须同时指定至少一位负责人。负责人写 GitHub 账号，
带 `@` 前缀，多人用英文逗号分隔。范围由文件所在目录决定，不在文件里写路径；
需要说明时加 `#` 开头的注释行。

## 拿到归属之后怎么做

- **shared 或 Open 区域** → 可以直接改，照常跑测试。
- **指定 Owner 且非 Open** → 只有 `Owner:` 里列出的账号可以改。若任务确实需要动
  他人的非 Open 文件（例如调整公共接口），**停下来**跟用户说清楚，由负责人自己改。

两条禁令，都是为了不让机制被绕过：

- **不得修改他人的 `OWNERS`**，不得把自己写进他人的、且非 Open 的 `Owner`。
- **声明变更需先达成一致，再修改文件**。不得通过自行修改或删除声明绕过权限限制。

## 新增一个包时

按上面的格式给它一份 `OWNERS`，让后来的人知道这个包归谁、能不能改。不写 `OWNERS`
同样按 `shared` 管理，但那样没有人知道该找谁。标成 `@某人 + Open` 是最常见的写法 ——
所有人能改，出了方向性问题有人能拍板。
