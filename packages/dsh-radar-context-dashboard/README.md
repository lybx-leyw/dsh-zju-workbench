## 增强哪个现有功能

**`packages/dsh-zhiyun-page-today`（「今天」页）的会话状态区 × `dsh-radar-deep-read` 的
精读链路的「上下文预算」这一件事。**

本仓是**长材料密集型**工作台，上下文是它的**核心稀缺资源**：

| 吃上下文的环节 | 现状 |
| --- | --- |
| 论文阅读页（`dsh-zhiyun-paper`） | 吞吐整篇 PDF |
| 笔记域（`dsh-zhiyun-notes`） | 挂长文 |
| 精读（`dsh-radar-deep-read`） | **分段多次调用模型**，是最大户 |
| 「问一问」 | 多轮追问持续累积 |

而**本仓没有任何一处能回答「上下文被什么占满了」** ——
学生只能等模型开始丢信息（答非所问）才发现出事了，属于**事后才发现**。
接上游后**同一位置**补齐「事前可见」：按来源分解的构成 + 剩余预算 + 膨胀趋势。

**为什么不是简单集成**：本仓**没有**上下文统计能力，不存在「重复造轮子」风险；
上游形态（sidebar / dashboard）**正好接得上**「今天」页右侧栏 ——
属于典型的「某功能已有、外部有更优底层时接进来增强它」。

## 接入边界（重要）

本骨架**只做锁版引入 + 承载**，不碰上游源码，也不改他人 `OWNERS`。

**最需先确认的一点**：上游 `dsh` 字段声明了 `client.inject` 注入
**6 个 UI 分包**（含 `dsh-client-ui-sidebar-right` 与 `dsh-client-ui-settings`），
即它**自带 UI、是面板型插件**，而**不是**纯工具。

对比 `dsh-radar-deep-read` 的上游（只声明 `bundle`、无 `client`，判定为 tool 形态、
「不应新增任何 UI」）—— **两者的接法完全不同，评审时勿套用**：

- 本上游会往**右侧栏**和**设置页**挂东西 → 必须先裁定与本仓既有内容的共存方式。
- 上游的 `dashboard` / `browser` / `context 命令` 三个入口，对学习工作台而言
  只需保留**统计与构成**，其余入口宜收窄。

真正把「上下文构成」挂进「今天」页右侧栏的那一步属于**编辑性质**，
**不在本骨架内完成** —— 待评审通过后，由独立的编辑流程处理。

## 需要人工裁定的事项

1. **DSH 版本是否落在上游白名单内**（最优先）—— 上游只声明
   `0.1.7-rc.2` / `0.2.0-rc.2` 为 `compatible`。本仓当前版本若不在其中，
   **必须先核再挂**，否则可能静默降级或直接失败。
2. **Node 版本** —— 上游要求 `^22.19.0 || >=24.0.0`。这条比 DSH 版本**更容易被忽略**，
   且不满足时挂载即失败。本仓须先确认。
3. **右侧栏 / 设置页的共存方式** —— 上游会注入两者。是叠加、分 tab，还是二选一？
   当前本仓这两个位置都已有内容，需明确边界。
4. **peer 依赖版本比对** —— `react ^18.3.1` 与
   `@deepseek-ai/dsh-client-ui-primitives >=0.1.7-rc.2`。
   不匹配通常**不硬报错**，而是静默样式错位，更难发现。
5. **能力入口收窄** —— 上游四块能力（统计 / 构成 / 分解 / 演化），
   本仓建议只取**统计 + 构成**；`browser`（逐条浏览）与 `evolution`（历史演化）
   是否开放需裁定。
6. **与 `dsh-radar-deep-read` 的加载顺序** —— 两者**不重复且互相需要**
   （精读是吃上下文的大户，本包是让吃法可见）。同时挂载时需先有统计，
   精读才可观测。
7. **上游高迭代风险** —— 版本号已到 `0.71.0` 且推送频繁（2026-10-14）。
   锁版后若需升级，须人工重新复核 `client.inject` 形状与白名单，
   **不可依赖 `npm update`**。
